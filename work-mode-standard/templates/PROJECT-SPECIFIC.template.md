# PROJECT-SPECIFIC.md 项目专项模板

> **怎么用**:把「工作模式标准」装进新项目时,复制本文件到项目 `docs/PROJECT-SPECIFIC.md`,把全部 `<尖括号>` 占位符替换成新项目的实际值,**删掉与本项目无关的条目**(章节骨架保留)即可。
>
> **这是什么**:标准包(共享核心 / 主控层 / 角色层)里的规范都写成通用词,凡是「每个项目长得不一样」的东西——项目名、域名、部署命令、定时任务时点、权威数据源、展示位、公示文件、禁止事项——一律写在本文件。标准包里对应位置只留 `<占位符>` 指针,指到本文件。
>
> **状态型内容纪律**:本文件是**活文档**,里面的值随时间会变;每次改动了依赖它的东西,顺手更新对应行。角色 skill 与共享核心**绝不**写死这些状态值(写死了就会过时,过时的规范比没有更危险)。

## 0. 项目概览

- 项目名:`<项目名>`
- 一句话定位:`<这个项目是干什么的>`
- 技术栈:`<前端 / 后端 / 数据存储 / 部署方式>`
- 代码仓库:`<仓库地址 + 公开还是私有>`
- 开发机 vs 生产机:`<本机跑不跑定时任务 / 生产机在哪 / 有没有云上机器>`

> **为什么要有这一项**:同一个项目里,"写代码的机器"和"跑任务出数据的机器"常常不是同一台;搞混了就会在本机去找一个其实跑在云上的任务,白忙一场。

## 1. 线上域名与部署

- 主域名 / 备站:`<主域名> / <备站1> / <备站2>`(验收时任一域名到新版,即算上线 OK)
- 部署命令:`<部署脚本路径 + 用法>`
- 合并 / 推送统一入口:`<主分支合并统一脚本>`

> **为什么要有这一项**:上线验收、多站同步、防"只在主站生效",全靠这些具体地址与命令。

## 2. 定时任务时点表

| 时点 | 任务名 | 做什么 | 归属机 |
|---|---|---|---|
| `<HH:MM>` | `<任务名>` | `<一句话说明>` | `<本机 / 云上>` |
| `<HH:MM>` | `<任务名>` | `<一句话说明>` | `<本机 / 云上>` |

> **为什么要有这一项**:判断"现在能不能部署 / 能不能重跑数据"必须先看这张表;撞上正在跑的任务 = 线上数据被覆盖的事故。

## 3. 权威数据源

- 生产数据的权威库 / 权威目录:`<路径或描述>`(本机可能只是陈旧镜像,**行数都可能不一样**,别拿本机当权威)
- 回测 / 测试基准定义、复现数字:`<版本号 + 关键口径 + 基线数字>`

> **为什么要有这一项**:同一份数据本机与线上可能不一致;断言"有没有 X / 有多少行 / 某天全不全"之前,必须先认准哪一份才是权威。

## 4. 产物同步链路

- 数据产物目录(部署对象):`<目录>`
- 同步链路(改一处要一起动的地方,一条不落):`<本地产物目录 → 线上存储 → 缓存层>`
- 缓存层与清缓存方式:`<缓存位置 / 过期规则与清理办法>`

> **为什么要有这一项**:用户看到的数据来自"文件 + 缓存"两处;只更新文件不更新缓存,用户看到的还是旧数据。

## 5. 公示位清单

- 算法 / 口径公示文件:`<公示文件路径>`(改了算法或数值,**必须**同步改这里的说明文字)
- 说明文字里要一起改的关键词:`<关键词列表,如"评分 / 权重 / 匹配规则 / 百分位">`
- 同一事实的多处副本(键集 / 字段清单 / 白名单 / 端口):`<各登记点位置>`

> **为什么要有这一项**:算法改了、界面上的说明没改,用户会照旧规则理解,等于误导;同一事实的多个副本不同步,就是"用户在不同地方看到不一样的数据"。

## 6. 禁止事项

- 不该进 git 的文件 / 目录:`<本地数据库 / 缓存 / 密钥 / 大文件>`
- 时间禁区:`<什么时点不许推主分支 / 不许跑全量任务>`
- 凭据纪律:`<密钥从哪读 / 不许硬编码 / 不许打印>`

> **为什么要有这一项**:这些是"碰了就会出事故"的红线;写出来,才有人守得住。
