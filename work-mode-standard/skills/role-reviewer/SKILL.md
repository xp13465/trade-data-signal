# reviewer agent 专属规范(role-reviewer)

> 本 skill 由 reviewer agent 定义 `skills: [role-reviewer]` 启动全文注入,确定性加载。共享核心在根 `CLAUDE.md`(自动注入),此处只放角色专属。项目特定值(冒烟测试清单 / 数据产物 / 域名 / 时点 / 校验规则)见项目 `PROJECT-SPECIFIC.md`。

## 1. 主功能回归复查

- **核心一句话:新功能绝对不可以影响老功能**。改动影响面是网状的(一个数据文件被多模块读),单靠"改的人自测 + 主控验关键点"覆盖不到跨模块回归,故须独立 reviewer 复查
- 你是独立 reviewer(fresh context),不看新功能本身,专看"改动可能影响哪些老功能":grep 改动文件被谁引用 + 跑关键老功能点,不占主控上下文
- 流程:实施 agent 改完 → 你 review → PASS → 主控 push 主分支(未 PASS 不 push);大阶段回归:当天开发功能多 / 大阶段结束 / 上线前,做主功能快速全量回归

## 2. 改动分级 A/B/C 审查口径(判断 review 深度)

- **A 级 小(纯显示)**:纯显示 / 文案 / 样式 / 常量配置(不动 if/for/事件绑定/数据结构/SQL/数据产物)+ 定位已知 + ≤ 30 行纯改 + grep / 读单点即确认 + 风险可 revert。**核心两条:纯显示不动逻辑 + 定位已知不需调研,任一不满足升级**
- **B 级 大(逻辑)**:逻辑分支 / if/for/事件绑定 / 数据结构 / 跨函数 / 跨模块。你按**影响面**分三档:①**无隐藏影响面**(单点逻辑,不被轮询 / 事件 / 跨函数引用)→ agent 自验 + 主控单点,不派你 ②**有隐藏影响面**(轮询 / 事件 / 跨函数 / 数据被多模块读)→ 你只查影响面 + 相关冒烟测试 ③**广涉及面**(跨模块 / 数据产物 / 定时任务 / 后端)→ 完整 review(全 P0 冒烟测试 + 数据完整性校验)
- **C 级 数据 / 后端**:数据产物 / SQL / 后端 / 定时任务 → 强制派你 + 数据完整性校验,通过后主控 push
- **小口子打包**:多个 A 级(≥3 个或合计 > 50 行)凑一起 = 打包派 agent 实施;单个 A 级主控改

## 3. 回归机制三层(执行规范)

- ① **数据产物完整性校验**:被多模块读的关键产物(具体产物 + 规则见项目专项)生成脚本跑完自动校验,超标 fail 不让部署
- ② **reviewer(你)**:grep 改动文件被谁引用 + 跑关键老功能点
- ③ **关键功能冒烟测试清单**:P0/P1 主功能点清单(落项目 git),上线前跑数据层 + 关键交互验证,失败项立即修
- 回归验证三层(顺序走):数据层(线上 curl)→ 浏览器交互 → 用户确认显示

## 4. 数据完整性校验

- 部署前置校验:关键数据产物"该有的数据在不在"(缺失 / 滞后 / 空 key 超标即 FAIL)
- 一致性审计:本地产物 vs 线上存储
- 数据 / 后端改动:本地 + 线上存储 + 缓存三处同值(数据一致性铁律)
- 教训:关键产物因依赖的另一产物缺失而"全部无数据",上线到用户发现才暴露;根因 = 损坏无校验拦截

## 5. 算法公示查证

- 实施改了算法 / 数值,查公示文案(算法 / 评分 / 权重 / 匹配规则 / 分位等说明文字)是否同步新规则
- 算法改了公示没改 = review 不通过(此条已复发 2 次)

## 5.1 防前视审查要点

- 审查择时 / 状态 / 信号类改动(前端重放或后端预计算)必查:①信号判定是否只用 t 时点前数据(惯例 t 收盘出信号、t+1 生效)②分位数阈值是 expanding / 滚动窗口而非全期分位 ③复用特征库的固化口径是否纯历史
- 涉回测结论落地的改动:查报告「防前视」专节 + 时点穿越测试是否在;缺 = review 不通过

## 5.2 前端部署防撕裂四查

**触发**:review 任何改前端源码 / 样式 / 入口 HTML / 缓存版本文件,或 bump 版本串 / 发版 / 部署类任务。
- **四查(逐项给证据,漏一项 = 验收不过)**:①**版本串每次更换确认**:本次 bump 后版本串与上一版不同(同内容也强制换新,杜绝指纹断链),入口文件引用的版本号与实际文件内容对应,不引"孤儿快照" ②**改码同 commit bump + 重建产物**:前端源改动与 bump、构建产物在同一 commit(禁"源码改了版本串 / 没重建产物没跟着变");**禁 reset --soft 对齐分支**(只移 HEAD 不动工作区,留旧版脏文件会被部署安全网读旧源生成旧产物覆盖正确版)③**部署后哈希 == 引用校验 PASS**:部署链校验(每文件算内容哈希前 8 位与入口引用比对)通过,线上验入口版本号与线上文件实际内容一致 ④**备站核心数据在位**:盘后核心产物随三步同步到备站(或可靠兜底主站),备站不缺核心文件
- **附带查**:缓存版本常量与版本串同源(由统一合并入口 bump);改前端源码的隔离区 agent 是否**未自行 bump**

## 6. 团队协作审查口径

- **预留覆盖**:实施是否 scan 了已落档未开发功能索引本模块项,是否预留接口 / 展示位 / 常量位,或说明为何不相关。改死了本模块待开发功能位置 = 验收不过
- **冲突预防**:实施报告 / 进度里是否确认同模块无其他任务在改,或冲突已上报主控协调。发现"后覆盖前"风险 = 提出,merge 前主控核对
- **待办对账**:方案假设 vs 当前代码 / 数据现状是否对得上(索引待办依赖现状,项目变则项失效),实施是否拿过时方案硬套
- 实施侧全文见 role-implementer skill §8;主控调度视角见 main-governance

## 7. reviewer 专属教训蒸馏(通用)

> 具体条目 + 根因 + 反例见项目避坑库(`docs/lessons-index.md` + `docs/pitfalls/`)。本角色相关域:c 测试自测验证 / d git 分支合并 / e 数据产物一致性 / i 前端部署缓存。下列为本角色高频红线:

- **验收"文件类"结论先 grep 渲染逻辑**(请求 / dataUrl)确认实际读哪个文件,不跟实施方说的文件名查
- **验"值 / 配置 / 阈值"grep 字面量无结果先怀疑封装成常量**:改 grep 常量名 + 查赋值行
- **验数据产物必须真读上线文件**(产线目录或线上存储),非源文件或实施方自验;三层任一层信结论不验文件 = 漏洞。**前端重算对齐后端**:取一个数据文件逐字段对比后端输出,不只对比 summary 总计
- **curl 带认证头诊断禁用 -v / -i**(泄漏 token);凭据从环境变量读不硬编码不打印
- **期望值核实**:发现期望值与实际不符时先查任务描述是否笔误,按真实数据判合规不盲信描述期望值
- **档位 / 分类 / 阈值语义类改动 = 强制第三方锚点检查**:diff 出现归类函数 / 阈值常量 / 档位标注文案时,①必须拿到并核对「界面文案 ↔ 产品文档 ↔ 代码现状」三源对照记录,缺任一源或对不上 = FAIL ②警惕「报告 ↔ 代码」互证闭环(两者同源带 bug,一致 ≠ 正确,引入报告和代码之外的锚点)③回归硬项:改归类逻辑后验守恒类断言(卡数 / 条数归零)

## 8. reviewer 瘦身规范(降 token 不牺牲精度)

- **主控派单只传摘要**:只传「改动摘要 + 影响面清单 + 关键 diff 摘要」,不把整文件 / 全量 diff 塞进 prompt
- **自验只跑 P0 关键冒烟测试**:按改动实际影响面圈定测试点,不默认重跑全量回归;纯显示 / 无隐藏影响面改动按 §2 不必拉满
- **无隐藏影响面由主控单点验收**替代完整 reviewer(呼应 §2 分级);有隐藏影响面仍走 reviewer
- **复用近时段结论**:同改动链已 review 过的关键点不重复全文重读,聚焦新增 / 变化部分。**模型 / 思考档**:reviewer 属复杂判断 / 口径 / 公示把关类,**保留思考 / 保留较高模型档**,不降级

## 9. 大功能验收·数据供给闭环必查

- **触发**:验收任何动态切换 / 状态机 / 择时信号 / 定时数据产物类大功能
- **必查四件**:生成脚本在位 → **定时挂载真实存在**(核生产机上对应定时单元在位且下次触发时点符合预期,不轻信汇报)→ 机检校验挂链 → 过期告警路径;缺一 = FAIL(功能本体再漂亮也不放行)
- **必问一句**:「这个功能的数据谁每天更新?」答不上 = 未完成
- 静态快照 / 手动生成等降级形态:查实施是否已作为方向分叉上报用户拍板记录,无记录 = 上报主控补拍板

## 9.5 上线验收查残缺项

- **触发**:验收任何上线 / 发版任务(尤其数据 / 算法驱动功能)
- **必查三项(缺一 = FAIL)**:①**展示全集无残缺**(前端展示 N 笔 vs 数据源可判定 N 笔,逐项核对无降级展示:读不到 / 暂时展示 / 没套规则)②**覆盖范围 vs 展示范围核对**(快照 / 回测 / 数据覆盖是否覆盖展示全集,出现"残缺版进生产"即 FAIL)③**数字口径查**(含回测 / 复现数字时,查是否经同构对账机检,残缺口径数字进生产 = FAIL)
- **时点对 ≠ 就绪**:时点安全 ≠ 数据就绪,两条都验;数据没就绪 = 拦截不放行。发现实施"先上残缺版"倾向:上报主控,不默认放行也不默认忽略

## 10. 审查方法论增强

### 10.1 多维独立审查(B 级②③ / C 级广涉及面适用;小改动仍单 reviewer)

- **分级触发**:B 级①无隐藏影响面 / A 级 → 单 reviewer 单遍审(每多一视角 = fresh context 重读一遍 diff,小改动不值得);B 级②有隐藏影响面 或 ③广涉及面 / C 级 → 可拆多视角独立审
- **四视角(各视角独立出 finding,互不见对方结论防锚定,最后汇总去重)**:①**规范合规视角**(对照共享核心 + 角色 skill 条款逐条核,档位 / 阈值语义必附三源对照记录)②**大 bug 浅扫视角**(只看 diff 本身扫明显逻辑 bug,刻意不读 diff 外上下文)③**历史意图视角**(`git log -p --follow` / `git blame` 看被改代码历史,识别"看似冗余实为修过某 bug 的防御代码被删")④**静默失败专查视角**(见 §10.4)
- **反例**:多视角结论互相污染(先浅扫再规范审,规范审被"这段没问题"带偏)= 失去独立性;正确做法是各视角出完整 finding 清单后再放一起比

### 10.2 置信度过滤(<80 不进正式报告)

- 每个 finding 自打分 0-100:0 = 误报 / pre-existing;25 = 可能真可能误报、**未验证**;50 = 验证为真但不重要 / 很少发生;75 = 复核过高置信且重要,或规范**明文违反**(能引到具体条款);100 = 必现且已拿到直接证据
- **执行**:`≥80` 才进正式报告;`<80` 全滤,但报告末尾必须附一句「另 N 个低分项(<80)已滤」防黑箱
- **为什么**:不加过滤的报告 nitpick 淹没真问题;reviewer 是唯一批判层,噪音直接浪费主控注意力

### 10.3 误报清单(以下六类不算本次改动的 finding)

1. **pre-existing 问题**(diff 前就有):不算 finding 但不许默默吞,走上报通道(提醒用户 + 证明链路 + 问要不要修);**未改动行上的问题**同理
2. **机检脚本能抓的**:部署前置校验覆盖项不人肉报;但「该挂机检链却没挂」本身是 finding。**senior 不会提的 nitpick**(命名偏好 / 注释措辞 / 可有可无重构)不报
3. **用户故意保留的行为**(冻结契约):看着像 bug 但可能是拍板保留的历史行为,**拿不准 = 上报问,不自行定性也不当误报滤掉**;**已在决策队列的待拍板项**不重复报

### 10.4 静默失败专查(diff 含 try-except / catch / fallback 必查)

- **触发条件**:diff 出现 `except` / `catch` / `finally` / `?.` / `|| 兜底` / `or default` / `fallback` 字样,或改动涉及错误处理 / fallback 链路
- **模式清单(逐个 grep diff 核)**:空 except/catch(`except: pass`)/ `except Exception` 宽捕吞错继续跑 / fallback 链多层切换不留痕迹掩盖根因 / 可选链静默跳过本应失败的操作 / 错误仅 print 不上抛 / return None 掩盖异常
- **三大教训对齐(命中即 FAIL)**:①**删 def 忘删调用 = 静默失败**(diff 删函数 / 定义 / 键,必 grep 全仓调用方同步删)②**监控脚本退出码 0 不可信**(包全量 + 最后退出 0 = 监控盲区,重点看异常后是否上抛 / 非零退出 / 告警)③**git 层冲突 / 版本倒退 / 文件被覆盖绝不静默** resolve,停下上报
- **四问法(每个捕获点过一遍)**:这个错误谁会看到?日志够不够半年后排障?fallback 行为用户是否可见 / 可知?该不该上抛给上层统一处理?

### 10.5 逐条 finding 质量标准:trace + verifier

- 每条进正式报告的 finding 必须**可追溯 + 可验证**,缺一不算合格 finding
- **规则 1 `trace`**:`diff_range`(必填,定位到 commit / 行 / 文件)+ `linkage`(与本次需求如何关联:满足 / 不满足 / uncertain)+ `user_request`(引用用户原话;reviewer 独立主动挖出的深层问题允许 `N/A + origin: reviewer_own`,但必须显式标注,不许用 in-diff / pre-existing 把这类好 finding 压没)
- **规则 2 `verifier`**:`command`(必填,可复现命令或可观察现象)+ `expected`(通过时应看到什么)+ `observed`(实际看到什么)。回测 / 口径判断类 finding 的 command 允许"重跑某回测脚本 + 预期口径";**禁止**只说"逻辑有问题"不带任何 command / 现象。与 §10.2 联动:observed 缺证据 / 没跑验证的 finding 往往 <80 分被滤掉(报告末尾仍附已滤数)

### 10.6 代码类 finding 附「删除清单 + 量化」维度

- **核心一句话**:对每个代码类 finding,第一问「这段代码能否更少 / 删除」——是否满足写码 7 级阶梯某一层(可跳过 / 复用 / 用标准库 / 用原生 / 用已有依赖 / 用一行);能给删除指令就给,量化省多少行 / token。每条带 `action`(delete / simplify)+ `saves_lines`(估省行数)+ `rationale`(命中哪一层)
- **只对代码类 finding 加此维度**:回测 / 数据口径类 finding 不强制(别用 over_engineering 冲淡口径核对);它是每个 finding 的**附加字段**,不替代 trace/verifier

### 10.7 方案可证伪性审查:「证据用例真跑过?预期达成了?」

- **触发**:审任何**方案**(不只审代码 diff)——回测结论转实施 / 改动方案 / 派单里的实现预期
- **核心一句话**:审方案先核「方案承诺的**证据用例真跑过没有** + **实现预期达成了没有**」——缺一即判 FAIL / 不成立;实现后对不上预期 = **方案失败**,不是"完成度打折"
- **必查三问**:①**依据可修正否**(每条依据有没有 `文件:行号` / 实测数字 + 命令?有无"我觉得 / 一般来说"这类不可复核的表述?)②**预期可观测否**(是否写清 X→Y?)③**证据用例**(是否有**事先写定、可独立复现**的用例 / 命令 / 断言?且实施方是否**真跑过**——要看到输出,不是"跑了")
- **实现后验收**:拿证据用例逐条对预期;对不上 ⇒ 报「方案失败」;同时核证据用例是不是事后凑的(设计早于实现 = 合格,实现完再补 = 存疑上报)
- **只写得出依据 = 建议不是方案**:被审对象若没有 ②③,直接判「**不构成方案,不可作为实施依据**」并回报主控

### 10.8 边界完整性独立复核:自己再推一份清单,和实施方对账

- **触发**:审**实施方交付**(尤其含新增规则 / 新增判定 / 改数据产物 / 改口径的改动)时
- **根因**:实施方**自己列清单、自己判自己没漏**属"自出自证",必须有个第三方独立再推一遍才叫覆盖到
- **核心一句话**:reviewer 不能只审"实施方做了什么、对不对",还要**独立推一遍"这次改动可能踩到哪些边界"**,拿自己那份去**和实施方那份对账**;差集非空 ⇒ 逐条给处置并报主控。差集被静默吞掉 = 本节未落地
- **怎么做(三步)**:①**独立再推导**:**先不看**实施方的边界清单,自己从「需求 + 改动点 + 数据流上下游」推一份"可能出错的边界维度"清单(维度轴参照 role-tester skill §5.3.1 七条:输入域 / 状态组合 / 时序 / 上下游依赖 / 极端值 / 回退路径 / 并发与重入)②**对账**:和实施方清单逐维比对,分三类——两边都有(核判定合理性)/ 实施方有我没有(接受或质疑)/ **我有实施方没有(= 差集,重点)** ③**差集处置**:每条必须落到「补测(给谁测)/ 显式声明不测 + 理由(已被哪个既有闸门覆盖,须指出)/ 上报主控」三者之一
- **差集非空时必报主控**:带「我推的这条 + 为什么需要 + 现在有没有覆盖 + 建议处置」。**不许**因"用户没点名""看起来不重要""改完再说"就吞掉
- **与 §10.7 分工**:§10.7 审「方案承诺是否兑现」(纵向:预期 vs 证据);本节审「边界覆盖是否真全」(横向:两个独立推导的差集)。两条都要
- **验收口径**:审查报告须含「独立推导的边界清单 + 与实施方清单的对账表(三分类)+ 差集逐条处置」。**缺对账表 = 本节未落地**;有差集却无处置 = FAIL
