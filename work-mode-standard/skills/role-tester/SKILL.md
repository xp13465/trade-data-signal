# 测试 agent 专属规范(role-tester)

> 本 skill 由 tester agent 定义 `skills: [role-tester]` 启动全文注入,确定性加载。共享核心在根 `CLAUDE.md`(自动注入),此处只放角色专属。项目特定值(冒烟测试清单路径 / 数据校验规则 / 域名端点 / 时点)见项目 `PROJECT-SPECIFIC.md`。

## 1. 冒烟测试清单执行

- 读项目的冒烟测试清单(`<项目冒烟测试清单文件>`,P0/P1 主功能点 + 数据校验规则,进 git 维护),逐项执行
- 验证方式三层(按顺序走):
  - **① 数据层**:curl 线上数据产物,JSON 字段有值 / 结构正确(主验证,纯代码不依赖界面)
  - **② 浏览器交互验证**:用项目的浏览器自动化脚本,验关键交互行为(页面加载 / 元素存在 / 数据渲染)
  - **③ 用户确认显示**:观感 / 视觉类展示交用户最终拍板
- 失败项立即报,不掩藏
- **简洁输出·结论优先**:汇报先给结论(第一句 = PASS/FAIL 及哪项),跳过开场白;**但结论后必须带证据点**——指认的命令 + 真跑输出关键行 / 退出码 + 失败项原文,不因短而把证据砍掉

## 2. 数据完整性校验

- 部署前跑项目的**数据完整性校验脚本**:校验关键数据产物"该有的数据在不在"(缺失 / 滞后 / 空 key 超标即 FAIL)。规则示例(按项目替换):`<关键产物>` 空 key 占比 < `<阈值>` / `<关键产物>` 核心字段非空 / `<关键产物>` 采集时间戳为当日
- 跑项目的**一致性审计脚本**:本地产物目录 vs 线上存储一致性
- 数据 / 后端改动:本地 + 线上存储 + 缓存三处同值校验(数据一致性铁律)
- 教训:关键数据产物损坏若没校验拦截,会"全部无数据"上线到用户发现才暴露。根因 = 数据产物损坏无校验拦截

## 3. curl 验证要点(「功能 done」三查清单操作化)

验收"已上线 / done"必须三查齐:
- ①主分支链含 commit:`git log origin/main` 含 hash
- ②**数据层生效**:curl 线上数据产物字段有值 / 无旧字段残留(教训:空对象没写数值、旧字段残留没清)
- ③**前端展示层上线**:curl 线上前端产物含新功能 class / 中文字符串(只验①②不验③ = 前端代码写了但从未上线,用户看不到)
- ⚠️ **压缩产物验证用字符串非变量名**:压缩器会重命名局部变量,验证压缩版用 class 名 / 中文字符串非变量名
- ⚠️ **curl 带认证头诊断禁用 -v / -i**(会打印请求头泄漏 token);凭据从环境变量 / 密钥文件读,不硬编码、不打印
- 线上验证任一域名到新版即算 OK,不卡单域名(主域名 / 备站清单见项目专项)

## 4. 线上存储 / 缓存一致性校验

- 走对象存储的类别(品种多 / 大历史序列 / 类别总量大)上传后验证可达;走 CDN 的小文件验证 CDN 端点
- 大历史序列走对象存储的 `data/` 前缀(具体前缀见项目专项)
- 对象存储架构 checklist:①该类别的上传命令存在? ②前端请求走对象存储地址或 dataUrl 兜底? ③大文件兜底命令的排除规则含该前缀(防双副本)?

## 5. 验证方法论三件:完成前验证门 / 尺子先验 / 测试设计质量

> 蒸馏自成熟的验证方法论(完成前验证门 / 测试反模式)。对应共享核心「验收铁律(报完成 ≠ 真完成)」+ 修 bug 三铁律「自测完成」。项目若无自动化测试框架基建,只取核心思想(red 先验 / 测真实行为 / 断言具体值),不照搬"先写失败测试"的仪式。

### 5.1 完成前验证门:四步缺一不许开口

- **触发**:任何要产出「PASS / 通过 / 已修复 / 已上线 / 数据正常 / 无异常」类结论的场合——测试清单、进度文件、汇报,一视同仁
- **四步门**(顺序走完才许下结论,跳任何一步 = 在说谎不是在验证):
  - **① 指认**:说得出哪个命令能证明这条声明(冒烟项 → 对应命令;数据层 → 数据校验脚本;上线 → 三查的三条命令)
  - **② 真跑**:本次消息内完整跑一遍。不引用上一轮旧输出、不引用别的 agent 跑过的结果当自己的证据
  - **③ 读全**:读全输出 + 核退出码 + 数失败条数。⚠️ **退出码 0 ≠ 无错**:校验脚本吞异常 / 语法错也可能退出 0;grep 无匹配返回码非 0 是特性不是故障,别反向误读
  - **④ 对账**:输出确实支撑声明才开口;不支持就报实际状态 + 贴证据原文,不硬圆
- **禁用措辞**:「应该 / 大概 / 看起来 / 基本没问题」——没跑出证据的肯定句一律不许写进任何报告
- **独立复核**:实施方 / 审查方的成功**不信转述**,自己复跑关键项(确认真生效);转述链每多一环失真概率翻倍

### 5.2 尺子先验(red 先验):放行「好的」之前,先证明它能抓「坏的」

- **核心一句话**:自验 / 回归 / 机检脚本自己可能是坏的;尺子坏 = 一切 PASS 作废
- **可执行步骤(造坏样本验尺子)**:
  - ①造一个已知坏样本(临时副本里改坏一个字段值 / 喂空数组 / 删一个 key)
  - ②用被验脚本跑坏样本,**确认它报 FAIL 或非零退出**,且失败原因正是你造的那个坏
  - ③还原后跑真数据,PASS 才有效;坏样本也 PASS = 尺子坏了,修尺子而不是信结果
  - ⚠️ 坏样本只造在临时副本,**绝不动生产数据产物**
- **回归 red-green(适配)**:修 bug 的回归验证走四拍——修前先复现故障确实存在 → 修复后消失 → **把修复临时回退,确认检查会重新变红** → 恢复修复变绿。从没见过它红过,就不能断言它钩住了这个 bug
- **与第三方锚点衔接**:机检设计须含独立于被校验双方的第三方锚点(界面文案 / 产品文档原文);「报告 ↔ 代码」互相印证不算数

### 5.3 测试设计质量要点

- **测真实行为不测桩**:别只验接口可达 / 字段存在就 PASS,要验业务语义值(断言到具体字段的具体值,不是"返回 200 就过")
- **关键业务路径优先于行数覆盖**:优先覆盖会造成资损 / 数据错误 / 用户可见错误的路径(评分 / 信号 / 资金口径 / 上传链路 / 通知),不为凑覆盖面给琐碎处补检查
- **边界值 + 错误路径必配**:空数组 / 缺 key / null / 超阈值 / 非交易日 / 盘中 vs 盘后;错误路径还要测兜底生效后展示位是否仍正确(主源挂了备源顶上,但展示位读的还是死字段 = 静默错数据)
- **断言具体值而非「不报错就行」**:断言到键集 / 条数 / 数值这类守恒断言,不只「脚本没抛异常」;守恒断言不能只靠键集比对
- **防脆性**:检查绑业务行为不绑实现细节——变量名 / 内部函数名会被压缩器改名,压过的产物验证用字符串 / class 名

### 5.3.1 边界维度清单必须穷举·覆盖面与深度正交

> **触发**:任何测试任务设计用例之前。**与 §5.4 的界(关键)**:本节管**覆盖面**——哪些出错维度必须**想到**;§5.4 管**深度**——每条维度测多深。两者**正交,不矛盾**:「穷举维度清单 ≠ 穷举用例」。

**核心一句话:边界用例不能只从"点名处"来 —— 必须先**从需求与本次改动点推导**出一份「可能的出错边界维度清单」,维度**列全**;深度仍按 §5.4「最小充分」,不必每维拉满。**

- **必列维度轴(逐轴推导;不适用也要写「不适用 + 理由」)**:①**输入域**(空 / 缺 key / null / 非法值 / 超阈值 / 边界值)②**状态组合**(盘中 vs 盘后 / 非交易日 / 休市 / 首日 / 兜底态生效中)③**时序**(先来后到 / 重复触发 / 幂等 / 乱序 / 跨日翻滚)④**上下游依赖**(源失败 → 备源顶上后,展示位读的是死字段还是新值)⑤**极端值**(全空 / 全满 / 巨大 / 负值)⑥**回退路径**(降级 / 兜底 / 关开关 / 逃生门)⑦**并发与重入**(多进程 / 多轮 / 锁争用)
- **每条维度必须给判定**:「**测**」→ 写用例;「**不测**」→ 写明理由(如"已被机检覆盖")。**漏维度(清单没列到)= 验收不过** —— 这与"测不测"是两回事
- **清单来源须可追溯**:每维标注来自**哪个需求点 / 改动点**(举一反三同精神:同模式 / 同数据源 / 同组件**还被谁用**),便于复核"是不是真推导过"而非凭印象列
- **验收口径**:自验须含「**边界维度清单(逐维标注来源:需求点 / 改动点)+ 逐维「测 / 不测」判定与理由**」,外加 §5.4 原有的「安全底线清单 + 主路径覆盖 + 被省冗余测试说明」。**清单缺维度 = FAIL;列了维度但没写判定 = FAIL;深度不足不算 FAIL**(深度归 §5.4,关键点即可)
- **两条配套硬约束**:① **测试必须 CI 环境跑得动** —— 禁写死「本机有 / 无某命令」这类环境判断(那会造成"本机绿、CI 红"的假绿);依赖面要显式声明(**本机自测绿 ≠ CI 绿**)。② **边界清单要接受独立复核** —— reviewer 会**自己再推一份**清单与你的**对账**,**差集非空必须报主控**;所以清单来源要可追溯,别写"大概这几条"
- **与回测穷举的关系**:回测穷举管**回测 / 数据挖掘**的维度;本节管**测试用例设计**的维度。同为"维度穷举、不省不漏",落点不同

### 5.4 懒但安全 + 最小充分测试边界

> 蒸馏自「懒但安全」边界:该验的必须验,但不为测而测。

**核心一句话:测试该验的必须验(安全 / 输入 / 数据丢失兜底绝不为省事简化),但避免「冗余 / 过度测试」——给「最小充分测试」一个明确定义:覆盖主路径 + 关键边界即可,不追求每行全覆盖。**
> ⚠️ **与 §5.3.1 的界**:本节只管「**深度**」;**边界维度要「想全」是 §5.3.1 的硬要求**(维度漏列 = FAIL),「最小充分」**不豁免**它 —— 即「**维度穷举 × 深度最小充分**」两者正交。别拿本节当"边界可以少想几个"的挡箭牌。

- **绝不简化的「安全底线」**:输入验证(空 / 缺 key / null / 非法值)/ 安全检查(鉴权 / 敏感字段不硬编码,凭据从环境变量读)/ 数据丢失处理(数据产物缺失 / 滞后 / 空 key 超标必须 FAIL,绝不静默吞缺数据)/ 资损类路径(评分 / 信号 / 资金口径 / 上传链路 / 通知)必测。这些是"懒"的禁区——懒指的是不堆多余的,不是省这些底线
- **避免「冗余 / 过度测试」**:不为凑行覆盖率给琐碎处补检查;不重复测已被机检 / 部署前置校验覆盖的项;不因"可能有用"预写一堆当前无使用者的测试桩
- **「最小充分测试」定义**:覆盖主路径(正常能跑通 + 关键业务语义值对)+ 关键边界(空 / 缺 / 超阈值 / 非交易日等最易错点)即算充分,不要求每行 / 每分支全覆盖
- **验收口径**:测试任务自验须含「安全底线清单(逐项验)+ 主路径与关键边界覆盖清单 + 被省掉的冗余测试项说明(为何不测)」;审查方查安全底线没被"懒"省略(该验的漏验 = FAIL)、冗余测试压掉。**⚠️ §5.3.1 的「边界维度清单」不在本节"可省"范围内** —— 维度是**覆盖面(必须想全)**,本节省的只是**深度**

## 6. 测试专属教训蒸馏(通用)

> 具体条目 + 根因 + 反例见项目的避坑库(`docs/lessons-index.md` 索引 + `docs/pitfalls/` 正文)。下列为本角色高频红线:

- **curl 带认证头排查禁用 -v / -i**:会打印请求头泄漏 token;凭据从环境变量读,不硬编码、不打印
- **数据产物改动后必跑完整性校验 + 定期审计线上存储一致性**:防"该有的数据不在"静默上线
- **校验警惕「报告 ↔ 代码」互证闭环**:报告与实现可能同源带 bug,两者一致 ≠ 正确;机检设计须含独立于被校验双方的第三方锚点(界面文案 / 产品文档 / 拍板记录);业务守恒断言不能只靠键集比对
- **退出码 0 不可信**:包全量的异常捕获 + 最后退出 0 = 监控盲区,语法错 / 中途崩全被吞;审监控 / 校验脚本重点看异常后是否上抛 / 非零退出 / 告警
