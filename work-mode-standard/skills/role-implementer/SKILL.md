- [ ] **算法公示**:改算法 / 数值,必 grep 前端公示文案(算法 / 评分 / 权重 / 匹配 / 分位等说明)全部出现处同步改,不只实施点

## 1. 单版前端铁律

- 前端源码只维护**单一源头**目录(不双写两份);服务挂载该目录到根路径
- **worktree agent 不自行 bump 版本串**:改前端源码后本地验证产物可跑构建脚本,但**不 commit 版本串改动**——版本串统一由主控合并入口 bump(唯一权威入口)
- 产物成对(每份源 → `.min.js` / `.min.css`):版本串格式由项目定,每次 bump 强制换新串
- **缓存版本常量与版本串同源**:改前端主 JS 后必须同步缓存版本常量(防旧缓存致用户拿不到新代码);由统一合并入口一并 bump,**agent 不自行 bump**
- **min 版验证用字符串 / class 名非变量名**:压缩器会重命名局部变量,grep 验上线用 class 名 / 中文字符串
- **产物输出路径同步**:构建 / 导出脚本的 cwd 不同会写到不同目录,与部署脚本读取目录务必一致,否则推旧版(导出后确认同步)

## 1.1 前端部署 / 缓存 / 服务工作线程(Service Worker)更新防撕裂

**触发词**:发版 / 改前端主 JS·样式·入口 HTML / bump 版本串 / 站点白屏 / 点更新新版白屏 / 多站版本混乱 / 缓存滞留。
**核心一句话:版本串必须随内容强制刷新(杜绝指纹断链),Service Worker 更新接管必须壳芯配套 + 失败回退,部署后必须验「内容哈希 == 入口引用版本串」。**
- **① 版本串用「发布序号(日期 + 批次)」而非纯内容哈希**:每次部署强制换新串,内容相同也换,杜绝"指纹断链、旧缓存不清、不触发更新"死角
- **② 改前端源码必同 commit bump 版本串 + 同 commit 重建产物**:改前端源 → 必须同 commit 跑构建 + bump + push + 验线上入口引用 `?v=` 与实际文件内容哈希一致;禁止"源码改了版本串 / 产物没重建没跟着变"。**禁 `reset --soft` 对齐分支**(只移 HEAD 不动工作区,会留旧版脏文件被部署安全网读旧源生成旧产物覆盖正确版);对齐用 `checkout <commit> -- <文件>`。部署只在主分支跑
- **③ 更新接管需「壳与芯配套 + 失败回退」**:清缓存 / 接管前先确认应用壳(主 JS / 入口)已预缓存就绪;未就绪不接管不强推,失败回退旧版 / 旧缓存,绝不全白
- **④ 数据全站同步覆盖核心产物**:盘后核心产物必须随三步同步到备站或可靠兜底主站,备站不得缺核心文件
- **⑤ 部署后自动校验「内容哈希 == 入口版本串」**:部署链加校验(每文件算内容哈希前 N 位与入口引用比对),不一致即阻断上线,防孤儿快照
- **验收口径**:上线 / 发版任务自验含「版本串每次更换确认 + 改码同 commit bump + 部署后哈希 == 引用校验 PASS + 备站核心数据在位」;reviewer 查这 4 项(细则见 role-reviewer skill §5.2),漏 = 验收不过

## 2. 算法改动同步公示

- **核心一句话:改算法逻辑必须同步改前端算法公示文案**。公示是用户理解算法的依据,算法改了公示不改 = 用户看老规则误导,修复成本高
- **触发**:任何改评分 / 权重 / 分段函数 / 匹配规则 / 阈值等算法逻辑的改动,必须 grep 前端算法公示文案(算法名 / 指标说明 / TE / R² / IR / 权重 / 百分位 / 匹配方式等说明文字)同步更新
- **验收口径**:算法改动自验须含「grep 确认公示文案已更新为新规则」,reviewer 查公示同步;算法改了公示没改 = 验收不通过
- **强化款(已复发 2 次)**:条款存在但 fresh context agent 仍不主动读。**主控 prompt 每次都要显式列 grep 动作 + 文件名**,不只引用"见本节";修一个数值要 grep 全站同一数值所有出现处同步改(同数据一致性铁律),不只实施点

## 3. 上线操作细节

- **push 主分支统一入口**:agent 只 push **feat 分支**,**禁止 agent 直接 push 主分支**。合并 + push 主分支一律由主控走统一入口脚本(内含 base 新鲜校验 + 合并 + 统一构建 / bump + 校验 + push + **push 后自动自查 CI 结论**)
- **push 后 CI 自查**:主分支合并成功后自动拉最新 CI 运行结论,按 commit 匹配本次 run:成功打印一行;**失败醒目告警(编号 / 链接 / 失败作业名)+ 非零退出**(主控立即派修);拿不到结论则告警 + 提示手动复核。**本机自测绿 ≠ CI 绿**(CI 环境差异致假绿)
- **完成报告必带「base commit + 版本串前后值」**:写明开工基于的 base commit + 改动前后版本串(改前端源码时记录改动前值)
- **开工强制 rebase 主分支 + base 新鲜校验**:worktree / 分支开工前先 `git fetch && git rebase origin/main`;提交前用 `git merge-base --is-ancestor origin/main HEAD` 校验 base 新鲜(落后先 rebase 再提交,防静默覆盖最近改动)
- **续跑同一任务必须延续原 feat 分支,不新开分支 cherry-pick**:先查原分支是否被残留 worktree 占用(被已完成的残留占用 → 报主控释放后可 checkout 继续,不擅自 cherry-pick);`git branch --show-current` 确认落在原分支。验收含「分支延续检查」
- **commit + push feat**:不推 = 白干;commit message 末尾加 `Co-Authored-By:` 行
- **不提交本地数据 / DB / 密钥目录**(按项目 `.gitignore`);**数据产物目录是正常上线渠道**——后端新增字段 / 种类后必须跑项目的部署脚本推数据上线,否则前端读旧数据
- **不 force**:force-with-lease / force push 是最后手段;non-fast-forward 优先 `git fetch + rebase origin/main + 重试 push`;rebase 失败 abort 等人工;不得擅自强推,尤其主分支
- **提交前核对**:推理"X 文件在某 commit 里"前先 `git show --stat <commit>` / `git log -- <file>` 确认,不靠推理
- **「功能 done」三查清单**:①主分支链含 commit(`git log origin/main` 含 hash)②数据层生效(线上 curl 数据产物字段有值 / 无旧字段残留)③**前端展示层上线(线上 curl 前端产物含新功能 class / 中文字符串)**。只验①②不验③ = 代码写了但从未上线
- **盘中(交易时段)不跑全量导出 + 部署**(全量导出 + 部署限收盘后;休市例外);盘中增量类走对象存储不推主分支
- **应急止血也守时点,不豁免**:线上坏了要"马上重出 / 重跑"**不是**豁免理由——先核当前时点 + 并发定时任务,**挪窗口外 > 报主控 / 用户拍板 > 直接跑**;确需盘中执行须拿到明确点头 + 事后留痕(起止 / 重叠对象与时长 / 影响证据);做治本改动须把时点约束**内建进设计**(窗口门 + 硬超时上限 + 避开既有任务时点)

## 3.1 存储架构准则(按数据类别,不按单文件大小)

- **是结构决策,不按单文件大小临时判断**:新数据类别从第一天就走对象存储架构(上传清单 + 前端 fallback),不等变大才补
- **走对象存储的类别(满足任一)**:①全量品种多 ②有大范围历史序列(单文件 > 阈值)③类别整体大
- **走 CDN 的小文件**:单文件 < 阈值且类别总量小的状态 / 监控小文件
- **上传命令按前缀建**(先按类别建独立命令,不依赖大小阈值)+ 一个大小阈值兜底;**前端 fallback**:大范围历史序列走对象存储 `data/` 前缀,其他类别用硬编码端点 URL
- **本地留引用**:上传后不删本地产物目录;大文件可 `.gitignore` 移出 git
- **新数据类别上线 checklist(同 §22 三步)**:写产物目录的生成器必须同时接 ①对象存储上传(清单或自动)②产物目录同步(同步脚本或部署脚本);「只写目录 + 手动上传不跑部署脚本」的独立生成器会留旧版直到下次部署
- **判断 checklist**:①该类别是否有独立上传命令?②前端 fetch 是否走对象存储 URL 或 fallback?③大小阈值兜底是否排除该前缀(防双副本)?三条齐全 = 架构合规
- **手动上传 / 导出必须显式指定正确的源根**:上传脚本源目录缺省可能回退到错误路径,手动命令漏指定环境变量会抓旧库整体覆盖线上 → 线上退回旧数据;**按项目专项写明必需的环境变量前缀**;生成脚本 / 定时链路须显式指定,并设计哨兵守卫(检测到"错误源 + 敏感时段"即拒传)

## 4. 生产稳定时点

- **任务冲突检查不应由用户提醒才做**:每次派任务 / 设定时任务 / 推主分支前**必须主动查定时任务清单**(按项目专项的命令),列当日盘后任务时点确认不撞,主动给用户时点建议
- **核心冲突类型**:①推主分支 vs 另一推主分支 = 互相覆盖事故 ②写同一 DB(评分 / 采集)vs 同 DB 任务 = DB 锁 / 进度撞 ③采集脚本并发 = 限流空转
- **盘后定时任务时点不推主分支不写关键 DB**;安全窗口内无推主分支 / 评分 / 采集任务(具体时点见项目专项)
- **agent 只 push feat 分支,不碰主分支**:撞车由主控统一合并入口检查拦截,agent 无需也不得自行判断主分支时点
- 盘中 push 代码不避增量类任务(走对象存储);**仍避盘后更新部署推主分支竞争**;盘中全量导出 + 部署仍禁

## 4.1 上线前数据就绪自检

- **触发**:任何功能 / 数据 / 算法上生产前;出现"先上残缺版,数据以后补齐"念头;回测 / 快照 / 覆盖不全想"先上线等后台追"
- **上线前必填数据就绪清单(缺一 = 不上线)**:①**展示全集无残缺**(前端展示 N 笔,数据源必须能判定 N 笔,逐项核对无降级展示)②**覆盖范围核对 PASS**(快照 / 回测 / 覆盖范围 vs 展示范围逐项比对全部命中)③**无降级展示项**(上线前消灭降级项,不靠上线后"自动消失")④**同构对账互证**(数据含回测 / 复现数字时,经同构对账机检确认与页面一致)
- **宁等不等错**:数据没就绪 = 不上线,先补齐再发;时点锁(§4)+ 就绪锁(本节)两把锁都开才上线
- **发现"先上残缺版"念头 = 停**:上报主控停住,不自作主张

## 5. 修 bug 三铁律操作化

- ①**修完整**:修一个 bug 前先全面调研同类错误面(用户报 1 个,先 grep 全量数据依赖 + 多处状态码列全同类异常),根因修复不只表面症状
- ②**自测完成**:修复后必须自己全面测试(用户报的模块 + 同根因其他模块 + 跨展示位一致性),自验列测试清单,不"草率说修好了"
- ③**排查同类**:修完自查"是否还有其他同类错误"(同文件类型 / 同 fallback 链路 / 同上传通道的其他文件)
- **验收口径**:自验须含「同类错误面清单(与用户报的同根因的所有模块)+ 逐项自测结果」,reviewer 查同类覆盖,漏 = 验收不过
- 防重犯:①修 bug 前必列异常面清单 ②修复后自测清单全覆盖 ③根因层面修,不逐文件打补丁

## 6. 举一反三(需求理解 / 做方案)

- **需求理解 / 设计 / 实施方案时主动举一反三**:用户点名做 A,方案要主动覆盖 A 的相关场景 / 位置 / 展示位(同类功能在同一模式处、同一数据源 / 组件还被谁用、N 个展示位一致性),不只做点名的那一处
- **验收口径**:自验须含「同模式 / 同数据源 / 同组件还被谁用 + 相关展示位清单 + 逐项覆盖结果」;reviewer 查举一反三覆盖,漏 = 验收不过
- 与修 bug 三铁律③同源,一为正(修 bug 排查已坏同类)一为前(做方案覆盖未做同类)

## 6.5 写码前 7 级阶梯 + 根因修复 + 少写抽象

**核心一句话:写码 / 改码前自问「能否不写 / 少写」,先理解问题再爬阶梯;修 bug 修根因不修症状;删除优先于添加。**

- **7 级阶梯(写任何代码 / 加任何逻辑前,自上而下停在第 1 个成立的层,不跳过前面的层)**:①**需要存在吗** → 不需要 = 跳过(先复述需求确认要不要)②**库里已有吗** → 复用现有函数 / 数据产物 / 展示位,不重写 ③**标准库有吗** → 用标准库,不手搓 ④**原生平台能力有吗** → 用平台原生能力 ⑤**已装依赖有吗** → 用已装依赖,不新装 ⑥**一行能搞定吗** → 一行搞定 ⑦**以上都不行才写最小可用代码**:只写满足当前需求的最小实现,不留"以后可能用到"的扩展位
- **先理解问题再爬阶梯**:不跳过"读现有代码 / 读需求"直接开写;看不懂就写易在第 2 层误判"库里没有"而重写
- **根因修复**:改前 grep 每个调用方确认影响面,**一个共享函数里的守卫 < 每个调用方各写一个守卫**(能在根因点修就不在 N 个调用处打补丁);修完按 §5 列同类错误面清单 + 自测覆盖
- **少写抽象**:不写单实现的接口 / 单产品的工厂 / 永不变化的配置;抽象只在出现第二个真实使用者时才提取。**删除优先于添加**——先想"能不能删掉 / 简化现有"而非"再加一层"
- **验收口径**:实施任务自验须含「7 级阶梯自问(第几层成立 / 为何不再低层)+ 复用点清单 + 无多余抽象确认」;修 bug 任务须含「根因修复点(单点守卫 vs 逐调用方)+ 每个调用方影响面已 grep」

## 7. 实施专属教训蒸馏(通用)

> 具体条目 + 根因 + 反例见项目避坑库(`docs/lessons-index.md` + `docs/pitfalls/`)。本角色相关域:c 测试自测验证 / d git 分支合并 / e 数据产物一致性 / g 派单任务调度 / i 前端部署缓存 / l 数据源外部依赖。下列为本角色高频红线:

- **"全量 / 全部"不擅自 exclude / 清理**:用户说全量先确认,不擅自缩范围
- **切分支前查并发任务与后台 agent**:防撞车;**方案先充分调研再实施**,不边试边改
- **归属 / 分类 / 阈值前复述口径确认**,不靠语义猜测;上游语义声明一律视为待验证假设而非事实
- **改样式 / 灯体系遍历所有 return / 分支**,grep 全部同类拦截点,不只看用户报的那处
- **理解需求不擅自加未要求的改动**,不确定时复述需求确认
- **新类别上线链路三步完整**(生成 → 上传 → 同步),缺一留旧版;**前端重算对齐后端**(取一个数据文件逐字段对比后端输出,不只对比总计)
- **改任何源码后自验必含「全量测试套件」**(不止直接相关用例):测试目录里可能存在**源码形状守卫**(grep 源文件里的字面量以锁定形状),源文件形状一变守卫即红;本机只跑「相关用例绿」≠ 全绿——同理,**本机绿 ≠ CI 绿**
- **动态 / 状态类功能·数据供给链路四件自检**:生成脚本 → 定时挂载(真实存在于生产机)→ 机检校验 → 过期告警,缺一 = 功能未完成;取静态快照 / 手动生成等降级形态**必须作为方向性分叉上报主控转用户拍板**
- **清理 / 杀进程必须按端口精确定位**,禁裸 `pkill -f <宽匹配>`(会误杀同族生产进程)

## 8. 团队协作:先查"已落档未开发功能"+ 同模块冲突预防

- **核心一句话**:多个子 agent 是一个团队,不能只顾自己的活。**开工前先查项目的「已落档未开发功能索引」**,凡"方案已出但未开发"的功能与本任务同模块 / 同数据源 / 同组件 / 同展示位的,必须提前考虑进去
- **预留位置**:实施时主动 scan 索引同模块项,写代码时**预留好位置**(接口 / 数据结构 / 配置位 / 展示位 / 常量表),或留 TODO / 注释说明"待某功能接入",不自顾自封死;与索引项相关但无法预留的,报告里显式提出
- **同模块冲突预防(后覆盖前禁止)**:两个任务改同一模块不得各自闷头改后让"后完成者覆盖先完成者"。①开工前查同模块占用(另有任务在改 → 第一时间上报主控协调 = 排队 / 约定 / 分区域)②不默默并行、不闷头做到碰壁才找用户 ③独立 commit + 分区,合并前核对无覆盖
- **待办-现状对账(防脱节)**:开做某待办前先核对当前代码 / 数据现状与方案假设是否一致,不一致先更新方案再实施,不硬套旧方案
- **验收口径**:自验须含「scan 索引本模块项 + 已预留位置清单(或说明为何不相关)+ 同模块占用检查(冲突已上报协调)+ 待办对账」;reviewer 查预留覆盖 + 冲突预防,漏 = 验收不过
- 与 §6 举一反三互补:§6 查"已上线功能"的同类位,本节查"已落档未开发功能"的衔接位 + 冲突预防 + 待办对账

## 9. token 优化行为层(实施专属)

> 与共享核心 §5.5 互补,本节列实施专属子集。
- **不贴回已写文件**:改完文件报结论时**不贴回文件全文 / 大段代码**,只给关键 diff 点 + 最终状态。省输出 30~60%
- **命令静默化**:`git status --porcelain`、`git log --oneline`、测试带 `-q`、日志 tail / 截断、大 JSON 输出落盘再 grep 而非整段打印。curl 验上线仍按 §3 三查清单执行,只裁剪输出不裁剪校验动作
- **@文件直接引用代替 Read**:定位 / 回报用 `@文件路径:函数 / 行号` 直接引用,能定位到行就不整文件 Read;查大文件定点 grep 看片段
- **简洁输出·结论优先**:完成报告 / 每步汇报**先给结论**,跳过开场白和结尾复述。**但结论后必须带证据点**——改了哪些文件(路径 / 行号)、自测逐项结果、口径标注(非基准须声明)三点是验收命门,简洁砍废话不砍证据
