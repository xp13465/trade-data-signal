## A 多 agent 协作与角色纪律(14 条 → `a-agent-collab.md`)

- 派单返回不等于启动成功 — 分派成功返回不代表执行者真起来了,必须看转录/进度是否在增长。
- 汇报在跑数量前逐条核对 — 汇报"在跑 N 个"前逐条核对完成通知,不凭印象累积计数。
- 判执行者死活看转录是否增长 — 进程在≠还活着;判活看转录是否持续增长,不靠进程名/进程号。
- 异步通知会丢,必须配轮询兜底 — 异步通知架构上不可靠,必须有轮询/巡检兜底才安全。
- 调度者不亲手实施与验证 — 角色分离:调度者只分派+验收,不亲手实施,避免自出自证。
- 小修复不套重流程 — 低风险小改直接做+自检;重流程固定成本高,套了反而浪费。
- 中途改口径就停旧派新 — 需求口径变了就停掉旧执行者、用新规格重派,不让旧规格继续。
- 用户接管先停在场执行者 — 用户一接管,先停掉同任务的机器执行者,避免双写撞车。
- 并发改同一仓库必须工作树隔离 — 工作目录与分支是全局的,并发改必须各自隔离工作树。
- 续跑同一任务必须延续原分支 — 同一任务改动永远落同一分支,不新开分支挑拣造成漂移。
- 派单必须要求每步写进度文件 — 长任务派单必须约定进度文件路径,否则卡死无从发现。
- 执行者自等定时器不可靠 — 执行者会话结束其定时器即失效,时点动作由持久调度方兜底。
- 破坏版本控制目录的操作会被拦死 — 这类操作会被工具层静默拦死,不派执行者做这类测试。
- 并行收益要量化 — 并行有协调成本,先量化再上,不强依赖"人多快"。

## B 通知与告警(9 条 → `b-alert-notify.md`)

- 排查告警必须事件驱动全量扫描 — 按时间找新鲜日志逐个看;关键词 grep 只是补充,不作主手段。
- 单一登记点沉默不等于没有告警 — 一条告警链可能有多个出口,单一登记点沉默≠全局安静。
- 能外发通知的脚本自测前先打桩 — 会真发邮件/群消息的脚本,自测前先打桩并证明拦截生效。
- 降噪必须保留真故障判别维度 — 降噪的验收核心=仍能区分真故障与良性缺失,且用反例实测。
- 告警去重与恢复通知 — 同故障持续期只发一次,恢复时补发解除,防轰炸、防不知已恢复。
- 监控脚本退出码为0不可信 — 退出码 0 可能吞掉子步骤失败,要有独立成功判据+时效阈值。
- 严重级告警统一镜像登记 — 最高级别告警必须统一镜像到权威位置,禁止旁路出口造成排查盲区。
- 定时与补发必须带业务日历判断 — 定时与补发都要先判业务日历,非业务日不触发、不补发。
- 重复跑是兜底不是冗余 — 多时点是兜底;用"任务是否幂等"决定复写还是跳过。

## C 测试 · 自测 · 验证(16 条 → `c-test-verification.md`)

- 断言输入必须取真实生产实测样本 — 人工构造样本会补上不存在的字段,造成"假样本养绿"。
- 新增守卫机制上线前必须生产实跑 — 新增守卫/可见性机制须在生产真触发一次,防长期空转。
- 自验窗口必须达到机制周期两倍 — 观察窗口少于机制周期的两倍,结论必然错。
- 复刻逻辑的脚本必须同构对账 — 复刻脚本是第二份实现,会静默漂移;发布前必须逐位对账。
- 复用旧自验脚本前先核对它的判定逻辑 — "验证的验证":旧脚本自己可能算错,先核它的判据。
- 自验口径必须产出用户同一视角的证据 — 自验要产出用户看到的那个视角的证据,否则等于没修。
- 生产事实必须用权威源并标注取自哪侧 — 本地副本会陈旧;生产事实必须用权威源并标注来源。
- 性能基准必须用生产真实清单 — 性能强依赖样本;基准必须用生产真实清单,否则数字不可比。
- 本地通过不等于集成环境通过 — 本地绿≠集成绿;推送后必须主动看集成结论,失败立即修。
- 守卫闸门设计的四条 — 闸门四问:位置/在生产目录验证/变更集判定/挂载点真在跑。
- 生产审查探针一律只读并用正白名单门控 — 审查探针只读,门控用正白名单,禁用可绕过的条件。
- 事故后必须独立取证 — 不采信当事方自述;证据不足就写"无法判定",不硬编结论。
- 语义类改动验收必须有第三方锚点 — 实现↔报告互证会一起错;必须有第三方锚点(文案/文档)。
- 改或删函数必须同步调用方 — 删定义前先列全部调用方逐一同步,漏改会静默失败。
- 新功能上线必须跑回归 — 新功能与老功能共享资源,上线必跑老功能回归+数据校验。
- 判机制影响面必须读代码确认调用链 — 作用范围由调用链决定,不由命名/直觉决定。

## D git · 分支 · 合并 · 发布(12 条 → `d-git-branch-merge.md`)

- 冲突覆盖与版本倒退绝不静默 — 任何冲突/覆盖/倒退绝不静默吞掉,宁可卡住上报。
- 判分支独有内容用内容哈希逐位比 — 三点 diff 会报假新增;判独有用内容哈希逐位比。
- 拿版本控制输出当清单要防中文名漏扫 — 输出会转义特殊名;当清单解析要关转义或用空终止。
- 精准暂存,禁用全量暂存 — 全量暂存会误带大文件;精准指定,提交前先看状态。
- 清理引用记录前先检查暂存区 — reflog expire/gc 会连带清暂存;清理前先查暂存并保全。
- 改已推送提交用同串推新引用名 — 改已推提交,把同串推到新引用名即可,零 force。
- 合文档分支前先核它只含文档 — 合文档分支前核改动面只含文档,防夹带代码一起上线。
- 合并前先取最新再核实本地引用 — 本地引用会过期;合并前先 fetch 并核实新鲜,防静默丢提交。
- 合并中途失败会留半完成态 — 合并失败会留半完成态;汇报必须说清每个改动落在哪个分支/提交。
- 发版本先全量核对版本链 — 发版本先全量核对版本链;发现历史疏漏先上报再补,不默默补。
- 报告类交付要四件套齐备 — 报告=本体+生成脚本+复现段+提交;提交前核本体真的被跟踪。
- 提交时间戳不等于任务触发时点 — 判断任务是否跑过看运行日志,不看提交时间戳。

## E 数据产物与一致性(10 条 → `e-data-artifact-consistency.md`)

- 多个展示位的数据必须统一 — 一个数据在 N 处展示必须统一;策略只决定何时更新/如何排序。
- 数据产物必须原子写 — 先写临时文件再改名,防进程被杀留半截数据。
- 生成路径不等于消费路径 — 生成位置≠消费位置;产物改动必须列全依赖逐个确认三步。
- 部分缓存当全量返回是反模式 — 部分缓存当全量返回会系统性漏算,必须能区分部分与全量。
- 同源字段先确认语义 — 同源字段语义可能不同(静态/动态、快照/增量),先确认再使用。
- 依赖上游已生成文件会静默全空 — 上游文件缺失时会静默返回空,必须有存在性校验。
- 状态型功能的供给要四件套齐备 — 动态功能供给=生成→定时→机检→过期告警,缺一不算完成。
- 口径基准切换前先做影响面审计 — 口径切换前按"会反转/数值变/能自愈"三类做影响面审计。
- 状态判断用稳定标识而非对象引用 — 对象引用会失效;状态判断用稳定 key 字符串。
- 计数与列表可以用不同基线 — 计数宽松、列表完整,两者可分开设计,不强求相等。

## F 成本与 token(8 条 → `f-cost-token.md`)

- token 优化的六条零成本行为 — 答案优先/命令静默/汇报只回结论/引用代替读/小任务不套壳/失败回退。
- 遇慢或贵先查模型参数层 — 遇慢/贵第一问模型参数层(思考开关/档位/缓存),再问任务层。
- 提高缓存命中率的做法 — 续跑不新开会话、派单只给差异、批量并行启动;换模型=缓存全失效。
- 清空上下文省成本必须以完整落档为前提 — 清空/压缩上下文前必须先把关键状态完整落档。
- 重复调研与试错返工是最大浪费 — 重复调研与试错返工最贵;"不可改善"结论要一次查到位。
- 大文件与重复内容走外部通道 — 机械的大文件/重复内容走脚本层=零 token,不经模型回合。
- 模型计费异常要主动审计 — 主动审计计费,查白名单外/绕道调用造成的泄漏。
- 上下文按需分层加载 — 入口只放核心,细节按需读,不让每轮重发全历史。

## G 派单 · 任务治理 · 调度时序(8 条 → `g-dispatch-task-scheduling.md`)

- 派单必须带定位锚点 — 派单必带"文件+行号/关键符号"锚点,不让执行者从第一行搜大文件。
- 派单前先核实基准与默认值的当前真值 — 派单前核实基准/默认值的当前真值,不沿用旧报告。
- 索引清单会漂移,按它办事前先核实物 — 索引会漂移(完成未销号);按它办事前先核实物。
- 任务状态实时更新且收尾要三块总结 — 状态实时更新;收尾给三块总结(改了什么/效果/下一步)。
- 任务治理走四态流转与单一事实源 — 任务四态流转+单一事实源+机检兜底,防多源状态矛盾。
- 定时任务要管时点冲突 — 派任务/设定时/推代码前先查定时清单,避开彼此窗口。
- 应急止血同样要守时点窗口 — 紧急不豁免时点约束;能挪窗口外就挪,确需例外先拍板+留痕。
- 看门狗外层超时必须大于内层 — 外层超时必须大于内层,否则误伤内层重试,表现为超时无重试。

## H 调研 · 结论纪律 · 防误判(16 条 → `h-research-anti-misjudge.md`)

- 调研先对准用户实际看到的位置 — 先对准用户实际看到的界面位置,再往下查生成层。
- 下没铺到或没数据的结论前先验数据产物层 — 下这类结论前先验数据产物层(新旧字段值对照)。
- 无或不可改善类结论必须换方法再下 — 换方法/换数据源/多维度验证后再下,并列已验证的方法。
- 归属分类口径决策前先复述口径 — 分类/归属/口径决策前先复述口径让人确认,不靠语义猜。
- 指定计算口径前先验算典型值合理性 — 定口径前先拿典型值/边界值验算,反常大数立即警觉。
- 外部系统的未知行为先上网查社区 — 外部/厂商/网关/API 未知行为先查社区+官方文档,不闭门实验。
- 凭记忆断定前先验证 — 记忆/笔记可能过时;凭它断定前先验证当前实际状态。
- 判断功能是否生效看运行证据 — 看运行证据(日志/指纹/输出),不凭配置推断"已生效"。
- 验收值类结论搜不到先怀疑被封装 — 搜字面值无果先怀疑被封装成常量/变量/配置键,改搜符号名。
- 报不一致之前先做归因三查 — 先归因:谁在生效/是否历史遗留/是否刻意设计,别误报漂移。
- 需求理解先复述确认不擅自扩展 — 先复述确认;不擅自扩展;叫停时复述删到什么粒度;"全量"不裁剪。
- 期望值与断言值先核实来源 — 期望值/断言值先核实来源,不盲信任务描述里的数字。
- 用户的使用记忆优先于你的推断 — 用户使用记忆与推断冲突时,先通读实现,用户记忆优先。
- 日期星期必须先核对日历 — 日期/星期/业务日先核对日历,强时序系统里日期错会全错。
- 统计口径不等于实施口径 — 调研统计口径不能直接当实施规格抄,派单要钉"与现状一致"。
- 评估开源项目必须跨角色穷举 — 评估开源/方法论要对每个使用角色逐个问增量,穷举完再下结论。

## I 前端 · 部署 · 缓存(11 条 → `i-frontend-deploy-cache.md`)

- 前端资源版本串必须与内容强绑定 — 版本串随内容强制刷新;部署后校验"线上哈希==页面引用串"。
- 离线缓存更新必须壳芯配套且可回退 — 离线缓存更新要壳芯配套+失败回退,改资源同步 bump 版本。
- 构建产物必须从版本库读取源 — 构建从版本库 HEAD 读源,不读脏工作区,防产物与提交不一致。
- 大文件下载校验先比字节数再比哈希 — 大文件校验先比大小再比哈希,防慢链路截断造成的误报。
- 验证线上资源要确认真实路径与访问条件 — 验证前先确认真实路径/请求头/重定向,防假阴性。
- 功能完成的"三查" — "完成"三查:代码进主线+数据层生效+前端展示层上线,缺一不可。
- 压缩产物验证用字符串而非变量名 — 压缩产物验证用类名/中文串,不用会被混淆的变量名。
- 界面问题多次修不好就该推翻假设 — 界面问题三次修不好=假设全错,停方向从零验证,换独立验证者。
- UI 改造必须钉落点并做真实浏览器验证 — 派 UI 改造钉落点+旧控件替代清单+真浏览器实操验证。
- 新功能先隔离验证再融合 — 新功能先隔离验证再融合,防污染主线。
- 算法或数值改动必须同步全部对外说明 — 改算法/数值必须 grep 全部对外说明同步改,不只 tooltip。

## J 删除与备份安全(6 条 → `j-delete-backup-safety.md`)

- 删除前必备份且实测可恢复 — 删除前必备份:先备份后删、实测可恢复、验过即删/验不过停、写明恢复路径。
- 有备份不等于可以删 — 有备份≠可以删;既有保留决定优先,别把"保险"当垃圾清。
- 删除或重构前先列删除与保留清单 — 删/重构前先看原实现,列删除清单+保留清单逐项确认。
- 杀进程前先核实进程属主链 — 杀进程前核实属主链,按端口精确定位,禁裸按名字全量匹配。
- 会翻滚的备份等于没有备份 — 会翻滚/无全量的备份形同虚设,必须验证"能重建完整快照"。
- 覆盖写入前先加备份护栏 — 覆盖写入前先加备份护栏;防误操作要多层防线(闸门/白名单/审计)。

## K 生产运维 · 稳定性 · 平台环境(12 条 → `k-prod-ops-stability.md`)

- 生产稳定性是最高优先级 — 上生产前先查定时任务清单与时点窗口,避撞是第一位。
- 优化落地后要设定期巡检 — 优化落地后设定期巡检(指标+判定标准+止损回滚),防负向漂移。
- 做"该有的数据在不在"的完整性校验 — 定义"该有的数据清单"逐项核对,防静默缺失。
- 开发与生产环境分离 — 开发与生产分离;判任务停摆要去真正跑任务的机器查。
- 未排定上线的功能必须与生产隔离 — 未排定上线的功能必须与生产隔离,不写生产数据。
- 慢任务排查要逐段计时 — 慢任务逐段计时找真因(锁/积压/资源),不归咎"网络慢"。
- 超时设计要按停滞判断并留梯度 — 超时按停滞(不按总耗时)判;留梯度;重试风暴是反模式。
- 环境临时授权不等于普遍约束 — 临时授权/限制≠长期规范,别把某轮约束写死成规则。
- 双树或符号链接目录先追真实路径 — 核验前先 readlink 追真实路径,否则核验的是镜像。
- 本机工具坑要记录 — 把本机工具坑记成清单(解释器版本/图像工具/环境库),下次直接查。
- 被定时任务重写的受跟踪文件会挡住同步 — 被定时重写的受跟踪文件会挡同步;处置赶在下一次写入前。
- 对象存储生命周期按对象自身年龄算 — 生命周期按对象自身年龄算,存量对象同样受管。

## L 数据源与外部依赖(7 条 → `l-datasource-external.md`)

- 数据源可靠性要压测且多源互备 — 数据源要压测找边界;多源互备,fallback 不走同源。
- 换数据源时按字段值过滤会静默失效 — 换源时"按字段值过滤"必静默失效;判据锚稳定标识。
- 外部接口报错别卡死重试 — 400/不支持类错误别卡死重试,立即换方案或暂存。
- 批量传输与调度有业界权威参照 — 批量传输/调度有业界范式:超时按停滞、重试风暴是反模式。
- DNS 劫持类问题用固定 IP 根治 — 先分清 DNS 层还是连接层;DNS 劫持用固定 IP 根治。
- 对外发布内容禁内部路径与密钥 — 对外内容带对外入口,禁内部路径与密钥,发布前扫敏感信息。
- 限流冷却时间按厂商实际恢复周期定 — 限流冷却按厂商实际恢复周期定,固定大冷却会锁死凭据。

## M 回测 · 口径 · 数据科学方法论(10 条 → `m-backtest-caliber.md`)

- 回测与测试默认落在当前基准 — 回测/测试默认前提=当前基准;测非基准必须显式声明+说明原因。
- 防前视:信号只能用当时之前的数据 — 择时/状态信号在 t 只能用 t 之前的数据;分位阈值用滚动窗口。
- 名义金额口径会系统性放大收益 — "名义金额×笔数"口径会放大收益;先验边界情形是否逐位相等。
- 收益率的实操性看资金倍数 — 收益率要配"峰值占用资金/本金"倍数,倍数过大=理论不可操作。
- 回测必须用可操作的补位口径 — 回测必须用与实盘一致的可操作补位口径,删笔口径只作对照。
- 新开关注计算叠加边际贡献 — 新候选要算叠加现有配置的边际贡献;最优组合可能依场景分裂。
- 数据挖掘前先核对字段覆盖 — 多轮挖掘前先核对字段覆盖,未覆盖字段=最大机会。
- 先建能力再评分 — 先做出能力再评过拟合/稳定性,不因"怕过拟合"缩手不做。
- 参数优化走测试驱动 — 参数优化多方案+数据让用户选,不把开放问题抛回。
- 回测报告要一次给全维度 — 核心问题报告一次给全维度(基线/按年/稳定性/回撤/极端/变体/诚实标注)。

## N LLM 平台与工具链操作(8 条 → `n-llm-platform-toolchain.md`)

- 带认证头的调试命令禁用详细输出 — 带认证头的调试命令禁用详细输出,防 token/密钥泄漏。
- 接口参数报错先抓原始请求体 — 参数报错先抓原始请求体对照文档;新版本会挪参数位置。
- 切换代理不能由跑在该链路上的会话执行 — 切代理不能由跑在该链路上的会话执行,否则自己先死。
- 密钥永不进版本库 — 密钥永不进版本库,放环境/密钥服务;已提交的立即轮换。
- 平台设置不一定作用于子会话 — 平台设置作用范围有限,子会话要另写要求,别假设全局生效。
- 供应商余额类错误是服务端预检 — 402/余额类错误是服务端预检,客户端压不动,解=充值/换服务。
- 外部协作者共用仓库也要隔离 — 外部协作者共用仓库也要工作树隔离+状态字段+原子写入。
- 工具评估要走实测并落档结论 — 工具评估走实测+落档结论,注明已知坑与适用边界。

## O 沟通 · 工作方式 · 文档治理(11 条 → `o-communication-docs.md`)

- 面向用户的输出要简洁口语化 — 面向用户输出言简意赅+口语化,说人话,细节落档不刷屏。
- 要人拍板前先说清优缺点并给方案集 — 拍板前先摆优缺点(缺点优先),给 2~4 个方案+建议。
- 方案必须是可证伪的承诺 — 方案=可修正依据+可观测预期+证据用例;写不出=建议,不许当方案。
- 方案的默认准则是完整正确不偷懒 — 方案默认准则:完整正确、一步到位、不以工作量偷懒。
- 任何事默认持久化 — 任何事默认持久化:任务持久、进度落盘、状态写档,不靠会话/记忆。
- 新产物当场落档并归类 — 新产物从创建起就放合适位置+归类+索引更新;报告四件套齐。
- 已发布功能是冻结资产 — 已发布功能=冻结资产,默认只新增不改旧;动旧功能必须先确认。
- 规则文档要防膨胀 — 规则文档定期 review 防膨胀:稳定条款下沉、根文件留摘要;精简保核心+可逆。
- 知识库索引要定期做孤儿死链审计 — 知识库索引定期做孤儿/死链双向审计,结果落档。
- 复杂数值表用三档互证教学 — 复杂数值表用"白话+场景+1:1 举例"三档互证,举例数字须核实。
- 过错要归档并编锚点防重犯 — 过错归档+编锚点+防重犯条款,形成可反查经验库(本手册的元方法)。
