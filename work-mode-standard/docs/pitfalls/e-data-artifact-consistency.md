## 多个展示位的数据必须统一

- **现象**:同一个数据出现在多个展示位(多端、多页面、多缓存层),用户在各处看到的版本不一致,一处新一处旧,产生误解。
- **根因**:数据有多份副本(多文件 + 多缓存),更新时只更新了其中一部分;底层有分层(源数据/中间文件/展示文件),更新没有同步贯穿。
- **防再犯**:一旦更新,**同一数据的 N 个副本 + N 个缓存必须一起同步**(全部文件 + 全部缓存层);各类"更新频率/排序策略"只决定**何时更新、如何排序**,不改变"更新就全同步"这条;底层常量/字段清单若在多处有副本,改口径时要 grep 全部副本逐一同步,并用机检比对一致(不一致就阻断上线)。
- **反例/代价**:副本不一致会让用户看到自相矛盾的数据,信任受损;也会让排障者被"到底哪个版本是对的"误导。
- **来源**:§22、mem:data-consistency-iron-rule(原项目编号/记忆名,仅供溯源)

## 数据产物必须原子写

- **现象**:进程在写数据文件时被杀,留下一个半截的文件,下游读的时候解析报错或读到残缺数据。
- **根因**:直接往目标文件里逐段写,写到一半进程没了,文件就处于半完成状态,而下游不知道它不完整。
- **防再犯**:数据产物一律**原子写**——先写临时文件,写完整后一次性改名(rename)到目标名;改名是原子操作,下游要么看到旧完整版、要么看到新完整版,永远不会看到半截。
- **反例/代价**:非原子写会产生半截文件,下游解析失败或静默读到坏数据,且时间上难复现、难排查。
- **来源**:mem:atomic-write-data-artifacts(原项目编号/记忆名,仅供溯源)

## 生成路径不等于消费路径

- **现象**:生成器把产物写到了 A 路径,而消费方习惯从 B 路径读,两处不同步;产物改了但消费方读的还是旧版。
- **根因**:生成路径与消费路径是两个独立设定的位置;没有一条约定把它们绑在一起,改一个不会自动带动另一个。
- **防再犯**:产物改动时,**列出它的全部依赖/消费清单,逐个确认"重新生成 + 同步到消费路径 + 上传"三步都做了**;生成器写的位置与消费方读的位置要么是同一个,要么显式声明同步步骤。
- **反例/代价**:路径不同步是经典静默陷阱——生成明明成功了,消费方却还是老数据,而且不报错。
- **来源**:L16、mem:export-output-path-sync(原项目编号/记忆名,仅供溯源)

## 部分缓存当全量返回是反模式

- **现象**:为了省资源做了"懒加载/分片加载",把"已加载的部分"当成"全量"直接返回,导致上层算出来的结果缺数据。
- **根因**:部分加载与全量加载的语义不同;缓存里只有一部分时把它当全量用,上层无法分辨"这是全部"还是"这是部分",于是错误地按全量处理。
- **防再犯**:缓存/懒加载时,**必须能把"部分"与"全量"区分开**(如带完整性标记或未命中就补取),绝不把部分结果直接当全量返回给消费方;需要全量的地方就确保取全。
- **反例/代价**:部分当全量会系统性漏算,结果偏小或缺失,而且看起来"正常返回了",极难被发现。
- **来源**:mem:lazy-load-partial-cache-anti-pattern(原项目编号/记忆名,仅供溯源)

## 同源字段先确认语义

- **现象**:两个字段看着是同一个东西,算出来的值却矛盾;排查半天,发现是字段语义不同(一个是静态快照、一个是动态最新;一个是增量、一个是累计)。
- **根因**:同名/近义的字段可能承载不同语义(静态 vs 动态、快照 vs 增量、时点 vs 区间);不去确认语义就当同一个用,必然矛盾。
- **防再犯**:用到"同源字段"前,先**确认每个字段的语义**(取自哪个时点、是快照还是动态、是增量还是累计);发现数值矛盾时,第一反应是"字段可能选错了",而不是"数据错了"。
- **反例/代价**:把语义不同的字段混用,会得出互相矛盾的数字,误导判断,还会浪费大量排查时间在错误方向上。
- **来源**:E14(原项目编号,仅供溯源)

## 依赖上游已生成文件会静默全空

- **现象**:一段代码依赖"上游早已生成好的某个文件",该文件缺失时,代码不报错,直接产出一个空结果。
- **根因**:读取不到文件时,很多实现会吞掉异常、返回空集合,让"文件缺失"表现为"结果为空";下游无法区分"真的没有"与"没读到"。
- **防再犯**:凡依赖"上游已生成文件"的代码,都要**加存在性校验**——文件不存在就明确报错/告警,不允许静默返回空;把"输入文件是否存在"作为前置检查项。
- **反例/代价**:静默全空会让整个下游链路"看起来正常跑完"却没有任何数据,故障无声无息,常在用户侧才发现。
- **来源**:mem:etf-index-map-source-switch-failure(原项目编号/记忆名,仅供溯源)

## 状态型功能的供给要四件套齐备

- **现象**:做了一个"随时间变化"的状态型/动态功能,交付时只做了"生成这次的数据",没有安排它每天更新、没有机检、也没有过期告警,于是它很快就过时了。
- **根因**:动态功能的价值在于"持续更新",而更新靠的是一条完整的供给链;只做生成那一步,链路是断的,数据会静默变旧。
- **防再犯**:状态型/动态功能的数据供给 = **四件套**(生成脚本 → 定时挂载 → 机检校验 → 过期告警),缺一件都算没完成;用"静态快照/手动生成"这类降级形态顶替时,必须把它作为**方向性分叉上报**给决策者拍板,不能自己悄悄降级。(附带:验收大功能必查"谁每天更新它"。)
- **反例/代价**:断链的动态功能会让人基于一个"已经不动的死数据"下结论,观察期得出的判断全是假的。
- **来源**:L45、mem:s06-static-snapshot-missing-daily-regen(原项目编号/记忆名,仅供溯源)

## 口径基准切换前先做影响面审计

- **现象**:把一个核心口径/默认基准从旧值切到新值,切完后各处数字东倒西歪,才发现影响面没盘清。
- **根因**:核心口径被大量功能依赖;切换会同时影响"会反转的判定""数值会变的展示""能自愈的缓存"等多类,不先盘清就会遗漏。
- **防再犯**:口径/基准切换前先做**影响面审计**,按三类盘:①会反转的(判定从真变假)②数值会变的(展示数字)③能自愈的(缓存/派生);审计完并行修根因,再全面修正受影响的功能。
- **反例/代价**:不做审计就切,会漏改导致数据自相矛盾(此新彼旧),返工范围随时间扩大。
- **来源**:E25(原项目编号,仅供溯源)

## 状态判断用稳定标识而非对象引用

- **现象**:保存"已处理的项"时,存的是对象引用;对象被重建后,引用失效,原先的"已处理"判断全部失灵。
- **根因**:对象引用在序列化、重建、跨进程后会指向新对象;它不稳定,不能当"身份"。稳定的是对象的某个 key 字符串。
- **防再犯**:状态判断(去重、已处理、已保留等)一律用**稳定的 key 标识**(字符串/ID)作为键,不用对象引用;集合用 key 化存储。
- **反例/代价**:用引用当键,数据一重建就全乱,去重失效或状态丢失,且问题难定位。
- **来源**:mem:poscap-keptmap-key-not-ref(原项目编号/记忆名,仅供溯源)

## 计数与列表可以用不同基线

- **现象**:按钮上显示的计数与列表里实际能看到的条目数不一致,用户以为坏掉了;其实是有意设计——计数用宽松口径、列表用完整口径。
- **根因**:计数和列表是两种用途,计数可以只算"粗略命中",列表则要"完整可操作";用同一基线反而不好用。
- **防再犯**:把计数与列表的**基线分开设计**(计数宽松、列表完整),并让用户能理解两者的差异;测试时把两者分开断言,不强行要求它们相等。
- **反例/代价**:强行统一两者,会让计数要么过严(数字难看)、要么列表要么过松(塞进不可操作项),体验受损。
- **来源**:mem:filter-count-vs-list-baseline(原项目编号/记忆名,仅供溯源)
