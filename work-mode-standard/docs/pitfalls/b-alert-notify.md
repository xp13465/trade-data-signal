## 排查告警必须事件驱动全量扫描

- **现象**:查有没有出故障,只去翻一个固定的"告警汇总文件",看到它没动静就以为一切正常;实际另有出口已经报过警,只是没写进那个汇总文件。
- **根因**:告警往往有多个出口(邮件、群消息、日志、指标面板),只盯一个出口等于只看了告警的一个角;而"按关键词搜"也会漏掉没见过的新故障。
- **防再犯**:排查告警用**事件驱动**方式——按时间去找"最近一段时间内被写过的所有日志/告警文件"(按修改时间筛),逐个看内容;关键词搜索只作补充,不作主手段。
- **反例/代价**:单通道排查会漏掉最严重的告警,等用户先发现时故障已扩大,且责任落在"监控明明报了但没人看"。
- **来源**:L46、mem:alert-triage-event-driven-scan(原项目编号/记忆名,仅供溯源)

## 单一登记点沉默不等于没有告警

- **现象**:某个"权威登记点"没有新记录,就推断系统无异常;实际上别的出口已经发过严重告警。
- **根因**:一个系统里同一条告警链可能有多个出口,单一登记点的沉默只代表"这个点没写",不代表全局安静。
- **防再犯**:盘清"这条告警链一共有几个出口",把每个出口都纳入排查;规定**严重级别的告警必须统一镜像登记到同一个地方**,禁止存在旁路出口。
- **反例/代价**:存在旁路出口时,严重告警可能永远不进权威登记点,排查者据此得"无异常"的错结论。
- **来源**:L46(原项目编号,仅供溯源)

## 能外发通知的脚本自测前先打桩

- **现象**:对一个会真实发邮件/发群消息的脚本做自测或改错测试,结果测试跑出了真实外发,把一条假告警发到了用户的手机/邮箱,一次测试变成一次真事故。
- **根因**:脚本在"测试环境"里忽略了环境标志,把测试路径当成生产路径,真的走了发送链路;而且测试前没有先证明"打桩(拦截发送)确实生效"。
- **防再犯**:任何具备真实外发能力的脚本(邮件/短信/群机器人),自测/变异测试前**必须先打桩**——把发送目标替换成空实现或沙箱,并**先跑一次证明拦截生效**;测试的验收点写成"本次自测未产生任何真实外发";万一真发了,如实上报并保留记录,不删已发记录。
- **反例/代价**:一次本意是"验证"的动作变成给用户发假告警,污染真实通知渠道、损害信任,还要花时间解释。
- **来源**:L48、mem:notify-script-selftest-must-stub(原项目编号/记忆名,仅供溯源)

## 降噪必须保留真故障判别维度

- **现象**:为了少打扰,把某类告警降级或豁免(不再提醒),结果连真正的故障也被一起静音,故障发生时毫无提示。
- **根因**:降噪时只盯着"减少数量",没有保留"真故障 vs 良性缺失"的判别维度;把整类告警一刀切,正常与异常一起被砍。
- **防再犯**:降噪/降级的验收核心 = 它**仍然能区分真故障和良性缺失**;并且必须用**反例实测**——造一个真故障样本,确认它仍会报警,而不是只测"良性情况不报"。
- **反例/代价**:降噪过度=把监控砍瞎,平时很安静,真出事时也安静,等用户发现时已经晚了。
- **来源**:mem:alert-denoise-keep-fault-discriminator(原项目编号/记忆名,仅供溯源)

## 告警去重与恢复通知

- **现象**:同一故障持续存在时,告警每隔几分钟重复发一次,轰炸用户;故障恢复后又不吭声,用户不知道好了没。
- **根因**:告警只做了"触发",没做"状态管理"——没有按故障维度去重,也没有"恢复"这一事件。
- **防再犯**:给告警加**去重 + 恢复**机制:同一处故障持续期内只发一次(用稳定的故障标识做去重键);故障消失时补发一条"已恢复"。去重键要稳定(如同一个任务 + 同一类关键词组合)。
- **反例/代价**:不去重会形成告警轰炸,用户对告警麻木(狼来了);无恢复通知则用户无法判断当前是否仍在故障。
- **来源**:mem:alert-dedup-mechanism(原项目编号/记忆名,仅供溯源)

## 监控脚本退出码为0不可信

- **现象**:监控脚本以退出码 0 结束,就断定"检查通过、一切正常";实际某个子步骤失败被吞掉,退出码仍是 0。
- **根因**:退出码只反映脚本最外层的结束状态,子进程失败、命令语法错误、部分步骤被跳过都可能不改变最终的 0;退出码 0 不等于检查项都真的跑了且通过。
- **防再犯**:不把退出码当唯一成功判据;要有**独立的成功判据**(如关键产物是否更新、关键字段是否有值)+ **时效阈值**(产物上次更新时间超过阈值就判异常),二者一起用。
- **反例/代价**:退出码恒 0 的监控看起来永远绿,真实故障被长期掩盖,是典型的"假绿"盲区。
- **来源**:mem:monitor-blindspot-exit0-syntax-error(原项目编号/记忆名,仅供溯源)

## 严重级告警统一镜像登记

- **现象**:最严重的告警只走了某个次要出口,权威登记点里看不到,排查时被漏掉。
- **根因**:告警的多个出口各自为政,没有规定"最高级别必须同时写进权威登记点",于是存在排查盲区。
- **防再犯**:规定**严重级别的告警必须统一镜像登记到同一个权威位置**,不允许任何出口绕过它;新增出口时同步补上镜像。
- **反例/代价**:旁路出口让严重告警"发是发了,但没人按权威位置去查",等于没发。
- **来源**:L46(原项目编号,仅供溯源)

## 定时与补发必须带业务日历判断

- **现象**:定时任务在非营业日(周末/节假日/休市日)照样触发,或者补发历史数据时把非营业日也补上,用户收到不该有的通知/数据。
- **根因**:触发源只按"到点"跑,没有加"今天是不是业务日"的前置判断;补发逻辑也只按目标时点跑,没过滤业务日历。
- **防再犯**:凡是定时触发与历史补发,**都要先判断业务日历**(今天/目标日是否为营业日、交易日、工作日),非业务日不触发、不补发。业务日判定要来自一个可信的日历源,不靠硬编码星期。
- **反例/代价**:非业务日误触发会让用户收到莫名其妙的通知,或者往数据集里塞进不该有的记录,污染后续统计。
- **来源**:L37/L38(原项目编号,仅供溯源)

## 重复跑是兜底不是冗余

- **现象**:把同一任务在多个时点重复排期视为"冗余",想砍掉,结果某次漏跑后没有任何补偿。
- **根因**:没想清楚重复跑的性质——它是**兜底**(某一次失败还有下一次补救),而不是浪费;是否真的冗余取决于任务是否**幂等**(重复执行是否安全)。
- **防再犯**:保留多时点重复跑作为兜底;同时确认任务的幂等性——幂等(重复写结果一致)就允许重跑覆盖,非幂等(重复执行会累加/重复发)就要加"跳过已处理"的判断。用"幂等与否"决定"复写还是跳过"。
- **反例/代价**:砍掉兜底时段后,单次失败就变成当天缺失且无人补,故障面从"个别时段"放大成"整天"。
- **来源**:mem:backup-strategy-redundant-runs(原项目编号/记忆名,仅供溯源)
