## 数据源可靠性要压测且多源互备

- **现象**:依赖的某个外部数据源某天挂了或开始限流,整条链路就断;或数据源在压力下悄悄降级/丢数据,平时看不出来。
- **根因**:只依赖单一数据源,且没有测过它在压力/异常下的行为边界;单点失效没有兜底。
- **防再犯**:①数据源可靠性要**压测找边界**(它在多大压力下开始限流/丢数/报错);②**多源互备**——任一数据源都必须有**其他数据源兜底**,且 fallback **不走同源**(同源兜底等于没有兜底)。
- **反例/代价**:单源无兜底时,一次源故障就是全链断供;不压测则不知道边界,突发流量下静默降级。
- **来源**:E28、mem:source-reliability-needs-stress-test(原项目编号/记忆名,仅供溯源)

## 换数据源时按字段值过滤会静默失效

- **现象**:更换/降级数据源后,某些筛选或映射"静默失效"——不报错,但结果全空或全错。
- **根因**:原实现用"某个字段的取值"当过滤判据,而新数据源里该字段的取值规则变了,判据匹配不上,于是静默失效。
- **防再犯**:换/加/降级数据源时,过滤/映射的判据要**锚在稳定标识**上(如 ID 规则、代码前缀这类不随源改变的结构),不要锚在"字段取值"上;换源后专门回归"筛选/映射还对不对"。
- **反例/代价**:静默失效最难查——不报错,只是结果悄悄变空/变错,发现时已经算了一堆错数据。
- **来源**:mem:data-source-switch-field-filter-blindspot(原项目编号/记忆名,仅供溯源)

## 外部接口报错别卡死重试

- **现象**:外部接口报了 400/不支持这类错误,实现却一直在重试,任务卡死在那里空转。
- **根因**:把"参数/契约类错误"当成了"可重试的临时错误";这类错误重试多少次都不会成功,只会卡死。
- **防再犯**:外部接口报 400/不支持类错误时**别卡死重试**——立即换方案、换参数,或把任务暂存待人工处理;区分"可重试(网络抖动/限流)"与"不可重试(参数/契约错误)",后者不重试。
- **反例/代价**:对不可重试错误反复重试=任务永久卡死,还占用资源、掩盖真因。
- **来源**:mem:handle-api-errors-without-stalling(原项目编号/记忆名,仅供溯源)

## 批量传输与调度有业界权威参照

- **现象**:自己设计批量传输/调度(超时、重试、锁、告警),凭感觉定参数,结果踩了别人早踩过的坑。
- **根因**:这类问题业界早有成熟范式与已知反模式;闭门设计会重复造轮子并踩坑。
- **防再犯**:设计/评审批量传输与调度架构时,先参照**业界权威做法**:超时一律**按停滞(而非总耗时)**判断;识别已知反模式(如"重试风暴"——失败后无限重试反而压垮系统与依赖);遇不确定性优先查权威文档/社区,而不是自己推演。
- **反例/代价**:不参照先例,容易把"重试风暴""按总耗时超时"这类已知坑当创新踩一遍,引发级联故障。
- **来源**:mem:batch-upload-arch-industry-refs(原项目编号/记忆名,仅供溯源)

## DNS 劫持类问题用固定 IP 根治

- **现象**:访问某个外部站点偶发失败/被导向错误内容,排查发现是 DNS 被污染/劫持。
- **根因**:域名解析走了不可信/被污染的 DNS,解析结果被篡改;问题出在解析层而非连接层。
- **防再犯**:先确认是**DNS 层还是连接层**问题;若是 DNS 劫持,把域名**固定到可信 IP**(经 hosts 或等效机制)根治;判断依据是"换一个可信解析后是否恢复"。
- **反例/代价**:不区分层就乱试(比如去改代理),方向错、耗时;不根治则问题间歇性复发,极难复现。
- **来源**:mem:dns-hijack-hosts-rootfix(原项目编号/记忆名,仅供溯源)

## 对外发布内容禁内部路径与密钥

- **现象**:一份对外发布的材料/商品里,不小心带上了内部路径、密钥或内部系统入口。
- **根因**:对外内容从内部环境直接拷贝,没有做"去内部化"处理。
- **防再犯**:对外发布内容**主动带对外入口**(官方站点/正规联系方式),**禁止**出现内部路径、内部主机名、密钥、内部编号;发布前做一遍"敏感信息扫描"。
- **反例/代价**:泄漏内部路径/密钥=安全事故,可能被利用,且很难完全收回。
- **来源**:mem:external-product-info-security(原项目编号/记忆名,仅供溯源)

## 限流冷却时间按厂商实际恢复周期定

- **现象**:被外部服务限流后,给凭据设了一个很长的固定冷却时间,结果可用凭据被长期锁死,产能大幅下降。
- **根因**:冷却时间是凭想象定的,不是按"该厂商实际多久恢复"定的;设得过长就把本来可用的凭据锁死。
- **防再犯**:限流冷却时间要**按厂商实际的恢复周期**来定(从文档/实测得到),不设"一个很大的固定冷却"一刀切;退避策略与实际恢复节奏匹配。
- **反例/代价**:冷却过长=可用凭据被长期闲置,产能损失;冷却过短=反复撞限流。都要按实际周期校准。
- **来源**:mem:sensenova-linear-cool-cooldown-overkill(原项目编号/记忆名,仅供溯源)
