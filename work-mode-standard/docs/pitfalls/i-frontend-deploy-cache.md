## 前端资源版本串必须与内容强绑定

- **现象**:发了新版,用户那边却还是老界面;或者某个用户点"更新"后整页白屏,控制台报"找不到某个东西"。
- **根因**:资源版本串(缓存指纹)与实际内容没强绑定——内容变了指纹没变,或指纹指向了一份不存在的产物(孤儿快照);浏览器/CDN 缓存据此滞留旧版或断链。
- **防再犯**:资源版本串**必须随内容强制刷新**(内容变→指纹必变,内容相同也换新串);部署后**自动校验"线上文件的内容哈希 == 页面引用的版本串"**,不一致就阻断上线;每次发布强制换新串,杜绝指纹断链。
- **反例/代价**:指纹断链会产生孤儿快照,缓存/离线机制据此重建时裸崩,表现为整站白屏,是 P0 级事故。
- **来源**:§24、mem:deploy-cdn-stale-snapshot-blue-screen(原项目编号/记忆名,仅供溯源)

## 离线缓存更新必须壳芯配套且可回退

- **现象**:站点更新后,用户的离线缓存(Service Worker)接管时出错,页面白屏;或者更新到一半,壳与芯版本不匹配。
- **根因**:离线缓存接管需要"壳(页面框架)与芯(资源)版本配套";若在两者未就绪时就强行接管清缓存,又无失败回退,就会白屏。
- **防再犯**:离线缓存更新必须**壳芯配套**——确认新版壳(页面框架/入口资源)已就绪再接管;接管**失败要能回退**到旧缓存/旧版本,绝不给用户一个白屏;改资源必须同步 bump 缓存版本串。
- **反例/代价**:无回退的接管一旦失败就是全站白屏,且用户难自愈(清缓存都未必管用)。
- **来源**:§24(原项目编号,仅供溯源)

## 构建产物必须从版本库读取源

- **现象**:构建出来的产物(min 后的文件)内容不对——包含了没打算发布的改动,或者漏了该发布的改动。
- **根因**:构建读的是"工作目录的源"而不是"版本库里已提交的源";工作目录里可能有未提交的临时改动,被构建带进了产物。
- **防再犯**:构建产物**从版本库(已提交的 HEAD)读源**,不读工作目录的脏源;构建前确认工作目录没有会干扰的未提交改动。
- **反例/代价**:脏源构建会让产物与"已提交的代码"不一致,线上跑的是没人评审过的版本,极难排查。
- **来源**:mem:build-min-dirty-worktree-rootfix(原项目编号/记忆名,仅供溯源)

## 大文件下载校验先比字节数再比哈希

- **现象**:下载一个大文件校验,哈希对不上,以为文件被改了;其实是下载中途被慢网络/中转静默截断,拿到的不是完整文件。
- **根因**:慢链路/中转可能在没报错的情况下截断传输;截断的残缺文件当然哈希对不上,但原因不是"内容变了"。
- **防再犯**:大文件下载校验**先比字节数(大小),再比哈希**;大小对不上就是传输不完整,先重下,别急着判"内容不一致"。
- **反例/代价**:不先比大小就报"哈希不符",会把传输问题误判成内容被篡改,排查方向全错。
- **来源**:mem:curl-large-file-truncation-false-mismatch(原项目编号/记忆名,仅供溯源)

## 验证线上资源要确认真实路径与访问条件

- **现象**:验证线上资源时,路径写错(根路径 vs 带前缀)、没带应有的请求头、或遇到重定向,导致验证失败,误以为"没上线"。
- **根因**:线上资源的真实访问路径与访问条件(是否需特定 UA、是否 307 跳转、根路径还是带前缀)与本地不同,直接按直觉访问会失败。
- **防再犯**:验证线上资源前,**先确认真实路径与访问条件**:确认是根路径还是带前缀、是否需要特定请求头、是否会发生重定向(跟随重定向后再看内容)。
- **反例/代价**:路径/条件错会得到假阴性,浪费一轮验证,甚至误判上线失败而重复发布。
- **来源**:mem:min-verify-root-path、mem:live-index-curl-307-use-browser-ua(原项目编号/记忆名,仅供溯源)

## 功能完成的"三查"

- **现象**:声称"功能已完成/已上线",但用户就是看不到——代码写了、数据也生成了,前端要用的那层却没上线。
- **根因**:"完成"被窄化成"代码写好了";而真正对用户可见需要三段链路都到位:代码进主线、数据层生效、前端展示层上线。
- **防再犯**:验收"已完成/已上线"必须**三查齐**:①代码进主线(主线历史里能找到对应提交)②数据层生效(线上数据里有新字段/新值、无旧残留)③**前端展示层上线**(线上前端产物里含新功能的中文字符串/类名)。只验前两查=前端代码可能从未上线。
- **反例/代价**:漏第三查会造成"代码写了但用户永远看不到",且内部还以为做完了,直到用户反馈才发现。
- **来源**:§8、mem:verify-feature-live-not-code-in-main(原项目编号/记忆名,仅供溯源)

## 压缩产物验证用字符串而非变量名

- **现象**:验证压缩(min)后的前端产物是否包含某功能,去搜那个变量名,搜不到,以为没上线;实际变量名被压缩器改了名。
- **根因**:压缩器会对局部变量做重命名混淆;变量名进不了产物,搜变量名必然落空。
- **防再犯**:验证压缩产物用**不会被混淆的内容**——类名字符串、中文字符串、用户可见文案;不用变量名搜。
- **反例/代价**:搜变量名会得到假阴性,误判"功能没上线",导致重复发布或错误排查。
- **来源**:mem:verify-minjs-use-string-not-varname(原项目编号/记忆名,仅供溯源)

## 界面问题多次修不好就该推翻假设

- **现象**:一个界面(视觉/观感)问题,声称修好了两三次,用户看到的却毫无变化,直到第四次才真正修好。
- **根因**:问题可能在三个层面都错了——①问题的定义错了(修的不是用户说的那个)②自验脚本本身算错了(假结论)③自验口径与用户感知口径不一致。
- **防再犯**:界面问题**三次修不好 = 假设整个错了**:停下当前方向,从零重新验证(穷举式排查),换独立的验证者;调度方在用户确认为止**不转达"已修好"**。
- **反例/代价**:在错误假设上反复小修,每次都"通过自验"却零变化,消耗大量往返,用户信任崩。
- **来源**:L42、mem:lite-svg-four-attempts-rootcause(原项目编号/记忆名,仅供溯源)

## UI 改造必须钉落点并做真实浏览器验证

- **现象**:派了一个界面改造任务,执行者改完"代码层验证通过",但真实交互(点击、悬停、联动)还是坏的。
- **根因**:界面改造的验收只停在代码层,而真实问题在交互层;派单时没把"UI 落点(改哪、改成什么)"钉死,也没要求浏览器实操验证。
- **防再犯**:派 UI 改造必须**钉死 UI 落点**(具体改哪个位置)+ **旧控件替代清单**(哪些旧控件被替换)+ **真实浏览器实操验证**(在真浏览器里点一遍);不接受只有代码层验证的交付。
- **反例/代价**:代码层验证过不等于交互层可用,用户一操作就露馅,返工。
- **来源**:mem:ui-refactor-dispatch-blindspots(原项目编号/记忆名,仅供溯源)

## 新功能先隔离验证再融合

- **现象**:新功能直接改在主线上,做到一半把主线弄乱,或新功能的问题影响了原有功能。
- **根因**:新功能在原环境里开发,未做隔离,风险与主线耦合。
- **防再犯**:新功能**先隔离验证**(单开一个环境/标签页/分支做出来并验证),确认可用再融合进主线。
- **反例/代价**:不隔离则新功能的问题直接污染主线,影响面扩大,回退也麻烦。
- **来源**:mem:new-feature-isolated-tab-first(原项目编号/记忆名,仅供溯源)

## 算法或数值改动必须同步全部对外说明

- **现象**:改了算法逻辑或某个数值,代码改了,但对外说明的文案(界面上给用户看的解释)还写着旧规则,用户按旧说明理解,被误导。
- **根因**:同一算法/数值在多处对外说明里出现(弹窗、提示、说明文档);只改代码不改说明,说明就成了错误信息。
- **防再犯**:改算法/数值时,**grep 全部对外说明处的同一数值/规则,逐一同步**(不只是改动点那一处 tooltip);把"公示文案已同步"作为自验项。
- **反例/代价**:说明与实现不符,用户按旧规则理解算法,误导;修复要重新定位所有说明点,成本高。
- **来源**:§21、L18/L25(原项目编号,仅供溯源)
