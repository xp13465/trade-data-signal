## token 优化的六条零成本行为

- **现象**:用大模型干活又慢又贵,第一反应是"要不要换更便宜的服务",却忽略了大量零成本的行为层优化。
- **根因**:成本不只来自模型本身,还来自"怎么问、怎么答、怎么调命令"这些行为;这些不经提示改就能省,且不动业务。
- **防再犯**:养成六条零成本习惯:①**答案优先/无开场白**(直接做,不解释要做什么,不贴回已写文件);②**命令静默化**(状态查询用简洁格式、测试带静默开关、日志只 tail 截断、大输出落盘不内联);③**汇报只回结论+证据点**(全文落档不贴回父上下文);④**用文件引用代替整段读**(回复直接给定位);⑤**小任务不套重流程**(合并处理,不每个都开重壳);⑥**走错方向用回退而非压缩上下文**(不锚定失败链)。收益:输出与上下文都能省一大块。
- **反例/代价**:不做这些,满屏冗余输出与重复阅读会持续吃成本,而且拖慢响应。
- **来源**:E29、mem:reduce-token-waste-behaviors(原项目编号/记忆名,仅供溯源)

## 遇慢或贵先查模型参数层

- **现象**:任务又慢又费,一直在"任务/流程层"想办法(批处理、固化产物),没想到去调最直接的模型参数层。
- **根因**:把"环境给定的模型参数(如是否开启推理思考、用哪个档位、是否开缓存)"当成不可调的常数,于是只在流程层绕。
- **防再犯**:遇"慢/贵"类问题,**第一问是"模型调用参数层有没有解法"**(思考开关、模型档位、token 缓存),再去问任务/流程层;性能/成本优化不固守自身认知,主动上社区/官方文档查经验。
- **反例/代价**:跳过参数层,可能在流程层做一大堆优化,收益还不如关一个开关来得大;白花时间。
- **来源**:§5.2、doc:thinking-off-optimization.md(原项目编号/文档名,仅供溯源)

## 提高缓存命中率的做法

- **现象**:同样的活越干越贵,输入成本居高不下,一查命中率很差。
- **根因**:缓存命中依赖"前缀稳定";频繁新开会话/每次都给全量背景/随手切换模型或档位,都会让缓存前缀失效,整段重新计费。
- **防再犯**:①**同主题续跑尽量不新开会话**(保持前缀连续);②**派单只给差异信息**,不给全量背景;③**一批独立任务并行启动**,共享同一段稳定前缀;④记住**换模型或换档位=缓存全部失效**,非必要不中途换。
- **反例/代价**:命中率差会让同样的工作反复按全价计费,成本翻倍且难以察觉。
- **来源**:mem:cache-hit-rate-optimization(原项目编号/记忆名,仅供溯源)

## 清空上下文省成本必须以完整落档为前提

- **现象**:为了省成本去清空/压缩上下文,结果把还没落档的关键状态一起丢了,恢复时要从头找,得不偿失。
- **根因**:上下文是"工作记忆",清掉就没了;如果没有把它们落到持久位置,清空就等于销毁。
- **防再犯**:清空/压缩上下文**之前,先确保关键状态已完整落档**(改动清单、待办、约束、进度都写到了持久位置);落档是前提,不是可选项。
- **反例/代价**:不落档就清,会丢失状态、重复劳动,省下的小钱远不抵重来的大成本。
- **来源**:mem:persist-before-clear-compact(原项目编号/记忆名,仅供溯源)

## 重复调研与试错返工是最大浪费

- **现象**:同一件事反复调研,或方案没想清就边试边改,来回返工,成本大多耗在这里。
- **根因**:调研不彻底就动手、方案不成熟就实施,会导致返工;返工的每一次都重付一遍成本,还要外加"推翻重来"的额外代价。
- **防再犯**:调研/方案阶段尽量一次到位(先充分调研再实施,不边试边改);遇到"无/0/不可改善"这类看似终结的结论,也要**换方法/换数据源/多关联维度**验证后再下,并在报告里列出"已验证了哪些方法",避免同一件事被反复重查。
- **反例/代价**:重复调研和试错返工是最贵的浪费——既花了时间又没推进,还容易带出错误结论上生产。
- **来源**:archive token 浪费段、L13(原项目编号,仅供溯源)

## 大文件与重复内容走外部通道

- **现象**:把大段重复内容反复喂给模型,或让模型来回搬运大文件,成本高且慢。
- **根因**:凡是"能被脚本/工具直接处理的机械动作"(大文件搬运、批量替换、格式转换),经过模型回合就多付一遍 token。
- **防再犯**:大文件与重复内容尽量走**外部通道**(由脚本层直接处理),不经模型回合 = 零 token;只在需要判断/生成的环节才用模型。
- **反例/代价**:让模型干机器该干的活,既贵又慢,还容易因为模型幻觉改动出错。
- **来源**:E17(原项目编号,仅供溯源)

## 模型计费异常要主动审计

- **现象**:账单突然变高,查半天发现是有请求"绕道"用了计划外/更贵的模型。
- **根因**:多模型环境下,某些调用可能没走预期的模型(配置漂移、默认值、白名单外模型被触发),造成计费泄漏。
- **防再犯**:对模型计费做**主动审计**——核对实际调用的模型是否为预期模型,发现"白名单外的模型/绕道调用"及时纠正;把"是否按预期模型计费"作为定期检查项。
- **反例/代价**:不审计则泄漏持续累积,账单高企却找不到原因,还可能是长期的隐性浪费。
- **来源**:L35(原项目编号,仅供溯源)

## 上下文按需分层加载

- **现象**:每一轮都把全部历史/全部规范重新发一遍,输入成本巨大(输入远大于输出)。
- **根因**:上下文策略是"全量注入"而非"按需加载";每轮基础重发超长历史,是最大的单点成本。
- **防再犯**:上下文**分层加载**——入口只放"所有角色都该知道的核心",细节按需读取,不让每轮都重发全历史;把稳定不变的部分放最外层,易变的部分按需取。
- **反例/代价**:全量注入会让每轮输入成本随历史线性增长,越到后期越贵,是"越用越贵"的主因。
- **来源**:doc:context-optimization-research.md(原项目文档名,仅供溯源)
