## 带认证头的调试命令禁用详细输出

- **现象**:用带认证头的调试命令(如带 token 的请求)加详细输出开关排查问题,结果 token/密钥被打印进日志、贴进对话,造成泄漏。
- **根因**:详细输出(`-v`/`-i` 之类)会把请求头、响应头原样打印,认证信息随之暴露。
- **防再犯**:凭据安全:**带认证头的调试命令禁用详细输出开关**;token 从环境变量读、不硬编码、不 echo;日志与对话里不出现密钥;万一泄漏,**立即吊销**该凭据。
- **反例/代价**:一次详细输出的排查可能就把密钥泄漏到日志/对话/仓库里,要花大代价轮换全部受影响凭据。
- **来源**:L22、mem:curl-v-leaks-auth-token(原项目编号/记忆名,仅供溯源)

## 接口参数报错先抓原始请求体

- **现象**:调用某接口报参数错误(400 类),一直改自己的参数试,试不敏感,其实参数位置/名称在本版本里变了。
- **根因**:接口/SDK 会随版本调整参数的名称或位置;不拿到"实际发出的请求体",就不知道真正被拒的是哪个参数。
- **防再犯**:参数类报错**先抓原始请求体**(把实际发出去的完整请求 dump 出来),拿它对照官方文档/官方 issue,再改;注意**新版本会挪参数位置**(同一个概念在新版可能换了字段名/层级)。
- **反例/代价**:不看实际请求体就盲改参数,可能改了半天没改到真正被拒的那个,浪费大量时间。
- **来源**:mem:claude-code-output-config-effort-400(原项目编号/记忆名,仅供溯源)

## 切换代理不能由跑在该链路上的会话执行

- **现象**:要切换代理/网关配置,却让一个"跑在这条代理链路上的会话"去执行切换,结果它自己先断线死了,切换做了一半。
- **根因**:切换动作会改变该会话赖以生存的链路;由链路内的人去改链路,必然把自己改死。
- **防再犯**:切换代理/网关配置**不能由跑在该链路上的会话执行**——由链路外的一方执行(或先给方案确认再一次性改对);切换前想清"谁执行才不会被切换动作影响"。
- **反例/代价**:由链路内会话切换=执行到中途自己失联,配置处在半改状态,可能两边都不通。
- **来源**:mem:proxy-switch-not-by-proxied-agent(原项目编号/记忆名,仅供溯源)

## 密钥永不进版本库

- **现象**:把密钥/口令写进配置文件并提交,被平台的密钥扫描拦截,或泄漏后难以回收。
- **根因**:密钥进版本库就进入历史,即使之后删除也会留在历史里;且会被平台扫描与外部收集。
- **防再犯**:**密钥永不进版本库**——放环境变量/密钥管理服务,配置里只放引用;提交前扫一遍;已提交的密钥一次性轮换。
- **反例/代价**:密钥入库=长期暴露风险,清理要重写历史,代价高。
- **来源**:mem:thinking-proxy-config-sop(原项目编号/记忆名,仅供溯源)

## 平台设置不一定作用于子会话

- **现象**:在平台层设了一个偏好(如输出风格),以为所有会话都会遵循,实际对子会话不生效,子会话行为与预期不同。
- **根因**:平台设置的作用范围有边界,某些设置只作用于主会话、不传递到子会话/子 agent。
- **防再犯**:用平台设置前**核实它的实际作用范围**;对"需要子会话也遵循"的需求,不能只靠平台设置,要在派单/子会话本身就写好要求。
- **反例/代价**:以为设了就全局生效,子会话却按默认行为跑,产出与预期不符且难解释。
- **来源**:mem:outputstyle-not-applies-to-subagents(原项目编号/记忆名,仅供溯源)

## 供应商余额类错误是服务端预检

- **现象**:调用外部模型/服务时报 402 或"余额不足/信用"类错误,在客户端反复调整参数、换请求方式都解决不了。
- **根因**:这类错误由服务端在预检阶段返回,是"账户侧"的状态(余额/信用),与客户端参数无关。
- **防再犯**:判 402/余额类错误=**服务端预检**,客户端压不动;解 = 充值或换服务/换模型,不在客户端参数上折腾。
- **反例/代价**:把账户类错误当客户端问题排查,方向全错,白试一堆参数。
- **来源**:mem:codex-openrouter-402-credit-check(原项目编号/记忆名,仅供溯源)

## 外部协作者共用仓库也要隔离

- **现象**:第二个协作者(另一个 AI 或另一个人)与你在同一仓库上工作,互相切分支、互相覆盖,协作状态混乱。
- **根因**:共用同一工作区意味着共享分支指针与工作目录;不隔离就会互相干扰,状态也没有明确的交接机制。
- **防再犯**:外部协作者共用仓库也要**工作树隔离**(各用各的隔离工作区)+ **明确的协作状态字段**(谁在做什么、做到哪)+ **原子写入**(产出一次写完整);通过这些机制交接,而不是共享一个工作目录。
- **反例/代价**:不隔离会导致互相切走分支、覆盖对方文件,协作消息也容易丢,状态无人说得清。
- **来源**:mem:codex-worktree-isolation、mem:codex-ref-channel-status-atomic(原项目编号/记忆名,仅供溯源)

## 工具评估要走实测并落档结论

- **现象**:评估一个工具有没有用,凭它的宣传/名气下结论,装进来才发现有明显的坑、或根本不适配。
- **根因**:工具的实际表现要看实测,宣传/名气不反映它在你的场景里的真实适用性。
- **防再犯**:工具评估走"**实测 + 落档结论**"——真跑一遍,把结论(值得/不值得/适用边界/已知坑)落档;注明适用边界,别凭宣传下结论。
- **反例/代价**:凭宣传采纳,可能引入不合适的工具,增加维护负担;结论不落档则下次又要重评。
- **来源**:mem:codegraph-eval-conclusions(原项目编号/记忆名,仅供溯源)
