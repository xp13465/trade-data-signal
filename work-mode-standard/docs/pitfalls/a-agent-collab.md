## 派单返回不等于启动成功

- **现象**:把一个任务分派给一个后台执行者后,以为"派了就跑了",过很久才发现执行者根本没启动(或被静默杀掉),任务空等。
- **根因**:分派动作的"调用成功返回"只代表请求被接收,不代表执行者真的起来了;启动失败、环境不满足、被沙箱拦截都会让执行者空返回。
- **防再犯**:分派后立刻做一次"真启动"核对——检查执行者的会话记录/转录文件或进度文件是否在**持续增长**(时间戳在推进、有新行);只增长一次不算、要求一个后续再查的增长证据。
- **反例/代价**:不核对就报"已派出",任务实际空转,等到验收才发现零产出,整段时间白费且要重派。
- **来源**:mem:agent-dispatch-verify-started(原项目编号/记忆名,仅供溯源)

## 汇报在跑数量前逐条核对

- **现象**:向用户汇报"当前有 N 个任务在并行跑",但其中几个其实早已完成(已收到完成通知),数字虚高,用户一眼看出不对。
- **根因**:凭印象累积计数,收到完成通知后没有把该执行者从"在跑"集合里移除;状态没有实时的单一来源。
- **防再犯**:汇报任何"在跑数量"之前,逐条核对每个执行者的**最新完成通知/状态**;凡已收到完成通知的立刻移出在跑集合,再统计。
- **反例/代价**:数字虚高会误导排期与资源决策;用户发现后信任受损,且可能据此误判还有空闲产能去接新任务。
- **来源**:L36、mem:agent-status-verify-before-report(原项目编号/记忆名,仅供溯源)

## 判执行者死活看转录是否增长

- **现象**:用进程名/进程号(`pgrep` 之类)判断一个后台执行者是否还活着,结果判断错误——进程在,但实际已卡死;或进程名匹配到了别的同名进程。
- **根因**:进程存在只说明有这么一个进程壳,不说明它还在推进工作;进程名匹配过宽还会命中无关进程;卡死的执行者进程仍在,但不再产出。
- **防再犯**:判活看**转录/日志文件是否持续增长**(比较两个时点的文件大小或最后修改时间);在册状态为"运行中"但转录长时间(如超过约定阈值)冻结,就判卡死并重启该执行者。
- **反例/代价**:误判"还活着"会一直干等一个死任务;误判"死了"会重复启动造成资源浪费与写冲突。
- **来源**:mem:agent-silent-death-pgrep-unreliable(原项目编号/记忆名,仅供溯源)

## 异步通知会丢,必须配轮询兜底

- **现象**:指望执行者完成后通过异步消息通知调度方,结果通知在传输中丢失,调度方一直傻等,直到用户催问才发现。
- **根因**:跨进程/跨会话的异步通知在架构上就不可靠(会丢),把"通知送达"当唯一信号源是设计缺陷。
- **防再犯**:任何依赖"等别人通知"的地方,都要配一层**主动轮询/巡检兜底**(定时去查状态或进度);把兜底巡检当成可靠残余,通知只是加速通道而非唯一通道。
- **反例/代价**:没有兜底就等于把整个流程押在一个会丢的通道上;一次丢消息就是一次长时间空等。
- **来源**:L01、mem:agent-sendmessage-to-main-notify、mem:dispatch-cron-backstop-rootcause(原项目编号/记忆名,仅供溯源)

## 调度者不亲手实施与验证

- **现象**:协调/调度角色图快,自己动手改代码、跑测试或生成数据,而不是把活派给专职执行者;结果既失去分工的复核价值,又把自己卷进细节。
- **根因**:紧急感让人走捷径("我自己改一下更快"),忘了角色分离的核心价值是"实施者与验收者分开"能防自出自证。
- **防再犯**:调度者只做分派、时点管理与最终验收;实施(改代码/改数据/跑脚本)一律派给执行者。唯一例外是**明确的小改**(纯文案、单行常量、无逻辑无跨文件影响)且确属紧急,才可自己动手,并做完自检。
- **反例/代价**:调度者亲手实施后,没人再从外部视角复核,错误自出自证;长期还会把调度者的上下文拖进实现细节,丧失全局视野。
- **来源**:L29/L43、mem:main-controller-*(原项目编号/记忆名,仅供溯源)

## 小修复不套重流程

- **现象**:一个改一行文案的小活,也走完整的"立项→派单→多角色评审→测试→合并"重流程,冷启动与协调成本远超改动本身。
- **根因**:流程是拿来保障风险的工作,不是越多越好;对低风险小改,重流程的边际收益近零而成本固定。
- **防再犯**:先判断改动等级——纯文案/格式/单行常数/无跨文件影响=小改,直接改+自检即可;涉及逻辑/口径/算法/跨文件=走完整流程。拿不准时按高风险处理(走流程)。
- **反例/代价**:小事套重壳,团队时间被流程吞掉,真正的风险改动反而因流程疲劳被草率对待。
- **来源**:mem:small-fix-no-agent-shell(原项目编号/记忆名,仅供溯源)

## 中途改口径就停旧派新

- **现象**:任务跑到一半需求口径变了,却只发个补充消息让原执行者"顺手改改",结果原执行者带着旧规格继续做,产出的东西一半旧一半新。
- **根因**:执行者的上下文里已经装了旧规格;中途追加消息很难保证它把旧规格完全替换掉,容易两套规格混用。
- **防再犯**:口径/方向一变,**停掉旧执行者,用新规格重新派一个**;不要把"改口径"当成给旧执行者的追加任务。停旧、派新,是需求变更的标准动作。
- **反例/代价**:旧执行者产出的中间产物基于旧规格,与新规格冲突,合并时要大量返工甚至推倒重来。
- **来源**:mem:midflight-pivot-stop-old-agent、L15(原项目编号/记忆名,仅供溯源)

## 用户接管先停在场执行者

- **现象**:用户决定亲自接手某个任务,而一个自动执行者还在同一任务上跑,两边同时改,撞车。
- **根因**:接管动作只发生在"人"这一侧,没有同步停止机器侧的同任务执行者,留下并发的第二个改动源。
- **防再犯**:用户一说接管,第一件事就是**停掉在同一任务上运行的所有执行者**,确认停了再动手,避免双写。
- **反例/代价**:两边并发改同一处,谁最后写谁覆盖,产出混乱且难追溯;用户的操作被机器覆盖,体验极差。
- **来源**:mem:user-takeover-stop-inflight-agent(原项目编号/记忆名,仅供溯源)

## 并发改同一仓库必须工作树隔离

- **现象**:两个执行者同时改同一个代码仓库,互相看到对方的中间状态,提交互相覆盖、分支互相干扰。
- **根因**:一个仓库的工作目录与分支指针是**全局共享**的;多人(多执行者)在同一工作目录上并发改,必然会互相踩。
- **防再犯**:每个并发执行者开自己的**隔离工作树**(独立的工作目录 + 独立分支);合并时先查分支归属,确认各改动落在各自分支上。
- **反例/代价**:不隔离就会出现"我改的文件被你 checkout 走了""你的提交盖了我的"这类难查的覆盖事故。
- **来源**:mem:concurrent-implementers-worktree-isolation(原项目编号/记忆名,仅供溯源)

## 续跑同一任务必须延续原分支

- **现象**:同一任务的后续改动,没有沿用原来的分支,而是新开分支再挑拣(cherry-pick)挪过去,导致分支身份漂移、出现废弃分支、提交哈希对不上。
- **根因**:隔离工作树被上一个执行者占用后未清理,续跑者无法签出原分支,只能转用挑拣的方式绕开,于是产生第二个分支。
- **防再犯**:续跑同一任务前,先查原分支是否被残留工作树占用;被占用先释放,再在原分支上继续改并确认当前分支正确。**同一任务的改动永远落同一分支**。
- **反例/代价**:分支漂移会产生多个近似分支,不知道哪个是权威,后续合并容易漏改或重复改。
- **来源**:mem:resume-same-task-reuse-branch(原项目编号/记忆名,仅供溯源)

## 派单必须要求每步写进度文件

- **现象**:一个长任务派出去后长时间没动静,想查它到哪一步了却发现无处可查,只能干等或猜它是不是卡死了。
- **根因**:派单时没有要求执行者把进度落到一个约定位置的进度文件里,于是没有任何可观测的中间状态。
- **防再犯**:派单指令里**必须写明**:每完成一步就往指定的进度文件追加一行(带时间与说明)。约定一个固定路径(如 `<临时目录>/进度-<任务名>.md`),调度方按它巡检。
- **反例/代价**:没有进度文件,卡死无法及时发现,只能靠超时后的猜测定性,浪费大量等待时间。
- **来源**:L21(原项目编号,仅供溯源)

## 执行者自等定时器不可靠

- **现象**:给执行者安排一个"过一会儿自己醒过来再干"的自定时期待,结果执行者所在的会话一结束,定时器就失效,该动作再也没发生。
- **根因**:执行者的进程/会话是短生命周期的,会话结束其内部的定时器随之消失,不能当作持久的调度器用。
- **防再犯**:任何"到点要做"的动作,由**持久的调度方**来兜底(一个长期在位的调度器/定时任务),不要依赖执行者自己内部的定时器。
- **反例/代价**:把时点动作押在执行者自身上,会话一断就是永久漏做,且没有告警。
- **来源**:L33、mem:subagent-timer-not-reliable(原项目编号/记忆名,仅供溯源)

## 破坏版本控制目录的操作会被拦死

- **现象**:派执行者做某些"往版本控制目录里做注入/破坏性写入"的测试,执行者卡住不动且报不出错,看起来像永久挂起。
- **根因**:这类操作会被工具/沙箱层拦截,且拦截后表现为静默卡死(不是明确报错),执行者无限等待。
- **防再犯**:不要派执行者去做"破坏版本控制目录"这类会被拦的操作;确需测试这类路径,换用不会触碰受保护目录的等价方式,或由人在受控环境里做。
- **反例/代价**:执行者卡死,任务假死,占用一个执行额度,还需人工介入清理。
- **来源**:mem:agent-sandbox-blocks-compound-commands(原项目编号/记忆名,仅供溯源)

## 并行收益要量化

- **现象**:默认"多开几个执行者就一定更快",实际加上协调、同步、冲突处理的成本后,并行并不划算,甚至更慢。
- **根因**:并行有固定的协调成本(任务拆分、状态同步、结果合并、冲突解决),该成本随参与方数量增长,抵消甚至超过并行省下的时间。
- **防再犯**:上并行前先量化:要拆几步、每步的协调/合并开销、冲突概率;只在"任务天然独立、合并开销低"时才并行。任务之间有强依赖或共享写目标时,串行更优。
- **反例/代价**:盲目并行导致协调成本吃掉全部收益,还要额外处理冲突;用户看到的是"人多了反而更乱"。
- **来源**:doc:parallel-cost-benefit-2026-08-18.md(原项目文档名,仅供溯源)
