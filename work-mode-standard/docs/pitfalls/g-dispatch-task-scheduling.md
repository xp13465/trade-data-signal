## 派单必须带定位锚点

- **现象**:派一个任务给执行者,只给了"去改那个功能"这种模糊描述,执行者从一个很大的文件的第一行开始搜,耗时且容易找错地方。
- **根因**:任务描述缺少精确定位;大文件从零搜的搜索成本高,还容易误判定位点。
- **防再犯**:派单时**必须带定位锚点**——给出"文件 + 行号"或"关键符号(函数名/类名/字符串/常量)",让执行者直接跳到定位点,不从第一行搜大文件。
- **反例/代价**:无锚点派单会让执行者把时间花在"找地方"上,且找错点会改错文件,来回返工。
- **来源**:§8.1(原项目编号,仅供溯源)

## 派单前先核实基准与默认值的当前真值

- **现象**:派单时沿用了某份旧报告/旧索引里的"基准值/默认值",而这些值早已被改过,执行者按过时的值干活,产出全部要重来。
- **根因**:报告与索引是"过去的快照",默认值会随开发变化;直接沿用就相当于用一个过期前提开工。
- **防再犯**:派任何依赖"基准/默认值"的任务前,先核实它的**当前真值**(以实际代码/权威定义为准),不沿用旧报告;发现派单后基准已变,立即同步给在跑的执行者,避免全量重跑。
- **反例/代价**:基于过时基准干活,轻则产出不可用、重则结论方向都错,整批返工。
- **来源**:L31、mem:pending-index-drift-verify-before-recommend(原项目编号/记忆名,仅供溯源)

## 索引清单会漂移,按它办事前先核实物

- **现象**:按一份"待办索引/清单"去安排工作,里面的条目其实早已完成但没销号,于是重复做已经做完的事。
- **根因**:索引是人工/半自动维护的,会漂移(完成未销号、状态未更新);索引只是指针,不等于实际现状。
- **防再犯**:按索引/清单办事前,**先核实对应的实物/现状**(去看代码/数据/产物是不是真的还没做);索引与现状不符时,以现状为准并顺手修正索引。
- **反例/代价**:按漂移的索引干活,会重复劳动、推荐的项可能已经过时,白费力气。
- **来源**:mem:pending-index-drift-verify-before-recommend(原项目编号/记忆名,仅供溯源)

## 任务状态实时更新且收尾要三块总结

- **现象**:任务状态等到收尾才更新,中间别人看到的都是旧的;收尾时也只是含糊说一句"做完了",没交代改了什么、效果如何、下一步。
- **根因**:状态更新被拖到收尾,中间态不可见;收尾缺固定结构,信息不全。
- **防再犯**:①**状态实时更新**(不用等收尾,变化就写下来);②收尾时给**三块总结**:改了什么 / 效果如何 / 下一步,并把总结落档 + 进提交信息。
- **反例/代价**:状态滞后会导致排期与协作基于旧信息;收尾信息不全则交接困难、无法验收。
- **来源**:mem:task-status-realtime-update、mem:task-wrapup-summary-report(原项目编号/记忆名,仅供溯源)

## 任务治理走四态流转与单一事实源

- **现象**:任务散落在多个文件里,状态各处写得不一样,谁也不知道某个任务现在到底在哪个阶段。
- **根因**:没有统一的状态定义与唯一权威来源;多个登记点各写各的,必然冲突。
- **防再犯**:任务按**四态流转**(活跃 / 远期 / 完成 / 归档,对应不同文件),并确立**单一事实源**(某一处的编号+状态列是唯一权威,其余地方只写指针),再加一层**机检兜底**(自动核对状态一致性)。
- **反例/代价**:多源状态必然互相矛盾,任务看板失真,反复出现"这个到底做完没"的扯皮。
- **来源**:§23.12、mem:tasks-*(原项目编号/记忆名,仅供溯源)

## 定时任务要管时点冲突

- **现象**:新增一个定时任务或派一个重活,和已有的定时任务撞在同一时点,互相争用资源(同一把锁/同一个库/同一个分支),造成覆盖或阻塞。
- **根因**:没先盘清"当前有哪些定时任务、各在什么时点跑",于是新任务撞进了既有窗口。
- **防再犯**:派任务/设定时任务/推代码前,**先查当前定时任务清单**,列出各任务时点,确认不撞;冲突类型要想到:同推一个目标、同写一个库、并发采集互相限流。主动给出时点建议,避开对方的窗口。
- **反例/代价**:时点撞车会导致线上数据被覆盖/库锁/任务互相拖慢,往往是不可逆的生产故障。
- **来源**:§14、mem:production-stability-p0(原项目编号/记忆名,仅供溯源)

## 应急止血同样要守时点窗口

- **现象**:线上出问题,急着"马上重出数据/重跑流程",就直接在禁区窗口里动手,和正在跑的定时任务撞上。
- **根因**:把"紧急"当成了时点约束的豁免理由;但紧急不改变"此刻有别的任务在跑"这个事实。
- **防再犯**:**应急止血同样守时点约束,不豁免**。动手前先核当前时点 + 当时并发任务:能挪到窗口外就挪;确需在窗口内执行,先报决策者拍板 + 事后如实留痕(现象/重叠时长/实际影响)。治本时要把时点约束**内建进设计**(窗口门 + 硬超时),不靠"跑的时候记得看表"。
- **反例/代价**:紧急之下踩线,可能把一个局部故障扩大成并发事故;事后还要花时间解释与取证。
- **来源**:mem:emergency-heal-respect-schedule-window(原项目编号/记忆名,仅供溯源)

## 看门狗外层超时必须大于内层

- **现象**:一个带超时重试的任务超时退出了,但日志里看不到任何内层重试的痕迹——外层看门狗把整个任务砍了,内层根本没来得及重试。
- **根因**:外层看门狗的超时设置**小于等于**内层重试所需的总时间,外层先到点把内层一起杀了,重试形同虚设。
- **防再犯**:设计超时要留**梯度**:外层看门狗的超时**必须大于**内层的单次超时(且内层要有自己的重试),让内层有机会完成重试;判"超时但没重试"要想到是不是外层把内层砍了。
- **反例/代价**:外层超时过紧会误伤内层重试,任务本该自愈却被整体砍掉,表现为"超时且无重试"。
- **来源**:mem:watchdog-inner-timeout-no-gradient(原项目编号/记忆名,仅供溯源)
