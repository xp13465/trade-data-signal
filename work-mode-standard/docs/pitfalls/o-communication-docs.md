## 面向用户的输出要简洁口语化

- **现象**:给用户的回答又长又绕,堆满术语和细节,用户读起来费劲,真正要紧的结论被淹没。
- **根因**:把"展示我做了多少"当成了"帮用户理解";没有区分"对用户说的"与"内部的完整记录"。
- **防再犯**:面向用户的输出**言简意赅 + 口语化**:结论优先、短句为主、像聊天一样自然;术语用大白话或首次出现时解释;完整细节落到文档里,不刷屏。**说人话**——自问"没干过这行的人读这句,知道要干嘛吗"。
- **反例/代价**:长篇大论让用户找不到重点,沟通效率低,还显得不体贴。
- **来源**:§6、mem:reply-brief-and-colloquial(原项目编号/记忆名,仅供溯源)

## 要人拍板前先说清优缺点并给方案集

- **现象**:向别人要决策时,只问一句"要不要这么办",对方没有任何依据可选,只能反问。
- **根因**:把决策问题抛成了开放题,没给选项与权衡,决策者无法有效拍板。
- **防再犯**:要人拍板前**先说清优缺点**(缺点/风险优先说),**不问"要不要"**,而是给 **2~4 个具体方案 + 各自好坏 + 我的建议**;让人在看清权衡后做选择。
- **反例/代价**:开放式提问把负担推回给决策者,来回一轮还定不下来;不摆缺点则可能误导对方做了错的决定。
- **来源**:mem:decide-with-pros-cons-first、mem:no-open-ended-questions-offer-options(原项目编号/记忆名,仅供溯源)

## 方案必须是可证伪的承诺

- **现象**:提了一个"方案",改完发现没达到效果,只好说"完成度打折";其实它从一开始就写不出"改完之后什么会变"。
- **根因**:"方案"与"建议"被混为一谈;只有"改了什么/为什么改/怎么证明有效"都写得出,才是方案;否则只是建议。
- **防再犯**:一个**方案**必须事先写死三件:①**可修正的依据**(可指认、可复核的事实,禁用"我觉得/一般来说")②**可观测的实现预期**(哪个字段/数字/行为,期望从 X → Y)③**证据用例**(事先定好、可独立复现的验证用例)。三件齐才算方案;**写不出预期与证据用例的只是建议**,不许当方案派单实施;实现后拿证据用例对预期,对不上=**方案失败**,不许当"完成度打折"放过。
- **反例/代价**:把建议当方案实施,就是"为改而改"——改完看不出效果,还消耗资源;无预期无证据,好坏无从判断。
- **来源**:§5.7(原项目编号,仅供溯源)

## 方案的默认准则是完整正确不偷懒

- **现象**:给方案时故意夹一个"偷懒版/温和版"凑数,或因为工作量大就省略维度、留"以后再说"的尾巴。
- **根因**:把工作量当成了取舍标准;而衡量方案好坏的标准应是"完整、正确",不是"省事"。
- **防再犯**:方案默认准则:①尽可能**完整正确**;②**不以工作量为衡量偷懒**;③尽量一步到位的终极完整合集;给选项时每个都要完整正确,不凑数;调研全面不省维度;实施彻底不留"后续优化"尾巴。技术细节自己调研给默认方案,只在真正方向性分叉时才给选项。
- **反例/代价**:偷懒方案会留下技术债与半成品,后续返工;留尾巴的"以后再优化"通常永远不会被优化。
- **来源**:mem:proposal-default-criteria-no-compromise(原项目编号/记忆名,仅供溯源)

## 任何事默认持久化

- **现象**:一个重要状态只存在会话/记忆里,会话一结束就丢了,得从头找。
- **根因**:把易失的会话/记忆当成了可靠存储;而它们都不保证长期存在。
- **防再犯:** **默认持久化**——定时任务设成持久;进度落到文件;状态写进文档;重要结论落档。凡"不该丢的"都落到持久位置,不依赖会话或记忆。
- **反例/代价**:不持久化=一次中断/一次清空就丢失状态,重复劳动,还可能丢失关键约束。
- **来源**:mem:persist-everything-by-default(原项目编号/记忆名,仅供溯源)

## 新产物当场落档并归类

- **现象**:新写了个文档/脚本/数据,随手一放,过阵子谁也找不到,或散落在多个不合适的位置。
- **根因**:产物创建时没有"立刻归到合适位置 + 建索引",想着"以后统一整理",而以后通常不会来。
- **防再犯**:新产物**从创建起就放在最合适的位置 + 归类一次到位 + 索引当场更新**;报告类产物要**四件套齐**(本体 + 生成脚本 + 复现段 + 配套提交),缺一不可。
- **反例/代价**:随手乱放会造成产物散落、索引脱节,后续靠"定期整理"补救,成本更高还常遗漏。
- **来源**:§23.5、mem:research-archive-immediately-categorize(原项目编号/记忆名,仅供溯源)

## 已发布功能是冻结资产

- **现象**:顺手"优化"了一个已经上线、用户正在用的功能,结果改变了它的行为/数字/交互,引起用户困惑或数据回退。
- **根因**:把"已发布功能"当成了可以随意改的普通代码;而它一旦上线就是"冻结资产",行为已被用户依赖。
- **防再犯**:**已发布功能=冻结资产,默认只能新增、不能改旧**;想动已上线功能的行为/口径/数字/交互,**必须先确认**(是热修 bug 还是改设计,要讲清);做性能/测试时若发现老功能的 bug 或历史遗留,**先上报完整证明链路再问确认**,不擅自改。
- **反例/代价**:擅自改已发布功能会静默改变用户依赖的行为,造成体验倒退与信任损失,还可能引发数据不一致。
- **来源**:§23.7、mem:version-feature-freeze-contract(原项目编号/记忆名,仅供溯源)

## 规则文档要防膨胀

- **现象**:规则/规范文档越写越长,每轮都要读全量,阅读成本高,真正稳定的条款与临时条款混在一起。
- **根因**:文档只增不减,没有分层;稳定条款与易变条款、核心与细节没有分开。
- **防再犯**:规则文档**定期 review 防膨胀**:把稳定条款**下沉**到专门位置、根文件只留摘要与指针;精简时**保核心 + 可逆 + 复查**(只动外层不动底层,精简后定期复查有没有误删核心);入口只放"所有角色都该知道的核心",细节按需读。
- **反例/代价**:文档膨胀会让每轮阅读成本上升、重点被淹没;而不分层则改一处牵动全身,难维护。
- **来源**:§5.3、mem:weekly-review-sink-stable-rules、doc:claude-md-slim-*(原项目编号/记忆名/文档名,仅供溯源)

## 知识库索引要定期做孤儿死链审计

- **现象**:知识库/索引越用越乱:有指向不存在文件的死链,也有没被索引收录的孤儿文件,找东西靠碰运气。
- **根因**:索引与文件是两套东西,会随时间分叉;没人定期核对,死链与孤儿越积越多。
- **防再犯**:知识库索引**定期做孤儿/死链审计**(双向机检:索引→文件查死链、文件→索引查孤儿);审计结果落档;有意的孤儿要显式说明。
- **反例/代价**:不审计则索引逐渐失真,别人按索引找不到东西,知识库的可信度下降。
- **来源**:mem:memory-orphan-audit-20260927、mem:memory-index-compression-20260927(原项目编号/记忆名,仅供溯源)

## 复杂数值表用三档互证教学

- **现象**:给别人的数值表/复杂指标说明太绕,对方看不懂,还得反复解释。
- **根因**:只用了一种抽象层级的说明;没有从"白话"到"具体例子"的过渡。
- **防再犯**:用**三档互证**教学:①**白话**(这个概念说白了是什么)②**场景**(在什么情况下会用到/会怎样)③**1:1 直白举例**(拿一组具体数字一步步算给它看);举例用的数字必须核实(举例也是自查手段)。
- **反例/代价**:讲不清会让对方反复问,沟通成本高;举例数字不核实则可能自己也被错误数字带偏。
- **来源**:§23.9、mem:complex-table-explanation-style(原项目编号/记忆名,仅供溯源)

## 过错要归档并编锚点防重犯

- **现象**:同样类型的错误反复犯;踩过的坑没人记得,下次照踩。
- **根因**:犯错后没有把"现象 + 根因 + 防再犯条款"沉淀进一个可反查的经验库;经验停在个别人的记忆里。
- **防再犯**:**每次犯错就归档 + 编锚点 + 写防重犯条款**(追加式,不重开条目),形成一个可反查、可 grep 的经验库;后续遇到相似场景先查库,命中就按防重犯条款执行——这也是本手册的元方法。
- **反例/代价**:不沉淀就会重复犯同类错,经验随会话/人员流失;有库但不可反查等于没有。
- **来源**:§18、mem:self-growth-mechanism(原项目编号/记忆名,仅供溯源)
