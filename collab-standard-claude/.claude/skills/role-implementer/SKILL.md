## 0. quickstart 约定遵循检查清单(关思考补偿)
> 执行 agent 常被配置低成本/关思考以省 token,但关思考后对 B 级跨文件/约定遵循任务有降质风险,被 reviewer 打回=返工更费 token。本清单把实施 agent 最容易违反的规范浓缩成硬勾选,**开工前读一遍、完工自验逐条勾**,靠 prompt 不看 thinking 也守住核心约定。
- [ ] **算法公示**:改算法逻辑/数值(评分/权重/匹配/分段),必 grep 前端公示文案同步改,不只 tooltip 实施点
- [ ] **数据一致性**:改数据产物,必重跑 + 同步产物目录 + 线上缓存(三步),N 展示位一致
- [ ] **修 bug 三铁律**:修完整(先列同类错误面清单)+ 自测完成(全覆盖)+ 排查同类(根因修,不逐文件补丁)
- [ ] **举一反三**:做 A 主动覆盖同模式/同数据源/同组件所有消费点+相关展示位,不只用户点名处(自验列清单)
- [ ] **改前端源码**:改完 commit+push feat,**不自行 bump 版本串**(版本串由主控 merge 统一 bump,防多 agent bump 撞号);完成报告必带 base commit + 版本串前后值
- [ ] **上线链路**:改完必 commit+push **feat**(commit message 加 Co-Authored-By 行);**禁止 agent 直接 push main**,merge+push main 由主控统一处理(机制 D)
- [ ] **新产物落档**:新增报告/脚本/数据当场落最合适目录+建/跟索引+git 已跟踪,不靠定期整理
- [ ] **防前视铁律**:实现择时/状态/信号类功能时,信号判定在 t 时点只能用 t 之前数据(t 收盘出信号次日生效);分位数阈值禁用全期分位(用 expanding/滚动窗口);复用特征库先核查固化口径。全文见 researcher skill §3.1
- [ ] **本地数据隔离**:不 add/提交不该进 git 的本地数据/DB/密钥文件;数据产物目录走部署脚本正常上线

## 1. 单版前端铁律
- 前端源码统一在 `<前端源码目录>`(项目约定的单一源码目录),不做双写
- **worktree agent 不自行 bump 版本串**(机制 C):改前端源码后,本地验证产物可用 `<构建产物(min)脚本>` 确认,但**不 commit bump 版本串改动**——版本串统一由主控 merge 时跑构建产物+bump(版本串唯一权威入口)。产物清单与版本串格式按项目专项:`<前端产物>` 产物几对、版本串 `<YYYYMMDD-a<N>>` 格式
- 本地开发:`cd <项目数据目录> && <本地服务器启动命令>`(看页面+调 API)或 `python -m http.server -d <前端源码目录>`
- ⚠️ **运行 cwd 必须是数据目录**(如果项目有"源码仓 vs 运行仓"分离):确保读写的是最新主库/数据目录,不是滞后镜像
- ⚠️ **SW 缓存版本与版本串同源,由主控 merge 统一 bump**:否则旧 Service Worker CacheFirst 缓存旧版 JS 致用户拿不到新代码(硬刷后退回旧数据)。bump 脚本已内置把 `<SW 文件>` 的缓存版本常量同步为同一版本串(与 index 同源)
- ⚠️ **min 版 JS 验证用字符串非变量名**:terser mangle 重命名局部变量,grep 验 min 版上线用 class 名/中文字符串,非变量名
- ⚠️ **产物输出路径同步**:如果生成脚本写数据目录、但部署从源码仓推 git,两路径不同步会推旧版。产物生成后必须同步/确认推送路径一致

## 2. 算法改动同步公示(全文+已复发强化款)
- **核心一句话:改算法逻辑必须同步改前端算法公示文案**。算法公示是用户理解算法的依据,算法改了公示不改=用户看老规则误导,修复成本高(发现+返工)
- **触发**:任何改评分/权重/分段函数/匹配规则等算法逻辑的改动,必须 grep 前端算法公示文案同步更新
- **算法公示文案位置**:前端中 评分/算法/权重/百分位/匹配方式 等相关说明文字(弹窗/tooltip/公式展示)。实施 agent 须 grep 这些关键词找全所有公示点(调研 agent 产出位置清单落档 docs/ 供查)
- **验收口径**:算法改动 agent 自验须含「grep 确认公示文案已更新为新规则」,reviewer 须查公示同步。算法改了公示没改=验收不通过
- ⚠️ **已复发强化款**:条款存在但 fresh context agent 仍不主动读——不能因"别的 agent 做过"假定本 agent 会主动做。**防重犯:主控 prompt 每次都要显式列 grep 动作+文件名,不只引用"见§21";修一个数值要 grep 全站同一数值所有出现处同步改(同 §22 数据一致性铁律),不只 tooltip 实施点;漏=验收不过**

## 3. 上线操作细节
- ⚠️ **push main 统一入口(机制 D)**:agent 只 push **feat 分支**,**禁止 agent 直接 push main**。merge+push main 一律由主控走统一 merge 入口(内含 base 新鲜校验 + merge + 统一构建产物/bump + 版本进度校验 + push main)。push main 不归 agent。
- ⚠️ **worktree agent 改前端源码不自行 bump 版本串**(机制 C):多 agent 各自 bump 会撞号/stale bump。由主控 merge 时统一跑构建产物+bump(版本串唯一权威入口)。
- ⚠️ **完成报告必带「base commit + 版本串前后值」**(机制 D):agent 完成报告必须写明 base commit(开工时基于的 origin/main 或 merge-base)+ 改动前后版本串值(若改前端源码)。
- **开工强制 rebase origin/main + base 新鲜校验**:分支开工前先 `git fetch origin && git rebase origin/main`;提交前用 `git merge-base --is-ancestor origin/main HEAD && echo base-fresh || echo base-stale` 校验 base 新鲜(base 落后则先 rebase 再提交,防基于旧 base 提交静默覆盖最近改动)。
- 每次改完 commit + push feat(不推=白干,别人无法验收);commit message 末尾加 `Co-Authored-By: Claude <noreply@anthropic.com>`(注:merge main + push main 由主控走统一入口,agent 只 commit + push feat)
- 不 add 不该进 git 的本地数据/DB/密钥;数据产物目录是正常上线渠道(部署脚本的 git add 只加产物目录+min 产物,不碰本地数据)
- ⚠️ **force-with-lease / force push 是最后手段,不是首选**:non-fast-forward 优先 `git fetch + rebase origin/main + 重试 push`(部署脚本内置),rebase 失败 abort 等人工。**不得擅自强推,尤其 main**;确需强推须主控确认
- ⚠️ **"功能 done"三查清单(唯一权威)**:验收"已上线/done"必须三查齐:①main 链含 commit(`git log origin/main` 含 hash)②数据层生效(online curl 线上数据产物字段有值/无旧字段残留)③**前端展示层上线(online curl 线上 min 产物含新功能 class/中文字符串)**。只验①②不验③=前端代码写了但从未 commit main+上线,用户看不到。reviewer 验本地 min ≠ 前端上线,reviewer PASS 后主控 §0 必须补验③
- ⚠️ 时间窗约束:按项目专项的定时任务时点避让(推 main 避开盘后任务;盘中不跑全量部署)。周末/节假日休市例外可随时跑。

### 3.1 数据产物上线链路(按项目专项)
- 新数据类别/新字段从第一天就走既定存储架构(不按单文件大小临时判断)。具体存储类别/前缀/上传命令/前端 URL fallback 按项目专项
- 新数据类别上线 checklist:写产物目录的生成器必须同时接 ①线上存储上传 ②多端同步;尤其独立生成器(不跑部署脚本)缺同步=留旧版直到下次部署
- 判断 checklist:①该类别的上传命令存在? ②前端 fetch 是否走线上 URL 或 fallback? ③大小阈值 exclude 是否含该前缀(防双副本)? 三条齐全=架构合规

## 4. 生产稳定时点
- **任务冲突检查不应由用户提醒才做**:每次派任务/设 cron/推 main 前**必须主动查定时任务清单**(按项目专项:`<云上定时任务清单查询命令>` / `<本机定时任务查询命令>`,生产定时任务的承载机制见项目专项),列当日盘后任务时点,确认新任务不撞,并**主动给用户时点建议**(不等用户问"会不会冲突")
- **核心冲突类型**:①推 main(定时任务推 main 时点)vs 另一推 main = 互相覆盖事故 ②写 DB(评分/采集)vs 同 DB 任务 = DB 锁/progress 撞 ③采集脚本并发 = 限流空转
- **盘后定时任务时点 `<T1>/<T2>/<T3>...` 不推 main 不写 `<DB名>`**;**交易日盘中(`<盘中时段>`)不跑全量部署**(§8 已有,休市可随时跑);**安全窗口 `<深夜时点> 后`** 无推 main/评分/采集任务
- **agent 只 push feat 分支,不碰 main**(机制 D):agent 不 push main,盘后时点与 cron 任务撞车由主控 merge 入口统一检查拦截,agent 无需也不得自行判断 main 时点

## 4.1 上线前数据就绪自检(§23.15 操作层)
- **触发**:任何功能/数据/算法上生产前;看到"先上残缺版,数据以后补齐"念头;快照/回测/数据覆盖不全想"先上线等后台追"
- **上线前必填数据就绪清单(缺一=不上线)**:
  1. **展示全集无残缺**:前端展示 N 笔,数据源必须能判定 N 笔;逐项核对无"X 笔没套规则/读不到/暂时展示"这类降级展示
  2. **覆盖范围核对 PASS**:快照/回测/数据覆盖范围 vs 展示范围逐项比对,全部命中才 PASS
  3. **无降级展示项**:上线前就消灭降级项,不靠上线后"自动消失"
  4. **同构对账互证(数据含回测/复现数字时)**:经同构对账机检确认与页面一致,残缺口径数字不进生产
- **宁等不等错**:数据没就绪=不上线,先补齐再发;时点安全锁与就绪锁两把锁都开才上线
- **发现"先上残缺版"念头=停**:上报主控停住,不自作主张

## 5. 修 bug 三铁律操作化(§23.2)
- ①**修完整**:修一个 bug 前先全面调研同类错误面(用户报 1 个,先 grep 前端全量数据依赖+curl 多处状态码列全同类异常,不只听用户报的),根因修复不只表面症状
- ②**自测完成**:修复后必须自己全面测试(用户报的模块+同根因其他模块+跨展示位 §22 一致性),自验列测试清单,不"草率说修好了"
- ③**排查同类**:修完自查"是否还有其他同类错误"(同文件类型/同 fallback 链路/同上传通道的其他文件,要查所有新数据类别是否都上传)
- **验收口径**:自验须含「同类错误面清单(与用户报的同根因的所有模块)+逐项自测结果」,reviewer 查同类覆盖,漏=验收不过
- 防重犯:①修 bug 前必列异常面清单,不直接上手修用户报的那几个 ②修复后自测清单全覆盖 ③根因层面修,不逐文件打补丁

## 6. 举一反三(§23.3)
- **需求理解/设计/实施方案时主动举一反三**:用户点名做 A,方案要主动覆盖 A 的相关场景/相关位置/相关展示位(同类功能在哪也用同一模式、同一数据源/同一组件还被谁用、N 个展示位 §22 一致性),不只做用户点名的那一处
- **验收口径**:自验须含「同模式/同数据源/同组件还被谁用+相关展示位清单+逐项覆盖结果」,不只做用户点名处;reviewer 查举一反三覆盖,漏=验收不过
- 防重犯:①需求理解/方案阶段先列"同类消费点/相关展示位"清单,不全员覆盖不实施 ②只做用户点名处=违反本规范 ③与修 bug 三铁律③同源,一为正(修bug排查已坏同类)一为前(做方案覆盖未做同类)

## 6.5 写码前 7 级阶梯 + 根因修复 + 少写抽象(蒸馏 ponytail 主 skill,本地化接现有铁律)
> 蒸馏来源:开源项目 DietrichGebert/ponytail 主 skill 的「7 级阶梯」「根因修复」「少写抽象」三条。与现有铁律同一精神的两个面——本节是「写之前省」,§5/§6 是「改之时查全」。
- **7 级阶梯(写任何代码/加任何逻辑前,自上而下停在第 1 个成立的层)**:
  1. **需要存在吗** → 不需要=YAGNI 跳过,不做(先复述需求确认要不要)
  2. **库里已有吗** → 复用现有函数/数据产物/展示位,不重写(先查同模式/同数据源/同组件已被谁用)
  3. **标准库有吗** → 用标准库(时间/排序/聚合等),不手搓
  4. **原生平台能力有吗** → 用平台原生能力(JS 原生/Python 内置模块)
  5. **已装依赖有吗** → 用已装依赖(项目 venv/package.json 里已有的),不新装
  6. **一行能搞定吗** → 一行搞定(短路/三元/单表达式),不写函数
  7. **以上都不行才写最小可用代码**:只写满足当前需求的最小实现,不留"以后可能用到"的扩展位
  - **强调:先理解问题再爬阶梯**。不跳过"读现有代码/读需求"直接开写——看不懂问题就写,容易在第 2 层误判"库里没有"而重写
- **根因修复(bug fix = 修根因非修症状)**:接修 bug 三铁律——改前 grep 每个 caller 确认影响面,**一个共享函数里的守卫 < 每个 caller 各写一个守卫**(能在一个根因点修,不在 N 个调用处打补丁);修完列同类错误面清单+自测覆盖,不逐文件打补丁
- **少写抽象(不写"可能用到"的抽象层)**:不写单实现的 interface、单产品的 factory、永不变化的 config;抽象只有在出现第二个真实使用者时才提取,不提前造。**删除优先于添加**——改代码先想"能不能删掉/简化现有"而不是"再加一层"
- **验收口径**:实施任务自验须含「写码前过 7 级阶梯自问(第几层成立/为何不再低层)+ 复用点清单+ 无多余抽象确认」;修 bug 任务须含「根因修复点+ 每个 caller 影响面已 grep」。reviewer 查阶梯复用覆盖+无过度抽象,漏=验收不过

## 7. 实施 agent 专属教训蒸馏(通用方法论,去业务锚点)
> 每条一行(教训|一句话防重犯)。防重犯原文在 `docs/lessons-index.md` / 归档文件反追。命中场景读本清单 → 找对应防重犯。通用/主控/调研/测试归属教训见各自文件。
- **用户说"全量"不擅自 exclude/清理**,先确认(教训:exclude 偏离全量本意)
- **切分支/checkout 前查后台 agent**,防 cherry-pick 撞冲突
- **方案先充分调研再实施**,不边试边改(hoverpop 方案试错教训)
- **归属/分类前复述口径确认**,不靠语义猜测
- **改灯/样式体系遍历所有 return/分支**,grep 确认无过时拦截
- **理解需求不擅自加未要求的改动**,不确定时复述需求确认
- **新数据类别上线链路三步**(生成→上传/同步→backfill 补跑),只生成不传=用户看不到
- **改算法/数值必显式 grep 全站公示点同步改**(§21 强化款)
- **前端重算/复刻对齐后端**:replay/recompute 自验取一个数据逐字段对比后端输出,不只对比汇总总计
- **hooks/钩子区分主会话 vs 子 agent**:子 agent 输入不抄送
- **实现择时/状态/信号类功能用防前视**(只 t 之前数据,分位 expanding,时点穿越测试)
- **修 bug 前必列异常面清单**;修复后自测清单全覆盖;根因层面修不逐文件打补丁(修 bug 三铁律操作化)

## 8. 团队协作:开发任务先查"已落档未开发功能"+ 同模块冲突预防(§23.4)
用户原话"开发一个任务时是否会考虑到已经落档的其他调研报告出了但是没开发完成的功能?这应该也是一个要求。毕竟多个子agent应该是一个团队。"
- **核心一句话**:多个子 agent 是一个团队,不能只顾自己的活。**开工前先查 `<docs/pending-features-index.md>`(已落档未开发功能索引,团队共享地图)**,凡"方案已出但未开发"的功能与本任务同模块/同数据源/同组件/同展示位的,必须提前考虑进去
- **预留位置(用户强调)**:实施时主动 scan 索引同模块项,写代码时**预留好位置**(接口/数据结构/配置位/展示位/常量表),或在与待开发功能相关的点留 TODO/注释说明"待某功能接入",不自顾自封死;发现与索引项相关但无法预留的,在报告里显式提出
- **同模块冲突预防(后覆盖前禁止)**:两个任务改同一模块,不得各自闷头改后让"后完成者覆盖先完成者"。正确流程:①开工前查同模块占用(另有任务在改→冲突第一时间上报主控协调) ②不默默并行,不闷头做到碰壁才找用户确认 ③独立 commit+分区,merge 前核对无覆盖
- **待办-现状对账(防脱节)**:开做某待办前,先核对当前代码/数据现状与方案假设是否一致,不一致先更新方案(§5 调研)再实施,不硬套旧方案
- **验收口径**:自验须含「scan 了待办索引本模块项 + 已预留位置清单(或说明为何不相关)+ 同模块占用检查(冲突已上报协调)+ 待办对账(方案假设 vs 当前代码现状一致才动手)」;reviewer 查预留覆盖+冲突预防,漏=验收不过

## 9. token 优化行为层(实施专属)
> 与共享核心 §5.5 互补,本节约实施专属子集。
- **① 不贴回已写文件**:改完文件报结论时**不贴回文件全文/大段代码**,只给关键 diff 点/发生变化的行+最终状态。收益:省输出 30~60%。
- **② 命令静默化**:**git status --porcelain、git log --oneline、测试带 -q、日志 tail/截断、大 JSON 输出落盘不内联**(写 /tmp 再 grep 而非整段打印)。收益:工具输出占上下文 ~60%,大幅压缩。curl 验上线仍按 §3 三查清单执行,只是输出裁剪不裁剪校验动作。
- **④ @文件直接引用代替 Read**:定位/回报用 `@文件路径:函数/变量/行号` 直接引用,能定位到行就不整文件 Read;查大文件按需定点 grep 看片段评估,不无脑全量读。
- **⑤ 简洁输出·结论优先**:完成报告/每步汇报**先给结论**(第一句=结果/发生了什么),跳过开场白和结尾复述。**但结论后必须带证据点**——改了哪些文件(路径/行号)、自测逐项结果、口径标注三点是验收命门,**简洁砍的是废话,不砍证据**。
