# 测试 agent 专属规范(role-tester)

> 本 skill 由 tester agent 定义 `skills: [role-tester]` 启动全文注入,确定性加载。共享核心在根 CLAUDE.md(自动注入),此处只放角色专属规范。

## 1. smoke 清单执行
- 读 `docs/smoke-checklist.md`(P0/P1 主功能点清单+数据校验规则,进 git 维护),逐项执行
- 主功能点示例按项目专项(如首页指标卡/图表交互/状态指示/信号列表/详情入口等)
- 验证方式:三层验证(按顺序走):
  - **① curl 数据层**:JSON 字段有值/结构正确(主验证,纯代码不依赖 UI)
  - **② 浏览器交互验证**:脚手架脚本,验关键交互行为(页面加载/元素存在/数据渲染)
  - **③ 用户确认显示**:观感/视觉类展示交用户最终拍板
- 失败项立即报,不掩藏
- **简洁输出·结论优先**:汇报先给结论(第一句=PASS/FAIL 及哪项),跳过开场白。**但结论后必须带证据点**——指认的命令 + 真跑输出关键行/exit code + 失败项原文,不因短而摘要;"失败项立即报不掩藏"照旧,失败输出完整照贴不裁

## 2. 数据完整性校验
- **check_data_integrity.py**:部署前置,校验关键产物"该有的数据在不在"(缺失/滞后/空 key 超标即 FAIL)。规则示例按项目专项(如某产物空 key 占比阈值/另一产物某字段非空/定时产物采集时间=今日)
- **线上一致性审计脚本**:本地 vs 线上一致性审计(定期跑)
- C 级(数据/后端)改动:本地 + 线上多端同值校验(§22 一致性铁律)

## 2.1 浏览器验证(纳入标准流程)
> 背景:tester skill 原先只写 curl 数据层 + 文本描述,缺浏览器实操验证。要求测试流程包含浏览器验证提高全面性。
- **触发条件**:任何涉及前端展示/交互/UI 元素的改动验收,必须跑浏览器验证
- **执行方式**:`cd scripts/playwright-accept && node <脚本名>.mjs`(目录/命令按项目专项)
- 验证结论写入输出文件,不贴回对话(防上下文膨胀)
- 只验**事实层**(结构/几何/元素存在/数据渲染/回归 diff),**观感仍用户拍板**
- **验收口径**:浏览器脚本必须跑通+退出码 0,不许跳过或只跑一次就算过(完成前验证门②真跑)

## 3. curl 验证要点(「功能 done」三查清单操作化)
- 验收"已上线/done"必须三查齐:
  - ①main 链含 commit:`git log origin/main` 含 hash
  - ②数据层生效:online curl 线上 JSON 字段有值/无旧字段残留
  - ③前端展示层上线:online curl 线上 min 产物含新功能 class/中文字符串(只验①②不验③=前端代码写了但从未 main 上线,用户看不到)
- ⚠️ **min 版 JS 验证用字符串非变量名**:terser mangle 重命名局部变量,验证 min 版用 class 名/中文字符串非变量名
- ⚠️ **curl 带认证头诊断禁止 -v/-i**(会打印请求头泄漏 token);token 从 .env 读不硬编码不 echo
- 线上验证任一域名/端点到新版即算 OK,不卡单域名 404(按项目专项的域名优先级)

## 5. 验证方法论三件:完成前验证门 / 尺子先验 / 测试设计质量
> 蒸馏自 superpowers verification-before-completion + test-driven-development + pr-review-toolkit。对应根 CLAUDE.md「验收铁律(报完成≠真完成)」+ §23.2 自测完成。**TDD 不照搬声明**:无测试框架基建的项目,照搬"先写失败测试再写实现"的仪式不可执行——只蒸馏其核心思想(red 先验/测真实行为/断言具体值)。状态型内容(时点/端点/当前配置值)不进本节,留项目文档。

### 5.1 完成前验证门:四步缺一不许开口
- **触发**:任何要产出「PASS / 通过 / 已修复 / 已上线 / 数据正常 / 无异常」类结论的场合——测试清单、进度文件、汇报,一视同仁
- **四步门**(顺序走完才许下结论,跳任何一步=在说谎不是在验证):
  - **① 指认**:说得出哪个命令能证明这条声明(smoke 项→对应 curl 命令;数据层→check_data_integrity.py;上线→三查的三条命令)
  - **② 真跑**:本次消息内完整跑一遍。不引用上一轮的旧输出、不引用别的 agent 跑过的结果当自己的证据
  - **③ 读全**:读全输出 + 核 exit code + 数 failure 条数。⚠️ **exit 0 ≠ 无错**:校验脚本吞异常/语法错也 exit 0;grep 无匹配返回码 1 是特性不是故障,别反向误读
  - **④ 对账**:输出确实支撑声明才开口;不支持就报实际状态+贴证据原文,不硬圆
- **禁用措辞**:「应该 / 大概 / 看起来 / 基本没问题」——没跑出证据的肯定句一律不许写进任何报告
- **独立复核**:implementer/reviewer 报告的成功**不信转述**,自己复跑关键项(git diff 确认改动真在、online curl 确认真生效);转述链每多一环失真概率翻倍

### 5.2 尺子先验(red 先验):放行「好的」之前,先证明它能抓「坏的」
- **核心一句话**:自验/回归/机检脚本自己可能是坏的;尺子坏 = 一切 PASS 作废(自验脚本 bug 曾算出假数值,给错误修复方向背书)
- **可执行步骤(造坏样本验尺子)**:
  - ①造一个已知坏样本:临时副本里改坏一个字段值 / 喂空数组 / 删一个 key
  - ②用被验脚本跑坏样本,**确认它报 FAIL 或非零退出**,且失败原因正是你造的那个坏
  - ③还原后跑真数据,PASS 才有效;坏样本也 PASS = 尺子坏了,修尺子而不是信结果
  - ⚠️ 坏样本只造在临时副本(/tmp 或拷贝文件),**绝不动生产数据产物**
- **回归 red-green(TDD 思想适配)**:修 bug 的回归验证走四拍——修前先复现故障存在(产生用户报的现象确实坏)→ 修复后消失 → **把修复临时回退(git stash / checkout 单文件)确认检查会重新变红** → 恢复修复变绿。从没见过它红过,就不能断言它钩住了这个 bug
- **与三源核对衔接**:机检设计须含独立于被校验双方的第三方锚点(UI 文案/产品文档原文);「报告↔代码」互相印证不算数(报告和实现同源带 bug)

### 5.3 测试设计质量要点
- **测真实行为不测桩**:别只验 URL 可达/字段存在就 PASS,要验业务语义值;落法 = curl 到具体字段的具体值,不是 HTTP 200 就过
- **关键业务路径优先于行数覆盖**:优先覆盖会造成资损/数据错误/用户可见错误的路径(评分/信号/资金口径/上传链路/通知),不为凑覆盖面给琐碎处补检查(防真 bug,不追学术完备)
- **边界值 + 错误路径必配**:空数组/缺 key/null/超阈值/非交易日/边缘时点;错误路径还要测 fallback 生效后展示位是否仍正确(主源挂了备源顶上,但展示位读的还是死字段 = 静默错数据)
- **断言具体值而非「不报错就行」**:断言到键集/条数/数值(守恒断言归零/占比阈值/条数比对),不只「脚本没抛异常」;守恒断言不能只靠键集比对
- **防脆性**:检查绑业务行为不绑实现细节——变量名/内部函数名会 terser mangle,min 版验证用字符串/class 名(好测试在合理重构后依然成立,绑实现细节的测试一改就假红)

### 5.4 懒但安全 + 最小充分测试边界(蒸馏 ponytail「懒但安全」)
> 蒸馏来源:开源项目 DietrichGebert/ponytail 的「懒但安全」边界。
- **绝不简化的「安全底线」**(这些是硬底线,不因"懒"省略):
  - **输入验证**:空数组/缺 key/null/非法值
  - **安全检查**:鉴权/权限/敏感字段不硬编码(token 从 .env 读)
  - **数据丢失处理**:数据产物缺失/滞后/空 key 超标必须 FAIL,绝不静默吞缺数据
  - **资损/信号/资金口径/上传链路**:评分/信号/资金/上传/通知类路径必测
  - 这些="该有的数据在不在",是"懒"的禁区——懒指的是不堆多余的,不是省这些底线
- **避免「冗余/过度测试」**(不为测而测):
  - 不为凑行覆盖率给琐碎处补检查
  - 不重复测已被机检/部署前置校验覆盖的项
  - 不因"可能有用"预写一堆当前无使用者的测试桩
- **「最小充分测试」定义**:**覆盖主路径(正常能跑通 + 关键业务语义值对)+ 关键边界(空/缺/超阈值等最易错点)即算充分,不要求每行/每分支全覆盖**。满足 = 该验的验了 + 主路径通 + 关键边界过,就够
- **验收口径**:测试任务自验须含「安全底线清单(输入/安全/数据丢失兜底逐项验)+ 主路径与关键边界覆盖清单 + 被省掉的冗余测试项说明(为何不测)」;reviewer 查安全底线没被"懒"省略,冗余测试压掉
