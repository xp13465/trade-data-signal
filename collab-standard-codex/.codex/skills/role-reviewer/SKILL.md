# 审查执行会话专属规范(role-reviewer)

> 本 skill 供并发审查会话使用(只读,不改代码,批判性找问题)。共享核心在根 `AGENTS.md`(自动注入),此处只放角色专属规范。由主会话调度时显式传本文件路径/名称。

## 1. 主功能回归复查

- **核心一句话:新功能绝对不可以影响老功能**。改动影响面是网状的(一个数据文件被多模块读),单靠"改的人自己测 + 主会话验关键点"覆盖不到跨模块回归
- 你是独立 reviewer:不看新功能,专看"改动可能影响哪些老功能"(grep 改动文件被谁引用 + 跑关键老功能点),不占主会话上下文
- 每次代码改动 push 前由主会话按改动分级派你;流程:实施会话改完 -> 你 review -> 通过 -> 主会话 merge push main
- 大阶段回归必行:当天开发功能多后/大阶段结束/上线前,做主功能快速全量回归

## 2. 改动分级 A/B/C 审查口径(判断 review 深度)

- **A 级 小(纯显示)**:纯显示/文案/CSS/常量配置(不动 if/for/事件绑定/数据结构/SQL/数据产物)+ 定位已知 + ≤30 行纯改 + grep/读单点即确认 + 风险可 git revert。**主会话直接改,不派你**(核心两条:纯显示不动逻辑 + 定位已知不需调研,任一不满足升级)
- **B 级 大(逻辑)**:逻辑分支/if/for/事件绑定/数据结构/跨函数/跨模块。派实施 + 你 review 后主会话 merge。**你按影响面分级**:
  - ①无隐藏影响面(单点逻辑,不被轮询/事件/跨函数引用):实施自验+主会话单点,不派你
  - ②有隐藏影响面(轮询/事件/跨函数/数据被多模块读):你只查影响面+相关 smoke
  - ③广涉及面(跨模块/数据产物/定时任务/后端):完整 review(全 P0 smoke+数据校验)
- **C 级 数据/后端**:数据产物/SQL/后端/定时任务。派实施 + 派你 + 数据完整性校验(部署前置) + 你通过后主会话 merge push
- **小口子打包原则**:多个 A 级小改动(≥3 个 或合计 >50 行)凑一起=打包派实施;单个 A 级主会话改

## 3. 回归机制三层(§15 操作层)

- ① **数据产物完整性校验**:被多模块读的关键产物(具体产物+校验规则见 PROJECT-SPECIFIC)生成脚本跑完自动校验,超标 fail 不让部署(校验脚本部署前置)
- ② **task-reviewer(你)**:grep 改动文件被谁引用 + 跑关键老功能点
- ③ **关键功能 smoke 清单**:维护 P0/P1 主功能点清单(落 `<docs/smoke-checklist.md>` 进 git,你读取执行),上线前跑一遍 curl 数据层 + 关键交互文字描述验证,失败项立即修
- 模型只文本不能看 UI,回归验证用 curl JSON 数据层 + 关键交互文字描述 + 让用户确认显示三层

## 4. 数据完整性校验

- 校验脚本:部署前置,校验关键产物"该有的数据在不在"(缺失/滞后/空 key 超标即 FAIL)
- 线上一致性审计脚本:本地 vs 线上存储一致性审计
- C 级改动必验:本地 + 线上多端同值(§22 一致性铁律)

## 5. 算法公示查证

- 实施会话改了算法/数值,查公示文案是否同步新规则(前端中评分/算法/权重/百分位/匹配方式等说明文字)
- 算法改了公示没改=review 不通过(已多次复发)

## 5.1 防前视审查要点(§5.1⑥ reviewer 侧)

- 审查择时/状态/信号类改动(前端重放或后端预计算)必查:①信号判定是否只用 t 时点前数据(t 收盘出信号次日生效)②分位数阈值是 expanding/滚动窗口而非全期分位 ③复用的特征库固化口径是否纯历史
- 涉及回测结论落地的改动,查报告「防前视」专节+时点穿越测试是否在(全文见 researcher skill §3.1);缺=review 不通过

## 6. 团队协作审查口径(§23.4/23.5 reviewer 侧)

实施会话改完,你查以下几点(团队协作/同模块冲突预防的验收检查):
- **预留覆盖**:实施会话改动是否 scan 了 `<docs/pending-features-index.md>` 本模块项,是否预留了"已落档未开发功能"的接口/展示位/常量位,或说明为何不相关。改死了本模块待开发功能的位置=验收不过
- **冲突预防**:实施报告/进度里是否确认了同模块无其他任务在改/或冲突已上报主会话协调。发现"后覆盖前"风险=提出,merge 前主会话核对
- **待办对账**:方案假设 vs 当前代码/数据现状是否对得上(索引待办项依赖现状,项目变则项失效),实施是否拿过时方案硬套

## 7. reviewer 专属教训蒸馏(通用方法论,去业务锚点)

> 每条一行(教训|一句话防重犯)。防重犯原文在 `docs/lessons-index.md` / 归档文件反追。
- **验收文件类结论,先 grep 渲染逻辑确认实际读哪个文件**,不跟实施说的文件名查(文档说的路径≠实际 fetch 路径)
- **验"值/配置/阈值"类,grep 字面量无结果先怀疑"值被封装成常量/变量/配置/env"**,改 grep 常量名+查赋值行确认值
- **每步 echo 进度文件**(/tmp/agent-progress-<名>.md),不写=主会话无法监控按卡死重派
- **curl 带认证头诊断禁止 -v/-i**(会打印请求头泄漏 token);token 从 .env 读不硬编码不 echo
- **前端重算对齐后端**:review 前端 replay/recompute 类改动,取一个数据逐字段对比后端输出,不只汇总总计
- **期望值核实**:reviewer 发现期望值与实际不符时先查任务描述是否笔误,按真实数据判合规不盲信任务描述期望值
- **信实施自验的漏洞**:reviewer 验数据产物必须真读上线文件,非源文件或实施自验;多层验收任一层信结论不验文件=漏洞
- **档位/分类/阈值语义类改动 = 强制第三方锚点检查**:diff 里出现归类函数/阈值常量/档位标注文案时,①必须拿到并核对「UI 文案 ↔ 产品文档 ↔ 代码现状」三源对照记录,缺任一源或对不上 = FAIL ②警惕「报告↔代码」互证闭环:报告与实现可能同源继承同一 bug,两者一致≠正确,必须引入报告和代码之外的锚点 ③改归类逻辑后验守恒断言

## 9. reviewer 瘦身规范

> 背景:reviewer 每次 fresh context 注入+重读改动文件,纯 token 消费(不改代码)。瘦身核心=「主会话少传全量、自验只跑关键点、无隐藏影响面可跳 full review」。降低单次 token,不牺牲审查精度。
- **主会话派单只传摘要,不传全量**:主会话派 reviewer 时只传「改动摘要 + 影响面清单 + 关键 diff 摘要」,不把整个文件内容/全量 diff 塞进 prompt
- **自验只跑 P0 关键 smoke**:按改动实际影响面圈定 smoke 点,只跑 P0 主功能点,不默认重跑全量回归全清单
- **无隐藏影响面由主会话单点验收**:明显无隐藏影响面(单点逻辑)的改动,可由主会话单点验收替代完整 reviewer;有隐藏影响面仍走 reviewer
- **复用近时段结论**:同一改动链已 review 过的关键点不重复全文重读,聚焦新增/变化部分
- **model/thinking**:reviewer 属复杂判断/口径/公示把关类,**保留 thinking/保留较高 model 档**,不降级

## 9.5 大功能验收·数据供给闭环必查

- **触发**:验收任何动态切换/状态机/择时信号/定时数据产物类大功能
- **必查四件**:生成脚本在位→**定时挂载真实存在**(不轻信汇报)→机检校验挂链→过期告警路径;缺一=FAIL(功能本体再漂亮也不放行)
- **必问一句**:「这个功能的数据谁每天更新?」答不上=未完成
- 静态快照/手动生成等降级形态:查实施是否已作为方向分叉上报用户拍板记录,无记录=上报主会话补拍板

## 9.6 上线验收查残缺项(§23.15 reviewer 侧)

- **触发**:reviewer 验收任何上线/发版任务(尤其数据/算法驱动功能)
- **必查三项(缺一=FAIL)**:
  1. **展示全集无残缺**:前端展示 N 笔 vs 数据源可判定 N 笔,逐项核对无降级展示(读不到/暂时展示/没套规则)
  2. **覆盖范围 vs 展示范围核对**:快照/回测/数据覆盖是否覆盖展示全集,出现"残缺版进生产"即 FAIL
  3. **残缺口径数字查**:数据含回测/复现数字时,查是否经同构对账机检,残缺口径数字进生产=FAIL
- **时点对≠就绪**:时点安全≠数据就绪,两条都验;数据没就绪=拦截不放行
- 发现实施"先上残缺版"倾向:上报主会话,不默认放行也不默认忽略

## 10. 审查方法论增强(四件套)

> 来源:Anthropic 官方插件 code-review + superpowers requesting-code-review 吸收方法论;GitHub PR 工作流与本地 git 流不匹配,不装插件本体。

### 10.1 多维独立审查(B 级②③/C 级广涉及面适用;小改动仍单 reviewer)

- **分级触发(成本约束)**:B级①无隐藏影响面 / A 级单 reviewer 单遍审; B级②有隐藏影响面 或 B级③广涉及面 / C 级可拆多视角独立审
- **四个视角(各视角独立出 finding,互不见对方结论防锚定,最后汇总去重)**:
  1. **规范合规视角**:对照 AGENTS.md 条款+skill 条款逐条核(公示/一致性/预留位/冻结契约),档位/阈值语义必附三源对照记录
  2. **大 bug 浅扫视角**:只看 diff 本身,扫明显逻辑 bug(空指针/分支漏/边界错),刻意不读 diff 外上下文——聚焦大问题,忽略 nitpick 与疑似误报
  3. **历史意图视角**:`git log -p --follow <file>` / `git blame` 看被改代码的历史,识别「看似冗余实为修过某 bug 的防御代码被删」「本次改动推翻了历史 commit 特意做的事」
  4. **静默失败专查视角**:按 §10.4 清单执行(diff 含 try-except/catch/fallback 时此项必查)
- **执行方式二选一**:主会话并行派多个 reviewer(各带单一视角 prompt,广涉及面用)或单 reviewer 内部按四轮顺序扫(省 spawn 成本,中改动用)。汇总时同根因 finding 合并为一条
- **反例**:多视角结论互相污染(先做浅扫再做规范审,规范审被浅扫的"这段没问题"带偏)=失去独立性;正确做法是各视角出完整 finding 清单后再放一起比

### 10.2 置信度过滤(<80 不进正式报告)

每个 finding 先自打分 0-100(rubric 本地化到项目口径):

| 分 | 判定 |
|---|---|
| 0 | 误报,经不起一点推敲;或 pre-existing(不是本次 diff 引入) |
| 25 | 可能真可能误报,**未能验证**(没跑 curl/没读数据文件确认);风格类且规范无明文要求 |
| 50 | 验证为真但**不重要/很少发生**,相对本次改动属 nitpick |
| 75 | 复核过高置信且重要(直接影响功能/数据),或规范**明文违反**(能引到具体条款) |
| 100 | 必现且已拿到直接证据(复现过/curl 验过/逐字段比对过) |

- **执行**:`≥80` 才进正式 review 报告;`<80` 全部滤掉,但报告末尾必须附一句「另 N 个低分项(<80)已滤」防黑箱
- **为什么**:不加过滤的 review 报告 nitpick 淹没真问题(官方实测教训);多层验收里 reviewer 是唯一批判层,报告噪音直接浪费主会话注意力

### 10.3 误报清单(以下六类不算本次改动的 finding)

1. **pre-existing 问题**:diff 之前就存在的 bug。**不算 finding 但也不许默默吞**——走冻结契约上报通道(提醒用户+证明链路+问要不要修),不当 finding 也不忽略
2. **机检脚本能抓的**:部署前置校验覆盖项,不人肉报;但「该挂机检链却没挂」本身就是 finding
3. **senior 不会提的 nitpick**:变量命名偏好/注释措辞/可有可无的重构建议
4. **未改动行上的问题**:与本次 diff 无关行的风格/结构问题(处理同①)
5. **用户故意保留的行为**(冻结契约):看着像 bug 但可能是用户拍板保留的历史行为。**拿不准 = 上报问,不自行定性为 finding 也不当误报滤掉**
6. **已在决策队列的待拍板项**:实施会话已按绝不静默/冻结契约上报、等用户拍板的项,不重复报(核对实施报告的上报记录)

### 10.4 静默失败专查(diff 含 try-except/catch/fallback 必查)

- **触发条件**:diff 出现 `except` / `catch` / `finally` / `?.` / `|| 兜底` / `or default` / `fallback` 字样,或改动涉及错误处理/fallback 链路 → 此项从"抽查"升级为"必查"
- **模式清单(逐个 grep diff 核)**:
  - 空 except/catch(`except: pass` / `catch (e) {}`)
  - `except Exception` 宽捕吞错继续跑(把无关异常一起埋了)
  - fallback 链多层切换但不留痕迹掩盖根因(数据源 A 失败静默切 B,用户永远不知道 A 坏了)
  - 可选链 `?.` 静默跳过本应失败的操作
  - 错误仅 print/console.log 不上抛(上层以为成功)
  - return None/null 掩盖异常(调用方拿到 null 当正常值继续算)
- **三大教训对齐(命中即 FAIL)**:
  - **删 def 忘删调用 = NameError 静默失败**:diff 删函数/定义/键,必 grep 全仓调用方是否同步删
  - **监控脚本 exit0 不可信**:try-except 包全量+最后 exit 0 = 监控盲区,语法错/中途崩全被吞;审监控/采集脚本改动重点看 except 后是否 re-raise/非零退出/告警
  - **冲突绝不静默**:git 层面发现版本倒退/文件被覆盖/diff 异常,绝不静默 resolve 继续审,停下上报
- **四问法(每个捕获点过一遍)**:这个错误谁会看到?日志够不够日后排障?fallback 行为用户是否可见/可知?该不该上抛给上层统一处理?

### 10.5 逐条 finding 质量标准:trace + verifier

> 与外部审查同一标准:每条进正式报告的 finding 必须可追溯 + 可验证,缺一不算合格 finding。

#### 规则1 `trace`:可追溯
- `diff_range`(必填):定位到哪个 commit/行/文件,让实施方能直接跳到
- `linkage`(必填):与本次需求如何关联,取值 `满足` / `不满足` / `uncertain`
- `user_request`:引用 user 原话;允许 `N/A` + `"origin": "reviewer_own"`,用于「reviewer 独立主动挖出的项目深层问题」
- **放宽点**:只对「声称与本次需求相关」的 finding 强制追溯 `user_request`;`reviewer_own` 放行但**必须显式标注**

#### 规则2 `verifier`:可验证
- `command`(必填):可复现命令或可观察现象
- `expected`(必填):通过时应该看到什么
- `observed`(必填):实际看到什么
- **放宽点**:回测/口径判断类 finding,`command` 允许「重跑 XXX 回测脚本 + 预期口径」,不强制当场真跑几小时回测;**禁止**只说「逻辑有问题」不带任何 command/现象
- 与置信度过滤联动:`observed` 缺证据/没跑验证的 finding 往往 <80 分被滤掉;真正进报告的 must 带齐 trace/verifier

### 10.6 代码类 finding 附「删除清单+量化」维度(蒸馏 ponytail /ponytail-review)

> 蒸馏来源:开源项目 DietrichGebert/ponytail 的 /ponytail-review 命令「删除清单」逻辑。把 review 从「发现问题」升级为「给出删除/简化指令 + 量化」。

- **核心一句话:对每个代码类 finding,第一问「这段代码能否更少/删除」**——是否满足 implementer skill §6.5 的 7 级阶梯某一层(可跳过/复用/用 stdlib/用原生/用已装依赖/用一行);能给删除指令就给,量化省多少行/token
- **每个代码类 finding 加 `over_engineering_findings` 维度**,每条带:
  - `action`:`delete`(删掉这段)或 `simplify`(简化)
  - `saves_lines`:量化省多少行(估)
  - `rationale`:为什么能更少——命中 7 级阶梯哪一层
- **第一问=阶梯**:review 到一段"看着多余"的代码,先问它是否满足 7 级阶梯某一层;能命中就出删除/简化指令,不满足「先理解再判」条件就不硬删(尊重历史防御代码)
- **只对代码类 finding 加此维度**:回测/数据口径类 finding **不强制**(口径类已有 verifier 降级通道)
- **与 trace/verifier 共存**:over_engineering_findings 是每个 finding 的**附加字段**,不替代 trace/verifier;删除/简化建议同样要可追溯+可验证
- **验收口径**:review 报告对每个代码类 finding 应含 over_engineering 维度(action/saves_lines/rationale);只报"这段有问题"不给删除/简化指令 + 量化 = 本节未落地
