## 1. 单版前端铁律(去业务化,全文)

> 换站/前端多版并存时,只维护单版前端。改前端源码必同 commit bump 版本串 + 重建 min + push + 验线上 index 引用一致。防全站白屏(CDN/浏览器缓存滞留孤儿旧快照→SW 更新裸崩)。

- **版本串方案**:发布序号(日期+批次)而非纯内容哈希,每次部署强制换新串,杜绝"指纹断链、旧缓存不清、不触发更新"死角。脚本:`<bump版本串脚本>`(或等价,按项目专项)
- **改前端源码必同 commit**:改 `<前端源文件>` 等前端源 → **必须同 commit 跑 `<构建产物(min)脚本>`(现在从 git HEAD 读源生成 min)+ bump 版本串 + push + 验线上 index 引用 `?v=` 与实际文件内容 md5 一致**;禁止"源码改了版本串/没重建 min 没跟着变"漏跑
- ⚠️ **禁 reset --soft 对齐分支**:reset --soft 只移 HEAD 不动工作区,会留旧版 M 脏文件,部署安全网构建产物读工作区旧源生成旧 min 覆盖正确版;要让 HEAD 对齐用 `checkout <commit> -- <文件>` 或正常 checkout,确需 reset --soft 事后必 `git status` 核对工作区无 M 脏文件再 push
- **部署只在 main 分支跑**(部署脚本已加分支校验+显式 main:main push,勿绕过)
- **SW 更新接管需「壳与芯配套 + 失败回退」**:activate 清缓存/接管前,先确认 app shell(min 产物 + index)已预缓存就绪;未就绪不接管不强推,失败回退旧 SW/旧缓存,绝不全白(<SW 文件> 实现)
- **部署后自动校验「内容哈希==index版本串」**:部署链加 check(对每个前端产物算 md5 前8,与 index 引用比对),不一致即阻断上线,防孤儿快照再产生
- **验收口径**:上线/发版任务自验含「版本串每次更换确认 + 改码同 commit bump + 部署后哈希==引用校验 PASS + 备站核心数据在位」

## 2. 算法公示同步(§21 全文+复发强化款)

> 用户铁律,已复发 2 次。改算法逻辑(评分/权重/分段函数/匹配规则等)必须同步改前端算法公示文案(`<前端公示JS文件>` 的算法/评分/权重/百分位/匹配方式 等说明)。

**复发教训**:改算法只改代码没改公示 → 用户看公示文案与实际行为不一致 → 信任受损。**核心:算法改了,公示文案必须跟着改,一次到位。**

- **改动前 grep 公示文件**:每个涉算法改动任务,prompt 必显式列 grep 动作 + 公示文件名,不只引用"见§21"
- **公示文件**:`<前端公示JS文件>` 等算法公示 JS + 前端页面展示算法/评分的说明文字(`<前端源文件>` 内)
- **必须同步的点**:算法名称/评分公式/权重/分段函数/匹配规则/百分位口径/判定来源,凡前端有公示文案的,逐处 grep 同步
- **验收口径**:算法改动任务自验须含「grep 公示文件结果 + 逐处同步确认 + 公示与代码一致」,漏=验收不过。reviewer 会查公示查证(对应 reviewer skill §5)

## 3. 上线操作(机制 D:push main 统一入口)

- **agent 只 commit + push feat 分支,禁止 agent 直接 push main**;merge+push main 一律由主会话走 `<主分支merge统一脚本>` 统一入口(内含安全窗口/merge/base 新鲜/统一构建产物+bump/版本进度校验/push main)。改前端源码的 feat 由统一 merge 脚本 bump 版本串(worktree agent 不自行 bump)
- commit message 末尾加 `Co-Authored-By: Claude <noreply@anthropic.com>`
- 不 add 根目录数据/DB/密钥(保持本地未跟踪,不推);`<数据产物目录>` 是正常上线渠道,后端新增 JSON 字段/新品种必须跑 `<部署脚本>` 推数据上线
- 线上 curl 验证任一域名到新版即算上线 OK,不卡单域名 404(`<主域名> 主站优先 / <备站1> / <备站2>`)
- ⚠️ **不 force**:force-with-lease / force push 是最后手段;non-fast-forward 优先 `git fetch + rebase origin/main + 重试 push`(部署脚本内置),rebase 失败 abort 等人工。不得擅自强推,尤其 main
- ⚠️ **"功能 done"三查清单(唯一权威)**:验收"已上线/done"必须三查齐:①main 链含 commit(`git log origin/main` 含 hash)②数据层生效(curl 线上 JSON 字段有值/无旧字段残留)③**前端展示层上线(curl 线上 min 产物含新功能 class/中文字符串)**。只验①②不验③=前端代码写了但从未 commit main+上线,用户看不到
- ⚠️ **git 冲突/覆盖绝不静默(§23.11)**:任何 git merge/commit/推送/bump/部署环节发现冲突、版本串倒退、文件被覆盖、diff 异常,绝不静默吞掉——宁可卡住上报主会话/用户当场决策,也不能等事态扩大成显性 bug 再修。涉及 git 操作/merge/部署任务自验含「全程无静默吞掉事件」

### 3.1 产物上线链路(数据产物/静态产物)

- 数据产物目录 `<数据产物目录>` 是正常上线渠道(部署脚本推送线上对象存储,后端新增字段/新品种必须跑,否则前端读旧数据)
- 上传机制:生成后即走上传(导出脚本末尾自动传,`<跳过上传环境变量>` 可跳过);上传失败告警、连接复用、multipart 防截尾(按项目专项)
- 对象存储 + CDN 三件:对象存储忽略缓存控制靠部署时 purge / 大 JSON 走对象存储 fallback / 重跑即看的文件加 no-cache 头(curl 验 no-store+purge)
- 上线验证:online curl 任一端到新版即算 OK

## 4. 生产稳定时点(去业务化,占位符)

> 生产稳定性是 P0 第一要素。定时任务撞车会导致线上数据覆盖事故/DB 锁/用户看到错误数据,是不可逆生产故障。任务冲突检查不应由用户提醒才做。

- **任务清单**:每次派任务/设 cron/推 main 前**必须主动查定时任务清单**——**生产定时任务的承载机制见项目专项(例如云上系统定时器,ssh 云上 `<查询命令>` 查清单;单元文件手动管理,代码更新不自动生效;本机是否跑定时任务按项目专项约定,查询前先确认正确的查询方式,不用错的工具)**。列当日盘后任务时点确认不撞
- **时点禁区(占位符,以 PROJECT-SPECIFIC.md 实际值替换)**:盘后定时任务时点(如 15:35/16:00/17:50/20:35/22:00)不推 main 不写关键 DB;**交易日盘中(09:30-15:30)不跑全量部署**;安全窗口(如 23:00 后)无推 main/评分/采集任务
- **push main 要避开**盘后定时任务时点(尤其 17:50 类部署脚本推 main non-ff 竞争;盘中 push 代码不避 intraday——对象存储迁移后 intraday 走对象存储不推 main)。统一 merge 脚本内含安全窗口检查,盘后时点自动拒绝

### 4.1 上线前数据就绪自检(§23.15 完整版铁律)

- **触发**:任何功能/数据/算法上生产前;看到"先上残缺版,数据以后补齐"念头
- **核心一句话:上线必须是完整版**——数据/口径/覆盖全部就绪才发;残缺版上了生产,到数据补齐之间的每一秒就是事故
- **自检三问**:①展示全集无残缺(前端展示 N 笔 vs 数据源可判定 N 笔,逐项核对无降级展示)②覆盖范围 vs 展示范围核对(数据/回测覆盖是否覆盖展示全集)③发现"先上残缺版"念头立即上报主会话停住
- **验收口径**:自验须含「数据就绪清单(展示全集无残缺)+ 覆盖范围 vs 展示范围核对 PASS + 无降级展示项」

## 5. 修 bug 三铁律(§23.2 操作化)

- **修完整**:定位根因后,先列「同类错误面清单」——同一根因还会影响哪些文件/展示位/入口,逐项修,不逐文件打补丁
- **自测完成**:自验必须全覆盖同类错误面,逐项给结果,不报"大概修好"
- **排查同类**:修复后主动排查整个项目是否还有同模式(同数据源/同组件/同逻辑分支)的其他 bug
- **验收口径**:自验须含「同类错误面清单+逐项自测结果」,漏=验收不过

## 6. 举一反三(§23.3 操作化)

- **触发**:用户点名做 A
- **动作**:做 A 时主动列出「同模式/同数据源/同组件还被谁用+相关展示位清单」,逐项覆盖
- **验收口径**:自验须含「同模式/同数据源/同组件还被谁用+相关展示位清单+逐项覆盖结果」,漏=验收不过
- **例**:用户让改首页某数据卡 → 列出该数据源还被谁用(实验室/详情页/邮件链路)→ 逐处核对是否也要同步

## 6.5 写码前 7 级阶梯 + 根因修复 + 少写抽象

> 蒸馏自开源项目 DietrichGebert/ponytail 主 skill + Karpathy 的 Simplicity/Surgical。

### 7 级阶梯(写任何代码/加任何逻辑前,停在第一个成立的)
1. **需要存在吗** → 不需要=跳过,不做(接 L11「不加需求外改动」)
2. **库里已有吗** → 复用现有函数/数据产物/展示位,不重写
3. **标准库有吗** → 用标准库,不手搓
4. **原生平台能力有吗** → 用平台原生能力,不用库
5. **已装依赖有吗** → 用已装依赖,不新装
6. **一行能搞定吗** → 一行搞定,不写函数
7. **以上都不行才写最小可用代码**:只写满足当前需求的最小实现,不留"以后可能用到"的扩展位

### 根因修复
- **消灭错误源头,不逐文件补丁**:同一类错误(如某字段在 3 处被取)修在源头(统一 getter/默认值),不 3 处各打补丁
- **修根因能消整类**:改了源头后 grep 全仓确认所有引用点都拿到正确值,不留下"这处改了那处没改"

### 少写抽象
- **抽象是负债,少写**:不为了"以后可能复用"预写抽象层/装饰器/工厂;确认 2 处以上真实重复才考虑抽
- **删比写难但更值**:重构时敢于删"留作以后用"的死代码,删前 grep 确认无引用

## 7. 实施专属教训蒸馏(通用方法论,去业务锚点)

> 每条一行(教训|一句话防重犯)。防重犯原文在 `docs/lessons-index.md` / 归档文件反追。命中场景读清单 → 找对应防重犯。
- **改算法/数值忘同步公示**:改算法逻辑/数值必须同步改前端公示文案,已复发 2 次,用户铁律(§21)
- **改前端忘 bump 版本串/重建 min**:改源码必同 commit bump+重建,禁 reset --soft 对齐分支
- **改主 JS 忘 bump SW 版本号**:独立点必同步 bump SW CACHE_VERSION,否则旧 SW 缓存旧代码
- **修 bug 只补点名处**:修 bug 走三铁律(同类错误面清单+全覆盖+排查同类)
- **做 A 只做 A**:举一反三,列同模式/同数据源/同组件清单逐项覆盖
- **动核心实用功能不发中间版本**:必须发中间版本+全站键集对齐审计(§5.4⑥)
- **"先上残缺版"念头**:上线必完整版,数据/口径/覆盖全部就绪才发,发现残缺念头立即上报
- **并发 worktree 不隔离**:多实施会话必须独立工作树(不看是否改不同文件),否则 checkout 即错位
- **回测/测试口径与前端链路不一致**:结论用与前端一致的补位口径,删笔仅对照附注
- **改数据产物漏供给四件**:动态/状态/择时类功能数据供给链路(生成→定时挂载→机检→过期告警)缺一不算 done
- **删函数/键忘删调用方**:重构/优化删 def,必 grep 全仓调用方同步删;删定义忘删调用=静默失败
- **同一事实多处代码副本**:键集/字段清单/白名单多处登记时 grep 全部同步+机检比对一致挂部署链
- **新产物不落档归类**:报告四件套(本体+生成脚本+复现段+配套 commit)缺一不可,commit 前 git ls-files 验 tracked
- **绝不 git add -A**:精准 add,数据/大文件走产物目录/对象存储不进 git

## 8. 团队协作(已落档未开发功能 + 同模块冲突预防)

- **开工前 scan 待办索引**:读 `<docs/pending-features-index.md>`,本模块相关有"已落档未开发功能"→ 预留接口/位置/常量位 或 说明为何不相关

## 9. token 行为层(去业务化)

- **输出简洁**:答案优先/无开场白/给结论清单不给全文
- **命令静默化**:`git status --porcelain`、`git log --oneline`、测试带 `-q`、日志 tail/截断、大 JSON 落盘不内联
- **@文件直接引用**:回复用 `@文件路径:函数/符号` 代替 Read,后续者精确定位
- **只回结论+证据点**:回报主会话只给「结论 + 证据点(文件:行号/命令输出/数据值)」,全文/大段调查过程落档不贴回
