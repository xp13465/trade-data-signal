## 一、结论一句话

**并行 + worktree 的真实收益 = 研究型大需求的墙钟速度(6 天打了 4 个版本 tag v1.0.0/v1.1.0/v1.1.1/v1.1.2) + 功能 merge 吞吐 3-5 倍(19 笔/天 vs 1-2 笔/天);真实成本 = 每日调度/审查放大 3-5 倍(agent 轮次 40-54/天)+ 08-18 一天 ~10 起覆盖事故吃光整个下午。净账 ≈ 打平到略亏(收益估 3-5 天 vs 成本估 4.5-8 天),置信度中低。用户的直觉「问题多/好处不明显」数据部分支持——并行赢的是「研究并行 + 版本发布速度」,输的是「同文件并发 + stale base 的结构性覆盖风险」,后者正好是 worktree 机制引入的新洞,不是并行本身必须付出的代价。**

## 四、三方案对比 + 推荐

| 方案 | 并行收益保留度 | 覆盖风险等级 | 实施成本 | 与五条机制+三缺口关系 |
|---|---|---|---|---|
| **A 完全废除并行**(回 08-12 前单 agent 顺序工作流,worktree 只用于隔离实验/回滚) | 低(丢研究并行+版本发布速度,回 5-10 units/day) | 结构免疫(串行天然无 stale base 覆盖) | 高(要重写派单制度+退回大提交) | 五条机制不再需要(过度);根治留着当保险=AB/E 保留 |
| **B 降级安全并行(推荐候选)** | 高(研究并行/版本速度保留 ~80-90%) | 压回「偶发」(根因层堵 stale base + 同文件并发) | 中(调度成本升高:主控盯文件占用+统一 merge) | 直接兑现诱因链缺口①②③:①开工强制 rebase origin/main+commit 前 base 校验 ②同文件串行工具化(git diff --name-only 查在跑 worktree)③bump 唯一权威=主控 merge 时统一 build_min+bump;复用已上线 A/B 哨兵(check_version_progress.py) |
| **C 保留现状+事后拦** | 高(调度最省) | 高(08-18 那种 8-10 起/天密度仍会发生,只是能及时发现) | 低 | 靠 A/B 哨兵事后拦,不解决缺口①②③;用户已表达「问题多」,违背其意愿 |

**推荐 B(降级安全并行)**:
- **贴合用户倾向**:用户说「好处不明显宁可不要,但根治留着当保险」——B 不用走到 A 的极端废除,它把「结构性覆盖风险」(stale base + 同文件并发 + 撞号,三个都是 worktree 机制引入的新洞)从根因层堵死,同时保留真正有价值的并行收益(研究并行 + 版本发布墙钟速度,这 6 天 4 个版本 tag 是实打实的)。
- **A 太极端**:会丢掉研究型大需求的墙钟速度(收益量化 2.3 的 +3-5 天),用户要的是「降级到安全点」不是「回到过去」。
- **C 太弱**:不解决事故密度,08-18 那种一天 8-10 起会复现,用户已经明确「问题多」,C 只是自欺。
- **B 的三条硬约束直接就是诱因链报告的缺口①②③**,加上已落地的 A/B 哨兵做 merge 前兜底,「事前防线+事后哨兵」双保险,覆盖风险从「结构性问题」压回「偶发」;实施后若并行收益实测确实不显著(§5.1 数据说话),再考虑 A 也不迟。
