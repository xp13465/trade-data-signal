## 0. 结论速览(3 行)

1. **选型:A(小文件独立锁)+ B(备份瘦身 + 大文件走分片)+ C(等锁可见性)三步都要做,但有先后**:先 C(加可观测,零风险)→ 再 A(止血,当天见效)→ 最后 B(治本,把 data-large 持锁时间砍半)。只做 A 能止血但不治本;只做 B 会拖几周且期间 nextday 照旧失败。
2. **量化依据:全局锁单次持锁 1420–2575s,其中「上传前备份」约占 2/3(10-21 推算 947.8s/1420.8s),而 nextday 的内层窗口只有 480s —— 数学上必输,不是偶发。** 10-21 只是没撞上锁(前一步 480s 内完成了)。
3. **预期收益:nextday 上传从「480s 超时 + exit 1 + 告警」变成「≤10s 成功」;data-large 持锁从 ~1500s 降到 ~500–900s(分两步吃)。** 两项都能用命令独立验证,不依赖实施方口头描述。

## 1. 现状机制图(文字版)

### 1.1 一共有三把锁,别搞混

| 锁 | 路径 | 谁拿 | 作用 | 代码 |
|---|---|---|---|---|

### 1.2 全局锁的获取/释放路径

```
upload_r2.py <cmd> ...
  └─ __main__ :4303   if cmd not in {list, delete, download-db, clean-data-backup, upload}:
       └─ :4304  _acquire_r2_upload_lock(skip_if_locked=--skip-if-locked 标志)
            └─ :4210  timeout = env R2_UPLOAD_LOCK_TIMEOUT 或默认 7300s
            └─ :4213  lock_path = env R2_UPLOAD_LOCK 或 /tmp/trade_r2_upload.lock
            └─ :4238  fcntl.flock(fd, LOCK_EX|LOCK_NB) 失败则 2s 轮询
            └─ :4267  每 30s 往 stderr 打一行「⏳ 等待 R2 上传锁 Ns」
            └─ :4258  超时 → 打印 fail-closed 说明 → exit 1
       └─ 整个命令(含扫描/备份/上传/purge)全程持锁,进程退出自动释放(:4171 注释)
```

**关键事实:锁是「命令级」而不是「文件级」**。任何命令拿到锁后,从扫描到 purge 全部持锁,期间别人一律排队。

### 1.5 备份为什么在锁里

`_backup_overwritten_keys`(`upload_r2.py:1147`)在 `_incremental_upload` 内部调用(`:1620`),而 `_incremental_upload` 整个跑在锁内。

- **语义**:PUT 覆盖 R2 上已有对象之前,先把**旧版本**经客户端中转(GET 老账号源桶 → 校验 md5/长度 → PUT 到新账号备份桶 → 回读校验 P6)存到 `signal-backup2/pre-upload/<YYYYMMDD>/<key>`。目的是「本机导出坏了覆盖线上时能回滚」。
- **实现**:8 线程并发,得 `(copied, skipped, failed, samples)`;减量规则 P2 = 备份桶已有今天备份 且 R2 ETag == 本地 md5 → 跳过(覆盖无损失)。
- **保留 7 天**:`_PREUPLOAD_RETENTION_DAYS = 7`(`:1097`),`_prune_pre_upload`(`:1100`)清理。

**关键量:这是 GET+PUT 双倍流量。备份 21 个 key ≈ 279MB×2 = 558MB,和「上传 279MB」是同一量级。**

## 2. 方案 A(止血):小文件走独立锁,不排全局队列

### 2.1 依据(文件:行号 + 数字)

1. `upload_r2.py:4303` 的豁免集合只有 `{list, delete, download-db, clean-data-backup, upload}`,`upload-data-files` **不在其中** ⇒ 必然排全局锁。
2. `upload_r2.py:2614` `cmd_upload_data_files` 收的是**显式文件列表**(`sys.argv[2:]`),天然可以在取锁前 stat 出总字节数 —— 不需要扫描目录。
3. 实测 nextday 三个文件合计 121,870B(云上 10-22),按观测吞吐(小文件 index 通道中位 175–197 KB/s)算,**真实上传 <1s**。
4. 10-21 该链整链 22:30:01 → 22:30:11 exit 0(10 秒),那天没撞锁 ⇒ 「不排队时本来就很快」有实证。
5. 锁的设计目的写明是**防跨境带宽互抢**(`:4164-4207` 注释),而 121KB 的带宽占用相对 279MB 可忽略 ⇒ 小文件不需要这把锁的**主要**保护。

### 2.2 改动点(最小集,4 处)

| # | 位置 | 改法(一句话) |
|---|---|---|
| A1 | `upload_r2.py:4163` `_acquire_r2_upload_lock` | 加参数 `lock_path_override: Path \| None = None`,默认仍读 `R2_UPLOAD_LOCK` —— 让同一把锁逻辑能服务两个锁文件(**复用现有 flock/心跳/超时/fail-closed 全部语义,零行为分叉**) |
| A2 | `upload_r2.py:4154` 附近新增常量 + 纯函数 | 加 `_SMALL_LOCK_PATH = Path("/tmp/trade_r2_upload_small.lock")` 与纯函数 `_route_upload_lock(cmd, files) -> Path`,规则见 2.2.1(**纯函数=可单测,不碰网络**) |
| A3 | `upload_r2.py:4300-4306` `__main__` 取锁段 | `if cmd == "upload-data-files"` 先按 A2 算目标锁,再 `_acquire_r2_upload_lock(..., lock_path_override=目标锁)`;其余命令一字不动 |
| A4 | `upload_r2.py:4194-4206` 文档字符串 | 补一条:`upload-data-files` 小载荷走独立小锁,并写明键集不相交前提(见 2.6) |

#### 2.2.1 A2 的路由规则(写死,可机检)

```
_route_upload_lock(cmd, files):
  if cmd != "upload-data-files":                  -> 全局锁(原行为)
  if 任一文件 _is_data_large_file(f) 为真:        -> 全局锁(见 2.6,防同 key)
  if 文件总字节 > R2_SMALL_CHANNEL_MAX_BYTES:     -> 全局锁
      默认 8 * 1024 * 1024(8MB),可用 env 覆盖
  否则                                            -> /tmp/trade_r2_upload_small.lock
```

- `_is_data_large_file` 已存在(`:2124`),判据 = `size>=1MB` 或文件名匹配 `_LARGE_RANGE_RE`(`:2120`,正则 `-(?:all|5y|3y)\.json$`)或前缀 `overfit_monitor`。
- 8MB 这个阈值的依据:nextday 实测 121KB;最大已知 `upload-data-files` 载荷是 `fetch_news` 的归档文件与 `alert_analyze_*.json`(每个 ~11KB,几十个文件)。8MB 给到 ~60 倍余量,同时远小于最慢通道(279MB)的 3%。**不是拍脑袋:阈值只影响「走哪把锁」,不影响正确性 —— 超阈值退回全局锁 = 现状行为。**

### 2.4 证据用例(事先写定,可独立复现,**全程零网络/零写入 R2**)

**用例 1(路由正确性,纯单测,不碰网络)**
```
small=$(mktemp)                       # 已存在的 0 字节文件(不存在的文件 stat 失败 ⇒ 永远被判成"小载荷",取不到证据)
python3 -c "import sys; sys.path.insert(0,'scripts'); from pathlib import Path; import upload_r2 as u; \
  assert u._route_upload_lock('upload-data-large', []) == Path('/tmp/trade_r2_upload.lock'); \
  assert u._route_upload_lock('upload-data-files', [Path('$small')]) == Path('/tmp/trade_r2_upload_small.lock'); \
  assert u._route_upload_lock('upload-data-files', [Path('big-all.json')]) == Path('/tmp/trade_r2_upload.lock')"
```
断言点:小载荷→小锁;大 range 文件名→回全局锁;非 data-files 命令一律全局锁。**纯函数,零副作用。**
⚠ 示例必须指向**已存在的 0 字节/小文件**(`mktemp`)或**仅按文件名命中大 range 正则**的路径:传一个不存在的文件时 `stat` 失败 ⇒ 总字节按 0 算,断言「小锁」永远成立,**证明不了路由**(2026-10-23 审查建议 3 修正)。

**用例 2(端到端锁选择,零 R2 流量)**
用一个临时空文件当「假全局锁」,人为占住它,再跑一个**不会真的传任何东西**的 `upload-data-files`(传一个不存在的文件名,`:2630` 会直接打印「⚠ 无文件」返回):
```
flock /tmp/trade_r2_upload.lock -c 'sleep 30' &          # 占住全局锁(不碰生产数据)
R2_UPLOAD_LOCK=/tmp/trade_r2_upload.lock R2_UPLOAD_LOCK_TIMEOUT=3 \
  python3 scripts/upload_r2.py upload-data-files __no_such_file__.json
```
- 改前:3s 后打印 `✗ R2 上传锁 /tmp/trade_r2_upload.lock 排队等待超 3s ...` 并 exit 1(证明它确实排全局锁)。
- 改后:同样命令应当**立刻**返回「⚠ 无文件」、exit 0(证明它没去排全局锁)。
- ⚠ 注意:`flock` 命令行工具是否在 mac/linux 都有需实施时确认;没有就用 `python3 -c "import fcntl,time; fd=open('/tmp/x.lock','w'); fcntl.flock(fd, fcntl.LOCK_EX); time.sleep(30)"`。**不要占生产锁文件超过必要时间**(建议用 `R2_UPLOAD_LOCK=/tmp/test_probe.lock` 另建一个假锁,避免与真实任务抢锁)。← 更安全的做法:**两个路径都用 env 覆盖成 /tmp 下的测试文件**。

### 2.5 风险与回滚

| 风险 | 等级 | 处置 |
|---|---|---|
| 小文件与大文件写同一个 key(见 2.6) | 中 | A2 的 `_is_data_large_file` 闸门 + 用例 1 断言;`upload-data-files` 传 ≥1MB 文件时自动退回全局锁 |
| 小文件之间的同 key 冲突 | 低 | 小文件通道共用**同一把**小锁,彼此仍互斥(与现状相对顺序一致) |
| 多进程同时打开 `/tmp/trade_r2_upload_small.lock` 首次创建 | 低 | `os.open(O_CREAT)` 已存在,语义与全局锁逐字一致 |
| 有人靠「等锁心跳」判断进展 | 低 | 心跳逻辑未改,锁路径出现在提示文案里,更清楚 |

**回滚 = 一个环境变量**:加 `R2_SMALL_CHANNEL=0` 时 `_route_upload_lock` 恒返回全局锁 ⇒ 一行 env 回到现状,不用回滚代码。

⚠ **取值只有 `0` 或 `1`**(实现 `os.environ.get(..., "1").strip() == "0"`):`false` / `off` / `no` / 空串 **都不生效**(不等于 `"0"` ⇒ 视为开启)。要关闭小锁通道必须精确写 `R2_SMALL_CHANNEL=0`。(2026-10-23 审查建议 3 写死)

### 2.6 同 key 并发写分析(必答)——**结论:有真实重叠,但不在 data-large 上,而在 `upload-all-data` 上;async 单例兜不住**

**(a) 与 `upload-data-large` 会不会撞同一 key?——按现有判据不会,但**不是结构保证**,要加闸门。**
- `data-large` 的取文件判据 = `_is_data_large_file`(`:2124`):`size>=1MB` **或** 文件名 `-(all|5y|3y).json` **或** `overfit_monitor*`。
- nextday 三个文件实测 246B / 91,708B / 29,916B,均 <1MB 且不匹配大 range 正则 ⇒ 今天**不相交**。
- 但 `upload-data-files` 不做任何大小限制(`:2614`),调用方传什么就传什么。**一旦有人传一个 ≥1MB 的文件,它就会同时落进 data-large 的取件范围** ⇒ A2 的路由闸门就是为此设的:**判到 `_is_data_large_file` 为真就退回全局锁**,把这条路径钉死。

**(b) 与 `upload-all-data` 撞不撞?——今天真的重叠,这是 A 的**唯一实质风险**。**
- `all-data` 取件 = `data/*.json` 减去 `_is_all_data_excluded`(`:2138`),排除项只有:`industry-`/`public_fund`/`offshore_fund`/`fund_score`/`etf_score_list` 前缀、`signal_kelly_trades*`、大 range、`overfit_monitor*`、`>=1MB`。
- 所以 `data/nextday_plan.json`、`data/schedule_stats.json`、`data/signal_kelly_day_snapshot.json` **都在 all-data 的取件范围里**,同时又是 `upload-data-files` 的常客 ⇒ **同一个 key 有两个写入者**。
- 今天它们被全局锁串行化;A 之后它们可能在**同一秒**并发写。

**(c) 撞了后果是什么?——不是数据损坏,是「可能写回旧版本」。**
- R2 的 PUT 是**按对象原子的**,没有半写状态;同一 key 并发 PUT = 后完成的赢(last-writer-wins)。
- 两边都调 `_upload_glob._upload_one`,payload 是**PUT 那一刻**的 `f.read_bytes()`(`:979`) ⇒ 正常情况下两边读到的字节**完全相同**,写了等于没写。
- 真正的坏情况:进程 X 在 t0 读字节 → 生成端在 t1 重写文件 → 进程 Y 在 t2 读到新字节并先完成 → X 在 t3 用**旧字节**完成 ⇒ R2 上留一天旧版本,直到下一个周期覆盖。
- 影响面:数据新鲜度(§22 一致性问题),**不是**结构损坏;**不会**产生半截 JSON。

**(d)**必须做的收口(二选一,建议 B0)**:
- **B0-1(推荐,零风险)**:让 `all-data` 跳过独立产物台账里的 key —— `_record_standalone_keys`(`:2443`)已经在 `data/.r2_standalone_keys.json` 里登记了「由 data-files 上传的独立链产物」,`cmd_upload_all_data` 的 `exclude_fn` 加一条「在台账里 ⇒ 跳过」即把两个集合**结构性拆开**。代价:台账只增不减,若某 key 哪天不再由 data-files 上传,all-data 会永久跳过它 ⇒ **必须同时加「台账条目 ≥N 天未被任何 data-files 调用更新则失效」的过期规则**,否则会新型漏传。
- **B0-2(更保守)**:接受这个理论风险,把「all-data 与 data-files 的时间窗在现实中相隔 4.5h(deploy 17:50 vs nextday 22:30),真正会撞的是 intraday 的 10 分钟一轮」写进验收说明,并加一条**只告警不改行为**的机检:两者窗口重叠时记一行日志。
- 本方案**推荐 B0-1**,因为它把「A 引入的新风险」压到 0;若用户希望 A 的改动面绝对最小,则选 B0-2 并在上线说明里写明。

**(e) 现有 async 单例能不能兜住?——不能,三个理由都有代码证据:**
1. **锁的不是同一件事**:`/tmp/trade_r2_upload_async.lock` 只包 `r2_upload_async.sh` 自己(`r2_upload_async.sh:49-54`),它防的是「两趟异步批同时跑」,不是「同一个 key 被两个通道写」。
2. **覆盖不到直接调用方**:nextday(`nextday_plan_generator.py:1182`)、intraday(`intraday_snapshot.sh:180/232`)、push_schedule_stats(`:73`)、fetch_news(`fetch_news.py:740`)、fapi_bj_width、kelly_intraday_rerun、s06、update_all、overfit_monitor(`:1995`)**全部直接调 upload_r2.py,不经过 async 单例**。报告里「10-22 async 单例 11 次跳过」说的是这些 async 批之间的互斥,与本次故障无关。
3. **它是批次级、不是键级**:即使两趟都走 async,它也只保证「不并发跑」,不知道谁写哪个 key。

> 一句话:**全局锁才是唯一的 key 级(其实是命令级)串行化机制;async 单例是上一层,兜不住。**

### 2.7 顺带说清:为什么不用 `--skip-if-locked`

现成的 `--skip-if-locked`(`:4192-4206`)是「拿不到锁就跳过 + exit 0」。对 nextday **绝对不能用**:
- nextday 的产物一天只生成一次,跳过后当天就**再没有第二次机会**(下一轮 10 分钟重试是 intraday 的语义,不是 nextday 的);
- exit 0 会让「数据没上传」变成**静默**(只打一行 `SKIPPED_LOCKED`),而现在是 severe 告警 + exit 1 —— **把响的故障改成哑的故障,是倒退**。

## 4. 方案 C(诊断):超时分支能看见「在等谁」

### 4.1 依据(文件:行号)

1. `nextday_plan_generator.py:1199`:`subprocess.run(cmd, env=env, capture_output=True, text=True, timeout=480)` —— **`capture_output=True` 把子进程 stderr 全吞了**,包括 `upload_r2.py:4267` 每 30s 的等锁心跳。
2. `:1212-1218` `except subprocess.TimeoutExpired:` 只 `log("⚠ R2 上传超时(480s, 将告警)")`,**一个字节的子进程输出都没打**。
3. 于是 10-22 只能从「480s 无返回」反推是等锁(报告 §7① 已诚实标注这点)。
4. 告警正文写「**R2 上传超时**」(`:1215-1219`),实际发生的是「**排队等锁超时**」—— 会把人引向「网络/服务端慢」的错误方向(报告 §5)。

### 4.2 改动点(3 处,全部是「只加输出」)

| # | 位置 | 改法(一句话) |
|---|---|---|
| C1 | `nextday_plan_generator.py:1212-1218` | `except subprocess.TimeoutExpired as e:` 里把 `e.stderr` / `e.stdout` 尾部 2000 字打进日志与告警正文(`subprocess.run` 在 `capture_output=True` 时会把超时前的输出挂到异常对象上) |

| C4 | `nextday_plan_generator.py:1215-1219` | 告警标题/正文改成说人话:「**上传前排队等锁超时**」+「一直占着锁的进程是 X,已等 Ns,本次只传 3 个小文件共 121KB」 |

## 6. 诚实标注(不确定项)

1. **「备份占 2/3」是模型推断,不是直接计时。** 日志没有分段耗时,我是用「10-09 基线的 473.8s 吞吐(589 KB/s)去反推 10-21 的备份段 947.8s,再验证备份搬运的 558MB/947.8s 恰好也是 589 KB/s」得出。两个独立算式对上同一个数,可信度较高,但**仍须 B-0 实测确认**;若实测备份占比 <40%,B-1 应停下重定位。
2. **10-22 到底是谁在 22:30–22:38 持锁,没有直接证据。** 日志不带行时间戳,nextday 的子进程输出又被吞(正是 C 要治的病)。现有证据链是:turnover 的 data-large 在 22:30:29 结束 + etf-hist 在 22:44:23 才拿到锁 ⇒ 中间 14 分钟锁被别的排队者占着。**具体是哪个进程,无法从现有日志确定。**
3. **R2 服务端 vs 云上出口网络未分离** —— 报告 §7② 已承认。所以「持锁时长恶化 2.5–5.4 倍」里有多少是备份、多少是链路本身变慢,只能靠 B-0 的分段计时拆开。
4. **`upload-data-files` 与 `upload-all-data` 的 key 重叠,我只做了代码层判定,没有实测两者真的在时间窗上重叠过。** 现实中 deploy 17:50 vs nextday 22:30 相隔 4.5h;真正会重叠的是 intraday 的 10 分钟一轮。要不要为此加 B0-1 的台账排除,需要用户拍板(它会给 all-data 引入新的「过期跳过」维护成本)。
5. **`_is_data_large_file` 的 1MB 阈值是「今天的」边界。** 如果哪天某个小文件涨过 1MB,A2 的闸门会自动把它退回全局锁(安全),但也就失去了 A 的好处 —— 这是刻意选的「安全优先」。
6. **B-2 的 multipart 会改变那两个 key 的 ETag 语义**(从 md5 变成 `hash-N`),`verify-r2` 是否真的按 Content-Length 判定,我只读了 `_upload_multipart` 的文档字符串(`:594-596`),**没有实跑验证**。用例 4 必须先 PASS 才允许上 B-2。
7. **本轮是纯只读调研,所有「预期」都未经实施验证**,按 §5.7 属于「方案」而非「已达成」。
