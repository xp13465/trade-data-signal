### 1.1 守卫设计(沿用同一判据、同风格提示)

判据 = 既有 `staticdata_write_guard.py --check-write-auth`(纯函数:`str(path).startswith("/home/ubuntu/")`),与 git 段(段2)调用**同一个脚本、同一 flag、同一 rc 契约**,不新起判据:

| `--check-write-auth` rc | 分支 | 行为 |
|---|---|---|
| 0 | 生产机(云上 `/home/ubuntu/…-staticdata`) | **原上传逻辑逐字节不动**(云上行为零变化) |
| 1 | 非生产机(mac/`/tmp`) | **默认跳过** upload-large-json(零 R2 接触)+ 降级 notify(`--tier` 默认,`--alert-issue` 写 latest.md,dedup 6h);逃生门 `STATICDATA_ALLOW_R2_UPLOAD=1` 才显式放行(覆盖写无「只增」闸门可套,故只给全量放行) |
| 2/其他 | 判定异常 | **fail-closed 跳过 + `STATICDATA_FAIL=1` + 告警** |

⚠️ **与 git 段 rc=2 刻意不同的取舍(请 reviewer 重点核)**:git 段 rc=2 走 L3 文档化的 **fail-open**(守卫 crash 时按生产机继续 best-effort,见 `staticdata_write_guard.py` docstring L35-38 + async L254-264)。R2 上传这里**明确否决 copy 该取舍,改 fail-closed**:R2 `large-json/<rel>.gz` 是**固定 key 覆盖写、唯一副本、不可逆**;守卫 crash 时无生产机判据,一旦 fail-open 就等于把「mac 覆盖正本」这条路在异常态重开。而跳过 R2 上传的代价极低(磁盘+git 留档仍在;生产侧下一轮 ETag 幂等补传),非破坏性。判据/风格与 git 段一致,仅**异常分支策略**不同,已在此显式记录。
