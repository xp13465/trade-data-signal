## 2. 新 helper 的暂存与重试语义

| helper | 语义 |
|---|---|
| `_load_email_pending()` | 读暂存账本 `{alert_key: alert_payload}`;缺失/损坏 ⇒ 空(降级不阻塞) |
| `_write_email_pending(p)` | 原子写;写失败 fail-loud 打印,**不另发告警**(防台账元噪声,plan §5 不变式5) |
| `stage_email_pending(alerts)` | 未达 ⇒ 暂存**整 payload**,按 `_alert_key`(`type\|kind\|name`)去重入账 |
| `retry_pending_emails()` | 账本非空 ⇒ 整批补发;成功 ⇒ 清账(`{}`);失败 ⇒ 保留再下轮 |
| `send_or_stage(alerts)` | 发邮件;未达 ⇒ `stage_email_pending`。返回是否真发出 |

**为什么存整 payload 而非 key**:`send_alert` 组装邮件 body 依赖 `a['desc']`(L303-307),
`desc` **无法由 `_alert_key` 重建** ⇒ 暂存必须存下整条 alert dict(任务硬要求②)。

**幂等保证(不重复弹前端 / 不重复落签)**:落签早在首次产出时已写;补发成功**不再触碰**
`anomaly_notified.json` ⇒ 前端源内容不变、不会重复弹(前端另有 localStorage 当日去重)。
`test_07` 轮3 显式断言「补发后落签内容逐位不变」。

**时点**:`retry_pending_emails` 置于 `main()` 顶部(**早于** `load_snapshot` 的 `return 0`),
故每次 detect 调用(随 `intraday_snapshot.sh` 30min 节奏、交易日盘中)都会尝试补发,不依赖今日快照。

## 6. 诚实标注 / 边界

- **跨日暂存语义**:账本不设过期(任务未要求,§6.5 少写抽象)。若邮件通道连续多小时不可用,未达 payload
  会跨轮累积,通道恢复后一次性补发(绝不永久丢失 = B 波不变式)。键为 `type|kind|name`(无日期),
  同标的同类长期只占一条。**未加过期 = 不引入未要求的行为**(§23.7),此边界如实标注供拍板。
- **staging 写失败**:唯一可致邮件丢失的路径(落签已写,前端不受影响);写失败 fail-loud 打印,
  不另发告警(不新增告警源,plan §5 不变式5)。
- **前端可见行为**:W3 **不改变**任何前端展示逻辑;它只保证「邮件通道故障时前端通知照常可得」。
  用户可见效果 = 邮件挂时前端仍弹 severe(修复前会一起静默丢失)。
- **与 W2 关系**:软依赖。detect 的 notify 调用**无 `--dedup-key`** ⇒ 无 suppressed 态 ⇒ 复用既有
  `notify_sent` 两态即可(未引入 `notify_state` 硬依赖),`test_16` 锁「判据仍复用唯一实现 notify_sent」。
- **§21 算法公示**: 本波**非算法变更**(无评分/权重/匹配/分段函数改动),不触发公示同步。
