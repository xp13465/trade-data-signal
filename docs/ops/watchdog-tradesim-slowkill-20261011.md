# upload-trade-sim 低速 kill 根因与治根方案(2026-10-11)

> 调研:researcher(只读,未改任何业务脚本);证据窗口 10-05~10-11(全部 r2_upload_async 日志)+ 实时 journal。
> 关联:`docs/ops/alert-triage-20261011.md` §2-B/§4-3(本报告修正其中两处事实)。

## 0. 结论速览

### 根因三层
1. **直接机制(为什么被杀)= 低速判据的「增量真空」在收尾阶段必然出现**:
   `r2_upload_async.sh:129-181` 低速判据 = 「连续 5 次 60s 采样、每次『日志字节增量』< 1MiB,且通道是 batch(`[N/M]` 的 M>10)」即 kill。
   「日志字节增量」只有两个来源:①文件**完成**行 `[i/M] ✓ xxx (sizeB)`(upload_r2.py:1019);②**≥8MiB 单 PUT** 的字节打点行 `↑ 上传中 … (deltaB)`(upload_r2.py:487-520,仅 L572-575 条件命中)。
   ⇒ 当 8 线程池的**最后一个文件**处于「发送末端阻塞 / 等响应」状态时,**5 分钟零输出是必然**(其余 7 线程早已空闲,没有别的完成行可产生)。
2. **梯度倒置(为什么杀早了)= 低速窗口 300s < 内层单请求超时 600s**:
   云上 `.env` `R2_UPLOAD_HTTP_TIMEOUT=600`(socket timeout,upload_r2.py:337)。内层对「卡住的单请求」设计有自愈链:**600s 超时 → 丢连接 → 退避 1/2/4/8s → 重试重发**(upload_r2.py:549/630-640,最多 5 次)。
   低速判据在 **300s** 就 kill ⇒ **内层的超时+重试(600s 才启动)永远没机会执行**。
   对照:停滞判据做过同款梯度修复(`r2_upload_async.sh:112-125`,#217②:900s > 600s,且显式防 `≤HTTP 超时` 倒置);**低速判据没有做——300 < 600,是 #217② 同源病灶在新判据上的重演**。
3. **放大器(为什么反复)= kill → marker 残留 → 下一轮强制全量 → 再遇慢链路再 kill**:
   kill 导致通道未完成,`.r2_trade_sim_html_uploading.marker` 残留(upload_r2.py:1302-1305 fail-closed 设计),下一轮 scan 到 marker → **强制全量重传 103 个文件 204.8MB**;叠加**周日 `weekday==6` 强制全量**(upload_r2.py:1381-1389),2026-10-11(周日)全天每一轮 deploy 都重复这条 204.8MB 的路径。

### 事实勘定(数据说话)
- **2026-10-11 两轮 kill 均精确停在 `[102/103]`(完成率 99%),trade-sim 从开始到被杀恰 17 分钟 = 12 分钟传完 102 个 + 5 分钟增量真空**(见 §2 时间轴)。
- **全历史低速 kill 仅 3 次,全部是「大批量通道 + 慢链路时段 + 最后 1~2 个文件真空」**:10-09 upload-index(158 文件,[128/158])、10-11 trade-sim×2(103,[102/103])。**不是 trade-sim 专属,是通用模式。**
- **kill 未造成 R2 数据缺口**:16:51 轮结束后 verify-r2 全量对账(18:23:49)只自动补传 2 个 news_digest 文件,**无任何 trade_sim 补传**(周日早些的 05:11 轮已全量成功、内容同版);state 文件停在 05:37 证明 kill 轮未写状态。
- **速率对照(同通道)**:成功轮 02:16=709.2s / 05:11=366.1s(凌晨,0.28~0.53MiB/s);被杀轮 16:51/21:16(傍晚,~0.27MiB/s 且末端单文件黑洞)。**时点差异是主变量,夜间成功率 100%、傍晚 0/2。**

### 「哪些是保护机制本该杀」——诚实判断
- 「5 分钟零字节流动」在 rclone `--timeout` / rsync / systemd WatchdogSec 的 IO-idle 精神下,**判死方向不算错**(真黑洞时该杀);
- **错在两点**:①**时机**——300s 时内层 600s 超时还没到,等于「每次 600s 级别的网络抖动都被杀」,自愈链被掐死;②**善后**——kill 后没有就近重试动作,只有「下一轮全量」这一种代价最高的恢复路径。
- 判定:**「杀」保留,「5 分钟」改「≥ 内层超时 + 余量」,并收紧「收尾阶段」的杀**。

### 首选方案(按默认准则取完整正确合集;改动全部在判据/告警层,不动数据口径)
- **P0-a1:低速判据窗口 300s → 900s**(与停滞判据同梯度口径;或按 `R2_UPLOAD_HTTP_TIMEOUT+300` 计算,沿用 L112-125 先例写法)。数学校验见 §5-a1:900s 恰好覆盖「600s 超时+退避+重试首行打点(~660s)」,重试恢复即清零;真死链由停滞判据(900s)+7200s 硬兜底继续守住。
- **P0-a2:收尾豁免**——batch 完成率 ≥ (M-2)/M(只剩最后 1~2 个文件)时,低速判据不 kill(改为落日志/告警)。理由:杀它 → 下轮 200MB 级全量;等它 → 最多一个内层超时周期。**全历史 3 次 kill 全部命中该条件,零误伤面。**
- **P1-d1:文档更正**(21:16 轮「静默」是误读,见 §3)。
- **P2-c1(需用户拍板,动语义):周日 full 的大批量通道(trade-sim/index)推迟到夜间首轮**(证据:凌晨 100% 成功 vs 傍晚 0/2;killed 的成本远大于延迟数小时的漂移防护)。
- **不建议本轮动**:b3 上行压缩(收益最大 204MB→约 40MB,但牵动 R2 对象编码/前端读取/CF 缓存/对账全链,单独立项评估);b4 multipart 阈值下调(23.9MB 仍小于单分片 64MiB,无增益);b5 加大并发(瓶颈是跨境带宽与单连接黑洞,非并发度,8 线程已打满链路)。

## 1. 看门狗判据与后果链(代码级)

### 1.1 低速判据本体(`scripts/r2_upload_async.sh:102-187`)

- L87-100:kill 前 `_dump_kill_tail` 把 tmp_log 尾部 30 行落主日志 + 累积 `R2_KILL_CTX` 供告警正文(#217③,事后定因)。

### 1.2 「字节增量」的两个来源(`scripts/upload_r2.py`)
- L1019:`_upload_glob` 完成行 `[done/total] ✓ rel (sizeB)`(as_completed 主线程打印;**文件在飞期间不打印**)。

## 5. 方案对比(带数据的取舍)

### a) 看门狗判据调整(推荐主方向)
**a1. 低速窗口 300s → 900s(首选)**
- 做法:`_low_bad >= 5` 改 `>= 15`(15 次 × 60s = 900s 窗口);或按梯度写法 `窗口 = max(900, R2_UPLOAD_HTTP_TIMEOUT + 300)`(与 L112-125 停滞判据同款口径,防未来再倒置)。
- 数学校验:内层自愈链周期 = 600s(超时)+≤15s(5 次退避之和,实际只到第一次重试)+ ~60s(重试后第一行打点)≈ **≤ 675s**;900s 窗口给足余量。且每次「超时→重试→打点恢复」都会让 `_upb` 增量回暖,`_low_bad` 清零——**只要内层还活着,900s 窗口不可能杀**;若 5 次重试全失败,自会走「✗ 失败行→通道 fail→对账告警」正路,**不需要外层低速兜底**(7200s 硬兜底仍在)。
- 风险:真黑洞场景杀得晚 10 分钟(600s)→ 可接受(停滞判据 900s 同量级);对「有打点行但增速极低」的通道,保护力从 5 分钟缩到 15 分钟——对照现网正常速率(0.27~0.53MiB/s=16~32MiB/分钟)与阈值 1MiB/分钟,真劣化通道仍会被抓。

**a2. 收尾豁免(首选配套)**
- 做法:采样时若 `_batch_total>10` 且**最近完成行 `[N/M]` 的 N ≥ M-2**(只剩最后 1~2 个文件),或 `_upb>0 且真空前 5 分钟内完成数≥M-2`,则低速判据不 kill(落一行日志「收尾阶段跳过低速杀」)。实现注意:`_batch_total` 现有逻辑已从 tail 取 M,需再取 N(同一次 grep);或退化成「超时前最后一次采样的 `_upb` 增速正常(前 5 分钟增量 ≥5MiB)」的「曾经健康」条件。
- 依据:全历史 3 次低速 kill **全部**命中「N/M ≥ 99%」;「98% 已传完、只剩最后 1 个文件慢」的场景,杀 = 100% 触发下轮全量 204.8MB,等 = 最多一个 600s 超时周期。
- 风险:若最后一个文件真黑洞且内层 5 次重试全败,靠失败行兜底(仍会告警);极端场景多花 ~50 分钟(5×600s)在通道尾——相对 7200s 硬兜底无冲突,且只在收尾阶段,不打穿通道预算。

**a3. 可观测性(建议顺带,低成本)**
- kill 尾部当前已有 30 行日志 + R2_KILLED 上下文;建议 kill 时额外落「本通道最后 3 分钟无新完成行、在飞数 = M-N」等一句话结论(数据已可算,仅落文本),_dump_kill_tail 里加一行即可。非必须。

### b) 上传侧优化(部分不推,一项单独立项)
- **b1. kill 后自动重试未完成文件**:复杂(需重新扫目录计算差集、重入 marker 状态机),且 a1+a2 后 kill 频率预计归零;**不推(留作 a1 失效时的兜底备选)**。
- **b2. photos/等响应打点**:`_ProgressBody` 刻意「只在字节流动时打点」是防「假活跃」(#180 设计),改成「等响应也打点」会同时废掉停滞判据的判死能力;**不推**。等响应 600s 内层超时兜底已经封顶,真正的解是 a1 让自愈链跑完。
- **b3. 上行 gzip 压缩**:204.8MB→约 40MB(html 压缩比 3~5x),能把「17 分钟窗口」压到「4~6 分钟」,**收益最大**;但牵动:R2 对象编码/`Content-Encoding`、前端读取链(static-site 与 CF 缓存行为)、对账(ETag/size 比对口径全变)、othello 兼容。**单独立项评估;本轮不动。**
- **b4. multipart 阈值/分片调整**:23.9MB 最大文件 < 单分片 64MiB,调阈值无增益;**不推**。
