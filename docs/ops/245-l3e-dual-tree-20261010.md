## 3. 切换瞬态处理(报告 §2.2-4)

**问题**:L3e 使告警去重文件单点化到**运行树**,而 py 侧历史 dedup 留在**代码树**不迁移 ⇒ 切换后 ≤6h 去重窗内,同 key 可能补发一次(低危但可一次性消除)。

**方案 = 一次性把代码树 dedup 合并进运行树(报告推荐项),已实施**:

新增幂等脚本 `scripts/merge_notify_dedup_trees.py`(dry-run 默认 / `--apply` 才写 / 备份 + 原子写 / 回读校验),云上执行证据:

```
# 1) dry-run(切换前,实测差异面)
[merge-dedup] run_keys=51 code_keys=52 merged_keys=64 added=13 updated=0 skipped=0
[merge-dedup] DRY-RUN: 将新增 13 键 / 更新 0 键 → /home/ubuntu/code/trade-data/data/notify_dedup.json

# 2) apply(备份 + 原子写 + 回读校验)
[merge-dedup] 已备份原文件 → /home/ubuntu/code/trade-data/data/notify_dedup.json.bak-20261010-132530
[merge-dedup] 已写入 /home/ubuntu/code/trade-data/data/notify_dedup.json(64 键)
[merge-dedup] 回读校验: post_keys=64 mismatch=0 PASS

# 3) 独立复核(不采信脚本自述)
post_run_keys 64   sig_keys 52   mismatch 0   sig_only_now_in_run 0

# 4) 幂等复跑(第二次)
[merge-dedup] run_keys=64 code_keys=52 merged_keys=64 added=0 updated=0 skipped=0
[merge-dedup] 无变化(幂等: 两树 max 已一致), 不写盘
```

**规则说明**:每 key 取两树 `last_alerted` **较晚**者 = 更保守的抑制(**绝不可能造成「该发而未发」**);`updated=0` 是因为 8 个交集差异键在信号树侧全部**更旧**(如 `deploy_r2_upload_fail` 运行树 10-09 17:35 vs 信号树 09-23),取 max 后运行树已是最新。13 个新增键 = 报告 §1.5 的「信号树独有 13 键」(nextday_gap_check_gen_fail / nextday_plan_*(4) / nextday_plan_gen_fail / daily_brief_notify_*(4) / sigkelly_snapshot_stagnation_ / verify_r2_mass_mismatch / verify_r2_standalone_stale)——**数字与报告 §1.5 逐键吻合**。

**关键时序(诚实标注)**:本脚本幂等且**切换前后各跑一次即终态**。当前已跑一次(切换前);**切换后需再跑一次收尾**(届时代码树不再新增,第二次即 `added=0`)。命令:

```bash
python3 scripts/merge_notify_dedup_trees.py \
  --run-tree /home/ubuntu/code/trade-data --code-tree /home/ubuntu/code/trade-data-signal --apply
```

**恢复路径**:`cp /home/ubuntu/code/trade-data/data/notify_dedup.json.bak-20261010-132530 /home/ubuntu/code/trade-data/data/notify_dedup.json`。
