### 1.2 有没有重叠/边界模糊?——两处模糊,各有实际后果

**(a) reviewer ↔ tester(中度重叠,文本级实锤)**:两个 agent 定义各自认领**同一批职责**:
- 冒烟测试:reviewer.md:15"读 docs/smoke-checklist.md 跑 P0 冒烟测试" vs tester.md:13"跑回归冒烟测试(P0/P1 主功能点,读 docs/smoke-checklist.md 执行)"——同一清单,且双方材料都把 role skill 的同一节列为自己的职责(两侧列举的节名都是"冒烟测试清单执行")
- 数据校验:reviewer.md:16"C 级(数据/后端)改动:数据完整性校验(check_data_integrity.py)+ 一致性(§22,本地 static-site/R2/CF 三处同值)" vs tester.md:14"数据产物完整性校验:check_data_integrity.py+ check_r2_consistency.py"+ tester.md:16"数据一致性(§22):多展示位/多文件/多缓存同值校验"——措辞不同,实质同一批职责
- **实际后果**(为什么这算问题):两个节点都能做→派单时主控按心情选→①重复劳动(同一改动两关都跑全清单)或②悬空("我以为对方会跑");且近 60 天 reviewer 提及 129 次 vs tester 17 次(2,639 个 commit 主题行,`git log --since="60 days ago" --oneline | grep -ci` 口径)——**重叠职责在实践中全部滑向了 reviewer**,六道关"审查∥测试并行、两关都过才放行"的设计(flow:13)在角色材料层没有对应的差异化指令支撑(六道关只在流程文档里,skill 里没有"我该查哪一半"的切割)。
- 六道关的设计意图是对的(④影响面+边界独立复核 / ⑤事实层+数据校验),但**没落到 skill 文本**——④才写进 reviewer skill §10.8、⑤才写进 tester skill §5.3.1,而旧的"冒烟+数据校验"两个重叠段一直留着。

**(b) implementer ↔ mech-runner(边界有判据,但注入错配)**:
- 判据清晰且写在明处(mech-runner.md:13-14"步骤明确、结果可机械核对、无判断空间";"需理解口径/判断跨文件影响/算法与公示同步/根因定位→归 implementer;遇到就停报主控")——**这点做得好**。
- 但两个节点**共用同一份 role-implementer skill 全文注入**(mech-runner.md:6-7 `skills: [role-implementer]`),39,318B 的重型规范(含 R2 架构准则/7 级写码阶梯/公示同步/R2 哨兵事故史)灌给一个 effort=low 的机械节点,**注入面与其定位错配**:它被要求"不判断、遇判断点停报",却又被要求"触碰前端源码/数据产物时不豁免 §21/§22/§24"(mech-runner.md:28)——而这些豁免判断正是它自认无法做的。
- 张力有本体系自证的数据背书:implementer skill §0 引 benvanik 数据"thinking 降致约定遵循违规 0→173 次",而 mech-runner 是低档路由——**长规范对它的遵循率是更低的**,却给了它最多规范。

**(c) 其余相邻边界(researcher↔reviewer↔主控)清晰**:researcher=只读出结论,reviewer=只读批判,tester=只读核事实,三者 tools 清单实锤(都没有 Edit/Write)——生成/验证分离贯彻干净。

### 1.3 5 节点对"一个主人 + AI 军团"是多是少?——数量合适,利用率不均

- **不为多**:业界职责分离(SoD)的经典形态是 3-4 个互斥角色(NIST 定义"任何人不得拥有足以独断滥用的权限"),本体系 5 节点覆盖了 4 个专业职能(构建/批判审查/情报调研/事实核查)+ 1 个性价档位(机械执行),**每个节点都能在 52 条台账里指认到自己的失败族**(见附录——无失败族支撑的空节点才是多余节点,这里没有)。节点数 ≈ SoD 上限的合理值。
- **问题在两处不均**:①reviewer 过载(129 次提及,承担了冒烟的重复职责)②mech-runner 渗透率极低(3 次提及,2026-10-07 上线以来实际用量小)——**节点建了但路由习惯没养成**,和"砍掉"是两回事(见建议菜单 M5)。
- 对照上一份系统评鉴的"单主人依赖零缺席预案":节点层无解,那是调度层的账(本报告呼应,不重复)。

## 四、维度④ 协作与信息设计

### 4.1 交接物格式纪律——做了两层,缺一层"统一遥测底账"

- **好**:派单侧有 §16 锚点规范(必带 `@文件:行号`,shared §8.1)+ 三件套机检(hook);回报侧有"结论+证据点,全文落档不贴回"(§5.5③);实施方报告必带 base commit/版本串(§15.2 回归口径);reviewer 报告有 §10.2 置信度过滤。**"写什么/不贴什么"是有纪律的**。
- **缺**:跨关交接物**没有统一 schema**——需求关产出(需求卡)→方案关三件套→实施关清单→审查关发现→测试关结果,各自格式散在 6 份文档里;**没有任何一处登记"本次任务走到了哪一关、各关证据在哪"**。现在的替代品是 TASKS.md 交接日志+progress 文件,粒度是"人肉日记"不是"关卡台账"。后果:上一份系统评鉴的"台账漂移"在节点层有一个投影——**跨关状态靠聊天记录与运气**。

### 4.2 信息不对称设计——亮点与破洞

- **亮点(全报告最值得保留的设计)**:§10.8 "reviewer 先不看实施方边界清单,自己再推一份,再对账"——双向独立推导后对账,**强于业界普通四眼原则**(四眼是"两人都看同一份";这是"盲推+对账",编造清单者会露馅)。同族还有 §5.4⑦ 页面实测锚点(禁预设用户记错)。
- **破洞**:①该设计的输入端(实施方清单)不存在(缝①)→ **不对称的两只脚只有一只**;②"信息不对称"只用在审查关,测试关没类似机制(tester §5.3.1②"清单受独立复核"沾边但无"先不看"字样——实测 grep "独立复核"在 tester skill:119 有,但盲推对账的强度未对齐);③观察锚点回核本可设计成"第二数据点由非实施者取"(天然信息不对称),现在无人承接。

### 4.3 丢信息/重复劳动的缝(点名三处)

1. **冒烟+数据校验双 claim**(1.2a):重复劳动或悬空,二选一必发生——实况是全部滑向 reviewer(129 vs 17),tester 的事实核查面被闲置。
2. **L48/L49/L50 的教训只活在 §18 滚动窗**(15 槽):给 reviewer 的三笔学费放在"迟早被挤出"的窗口里,**无纵深载体**——这就是"丢信息缝"的具体形态(见 B1)。
3. **mech-runner 的"适用判据"只有人读版**:主控每次派单都要人肉判断"这活有没有判断空间",无 checklist 化(如"命中以下任一即不派:含口径/含跨文件/含算法/含根因"已在 prompt 里但无机检、无复盘)——判据存在但零摩擦保障。

## 八、(加分)外部对照

**领先处**:本体系的"生成/验证分离"与业界职责分离原则(SoD,审计/DevOps 领域数十年沉淀:"任何人不得拥有足以独断滥用的权限",NIST 定义)一致,且做得更细——reviewer/researcher/tester 工具层物理只读 + §10.8"先不看实施方清单再独立推"的盲推对账,强度超过普通 four-eyes(四眼=两人看同一份;盲推=两人各自出清单再对账,能暴露"清单造假/漏推")。对照 Anthropic 多 agent 研究系统的经验(orchestrator-worker 模式:多 agent 比单 agent 研究任务提升 90.2%、token 消耗 15x、**性能方差 80% 由 token 用量解释**)——本体系用"节点分工+注入规范+机检"压低方差的路子与之一致,且把"角色成本路由"(mech-runner low 档)作为节点身份内置,比统一高档位更省。

**落后处**:①业界 SoD 强调**互斥角色须显式声明互斥**(谁不能审谁、什么角色禁止兼任),本体系 reviewer/tester 职责文本重叠(冒烟+数据校验双 claim)且无互斥声明——**重叠在 SoD 里等于"可兼任",会破坏独立性**(B4);②MAST 多 agent 失败分类学研究(arXiv:2503.13657,分析 200+ 任务发现 3 大类 14 种失败、~75% 失败率)结论:多 agent 系统失败主因是**协调结构缺陷而非单体能力**,且"提示词干预只带来 +15.6% 改善,结构修复才是关键"——本体系的假绿族(12 天 3 次,L49/L51/L52)恰是"修法停在纪律层(≈提示词)未做结构修复"的实例,对方验证:应把 L48/L49/L50 类检查做成"审查工具前置条件"结构(M6);③LLM 自验证研究(arXiv:2607.28908 反思增益 ΔI≈0;arXiv:2609.07680 "Audit Without Verification"——审查者倾向转述而非独立检查)从反面印证:本体系要求 reviewer"独立取证、置信度过滤"是对的,但**"谁验证验证者"必须靠结构(打桩证据/真实样本/盲推),不能靠审查者自觉**——同 M6。
