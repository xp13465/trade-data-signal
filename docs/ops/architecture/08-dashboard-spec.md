# 私有运维监控面板规格（设计稿，未接入实时采集）

本文件定义拟议面板，不表示已有实时平台或监控已经覆盖全部项目。现状入口和可复用数据源见06-deployment-and-surfaces.md；规则现状见04-monitoring-and-alerts.md。本次默认仅用户和维护者可见，公网健康页另行设计，不公开任务路径、主机、内部错误正文或通知目标。

## 一张面板回答的六个问题

1. 哪个业务结果受影响：数据/信号/交易计划/发布/页面/备份，而不是只看进程是否存在。
2. 哪一批应该完成、实际完成到哪里，前置输入的业务日期和版本是什么。
3. 是任务没执行、执行失败、执行成功但数据不完整，还是发布/缓存没有跟上。
4. 同一故障影响哪些下游；同一原始事件的多渠道通知是否已经关联。
5. 谁在处理、依据哪个固定版本和报告、还缺哪项验收，何时能认为恢复。
6. 页面和采集证据是否过期；证据不够时显示未知，不自动报健康。

## 信息结构

| 页面 | 主要内容 | 下钻与验收 |
| --- | --- | --- |
| 总览 | 业务能力影响、证据更新时间、未验证状态、当前发布批次、处理中事项 | 点击业务能力进入其输入→任务→产物→服务路径 |
| 服务 | 主机/运行单元/执行位置、运行状态、端口或入口、代码与部署版本 | systemd/launchd（launchd 已废弃/历史存档，生产定时任务已迁云上 systemd timer）状态与实际服务探测分开；显示观察来源 |
| 任务日历 | 预期窗口、上次/下次触发、运行时长、锁等待、超时、重试和跳过原因 | 日历按任务时区及交易日规则判断；手动和停用任务分列 |
| 数据资产 | 权威路径、生产者/消费者、业务截止日、完整性、冻结与映射批次、文件身份 | 检查实际消费者可读性和原事件成员，而非仅文件mtime |
| 发布 | 代码ref、数据批次、输入清单、上传/远端校验/CDN/站点生效阶段 | 单独展示上传、校验、purge和最终可见性，不能合并成一个成功位 |
| 告警/事件 | 首次/最近出现、状态、分类、同源关联、影响范围、责任和报告 | 原告警、渠道投递、当前检测、修复验收四者分开 |
| 问题与根因跟进 | 原工单/finding、修复/部署/验收/观察/根因措施多轴状态 | 原证据、固定版本、关闭条件、最后复核时间；不能用completed替代根治 |
| 备份恢复 | 最近可验证备份、覆盖资产、校验、恢复演练时间、保留策略 | 备份存在/上传成功/可恢复分别验收；检查非DB关键输入覆盖 |
| 架构/知识库 | 本次图谱、清单、对账差异、运行手册、变更记录 | 同一对象id连接清单、图、面板和事件，拒绝另一套人工名单 |

## 状态模型（拟议）

- `unknown`：未采集、证据过期、来源冲突、接口失败或缺少必要校验。灰色；不会因0条告警亮绿。
- `not_due`：本窗口按交易日/日历不应执行。明确标记，不是业务恢复。
- `scheduled` / `running` / `waiting_dependency` / `waiting_lock`：运行过程状态，不等于结果健康。
- `failed`：本项必要条件被本轮证据证实未满足；展示失败阶段、影响及原证据。
- `degraded`：有可验证降级结果或部分能力受影响，标注降级范围，不把缺关键数据包装成成功。
- `healthy`：在有效时间窗口内，业务结果必要条件全部验证通过；子项缺证据时不得聚合为全绿。
- `historical_unreplayable`：历史证据缺失的审计处置，保持原事件和依据，不能按普通恢复关闭。

对象健康、运行状态、事件处置状态分开存。既往failed unit记录不等于现在服务不可用；ack/completed不等于上线或恢复；业务过拟合风险不和系统故障用同一清零目标。

## 最小采集合同（拟议，优先复用现有产物）

每个观察携带object_id、observed_at、source_time、business_date、expires_at/有效窗口、source_kind、source_ref、evidence_uri、result、reason和采集器版本。没有可比证据的字段保持null及原因。

每次任务使用run_id、task_id、trigger（timer/manual/retry）、scheduled_for、started_at/ended_at、input_refs、output_refs、exit_code、business_checks、lock_wait、retry和skip_reason。不能把未执行的下游步骤写成成功。

每个数据批次携带代码ref、权威输入身份、信号业务日期、冻结时实际使用的映射/规则版本及校验结果。仅有日期文件名或当天pre-build快照不能证明冻结所用映射。

每个发布批次链接本地manifest、上传尝试、远端proof、CDN/站点校验与缓存状态。一个阶段未知，不推断下游成功。

每个事件携带event_id、rule_id、object_id、run_id、first_seen/last_seen、影响、检测证据、delivery_attempts、triage、owner、修复版本和verification。相同根因可关联多条症状，但原始记录不能被合并丢失。

## 数据接入与权限（后续实施）

先对齐现有schedule_stats、数据缺口检查、通知台账和发布/备份证据的字段与覆盖，再按缺口增加最少采集。知识库只存资产定义、数据合同和来源；时序观察另存，不把Git文档当实时状态数据库。

实时采集器遵循只读、超时、数量/字节预算、源端权限最小化；首版控制面仅浏览，不提供一键补采/删冻结/reset failed/deploy/改阈值。后续操作入口必须单独授权与审计。

接口/页面故障时保留最近已知值并显著显示其时间与过期状态；采集器失联自身必须成为可见状态。私人原始日志与脱敏知识库分离，凭证只通过既有安全配置传递。

## 分阶段交付与验收

1. **本次：静态基线与对账**。结构化清单、真实运行快照、架构图、未知与漂移、此规格。离线预览只表示盘点数据，不是实时服务。
2. **Claude复核后：接入现有观察**。实现私有只读API/页面或复用现有运维视图，逐对象绑定同id与证据新鲜度；采集失败必须变未知。
3. **补监控缺口**。按业务优先级增加消费者可读性、实际事件成员、发布proof、冻结批次和备份恢复证据，避免重复扫描全库/大文件。
4. **真实周期验收**。至少覆盖成功、失败、重试、正常跳过、锁等待、晚到数据、采集器失联和证据过期场景；不为了测试真实重复发信或重跑生产任务。
5. **维护闭环**。配置/入口/数据产物变化同步清单和图谱；由Claude维护实施与部署，Codex独立核查现状和验收证据。

本文件不承诺未实施的系统已运行，也不以新增监控数量或告警归零作为业务稳定的验收。
