## 0. 一句话结论

**这是把「生产事故驱动的个人经验」工程化得相当深的一套治理体系——长板极长、短板清晰,且体系自身正在变重。**

- **长板:能机检的错误基本治住了**(派单、部署撕裂、git 静默、删除不可逆等事故族机制化后未再复发);「错误→条款→机检」的升级阶梯、「方案=可证伪承诺」、「两个数据点才算立住」等设计在业界属先进,值得蒸馏推广。
- **短板:不能机检的语义纪律在反复复发**(假绿族 12 天复发 3 次;公示同步自注已复发 2 次),修法全部停在"纪律"层;而且**体系对自己的账本(错误台账/记忆索引)反而没做机检**——账已经漂了(归档实际 50 条 vs 声称 49 条;声称的"按归属 5 类分节"根本不存在)。
- **主要风险**:①单主人负荷无计量、无缺席预案(核心文档里「拍板」22 处、「上报」34 处,全靠主人);②规范瘦身后 11 天又涨 18.4%,只有加法没有减法的路径。继续原样用,"维护规范本体"会逐年吃掉它带来的效率。
- **打分:7/10**。有效、可学、当真;但需要一次"减重 + 补盲 + 给机制上保险"的手术(见第 5 节 10 条建议)。

## 2. 好点清单:最值钱的 5 个设计

### 好点 1(最值钱):错误台账 + 「机制阶梯」

每错一条记「根因 + 防重犯条款」;同类复发不新开条、要强化原条款;**被违反 2 次以上 = 条款无效,要重写或升级成机检**。
为什么值钱:①把每次事故变成永久资产(不是一次性道歉);②内建"升级"路径——重复犯错自动触发机制化,L01 二次复发直接催生了 hook 机检三件套(CLAUDE.md L25);③罕见地诚实:推翻过的方案、假数字、三次没修好的记录全部留痕可反查(§5.4⑦「旧假数保留可反查」)。业界很多团队有 postmortem,但做不到「复发即升级机制」这条闭环。

### 好点 2:把「自证陷阱」当结构问题拆

执行/审查/测试分不同上下文;reviewer **先不看实施方清单、自己再推一份边界清单对账**(reviewer skill §10.8,L203);事故后「独立取证,不采信自述」(L50 防再犯④)。
这条路与外部研究一致:LLM 对自身输出有系统性自偏好偏差,换独立上下文让模型"看到不同的东西"是主流缓解法(Anthropic context engineering、LLM-as-a-Judge 综述)。**它没有停在"换个 agent 复核"的表面,而做到了"信息不对称的双向清单对账"——这是真正稀缺的设计。**

### 好点 3:「方案 = 可证伪的承诺」(§5.7,CLAUDE.md L98)

三件套:可修正依据(文件:行号/实测数字)+ 可观测预期(X→Y)+ **事先写定**的证据用例;对不上 = 方案失败,不许"完成度打折"。
为什么值钱:等于把科研的"预注册"搬进工程——让"为了改而改"在上线前就暴露,事后验收不用吵架(跑用例即可)。与 spec-driven development(spec-kit verify 环节)同精神,但 sugas 版更狠:连证据用例都要求**事先**写定,且写不出预期/用例的只叫"建议"、不许当方案实施。

### 好点 4:四句口诀 + 三查清单 + 「两个数据点才算立住」

「报完成≠真完成 / 配置对了≠生效了 / 代码在主线≠功能上线了 / 检查全绿≠真没事」——四句话各自对应血案,短到能背、压力下想得起来。配套「上线三查」(主线含提交/数据层生效/展示层真上线)与观察锚点(「等它自然跑一轮,两个数据点才算治住」)。
为什么值钱:口诀是行为层最后一道防线——机制会漏(通知会丢、探针会挂),人还能背口诀兜住。实例:L45(S06 快照缺每日重生)正是被"状态型功能要问『谁每天更新它』"抓住的。

### 好点 5:把多 agent 协作当「分布式系统」来治

通知会丢(实测 task-notification ~96% 丢)→ 巡检 cron 兜底;agent 会卡死 → 转录 mtime 判活;写并发 → worktree 隔离 + hook 机检;merge 事故 → main-merge 统一入口 + CI 自检 + 哈希校验;数据多展示位 → §22 一致性机检清单。
这是不多见的把"AI 军团"的不可靠性当成工程问题(而不是提示词玄学)来处理的实践;且全过程保留"诚实修正"传统——如 cron 兜底的"为什么"里写着"曾误判 notify.py 为标准方案并实施,调研穷尽后推翻"(main-governance.md L54-55)。

## 3. 成本与可持续性:数字说话

### 3.1 启动税(每会话固定成本,估算)

- CLAUDE.md **61,533B**(≈1.37 万汉字)——注入每个会话(含所有子 agent;本评审 agent 自己也被注入了);
- MEMORY.md 索引 **30,585B**——每会话注入;
- 角色 skill 全文注入(确定性设计,启动即全量):implementer 39,318B / reviewer 32,031B / tester 19,094B / researcher 16,654B。
- **估算**(方法:实测 CJK 字符/字节数 × ~1 token/字,已标注为估算):主控会话开局 ≈3-4 万 token;一个实施子 agent ≈3-4 万 token。这是固定税,每派一个 agent 交一次。
- 对照:蒸馏 skill 反而轻——SKILL.md 2,067 汉字 + REFERENCE 11,446 汉字,是整套体系里"成本控制得最好"的产物。

### 3.2 规范本体维护成本(实测)

- 近 5 天(10-14 至今)全库 **108** 个提交里,**63 个(58%)** 改动 `docs/` 或 `.claude/skills/`(含业务分析文档,不能全算治理成本,但治理/落档文化占比之高肉眼可见);其中直接改 CLAUDE.md 的提交 5 个(按 --since 口径;10-14 当天另有 3 个按作者日期计入)。

- 蒸馏版 skill 同趋势:v1.0→v1.1 一个复查周期 +10 条新条款(SKILL.md L61),REFERENCE diff +45/−19;
- 台账归档 201 行 / 2.5 个月;`docs/ops` 已积 **462** 个条目;memory 目录 **256** 个文件;docs 根目录 95 个 md。

### 3.3 总判断

成本结构 = "前期重、边际还算便宜":绝大多数成本发生在"记录与机制化"那一刻,日常执行靠条款自动运行。但**三个趋势值得警惕**:①条款只加不减(见 W2);②每会话固定税缓慢上升;③"改动规范/写报告"在提交时间分配里占比不低(58%),存在"治理吃生产力"的苗头——尚不严重,设一个预算上限(建议 P3)即可控制。

### 3.4 过度工程 / 可轻量化的具体候选(指名)

1. 巡检三层冗余(prompt 纪律 + hook 机检 + 15 分钟 cron)对单人场景可评估压成两层;
2. `docs/ops` 462 条 + docs 根 95 个 md 的报告文化,建议设"季度合并归档"动作;
3. "18 处登记点"式人工同步清单应全部转机检(§22 自己已有此要求);
4. REFERENCE 全量版要求"新会话全文贴"(11,446 汉字=每会话税),宜拆"10 条必读 + 按需全量"。

## 4. 弱点清单(关键交付:8 条,每条带证据)

### W1. 系统对自己的「账本」没有机检——台账漂移已实际发生,且违反了它自己的 §22

- **账不对**:CLAUDE.md L139 两处不实声明——①「49 过错」+ 归档 L113 表头也写「49 条,与根索引表 #1-49 一一对应」,但 `grep -c '^L[0-9]'` 实测 = **50**;②声称「全量 49L+30E 锚点见归档文件末尾『防重犯锚点索引』块(**按归属 5 类分节**)」,归档里 `grep "按归属"` = **0 命中**,锚点块是扁平列表(归档 L113-201)。
- **账不全**:CLAUDE.md 自己标 L50/L51/L52「未单独归档」;2026-09-07 商汤 8899 误杀生产事故(implementer skill L174,靠 KeepAlive 自愈)在归档里查无此案(`grep 商汤` 唯一命中是 L47 另一件事;`grep 误杀|8899|KeepAlive` = 0)——没进账。
- **无机检**:scripts/ 中未找到对台账计数/锚点一致性的检查脚本(检索方法见第 7 节)。
- **为什么严重**:§22 明文要求「同一事实多处副本必须机检」(v1.1.5 切 NEW14 曾因漏一处登记点出事故),§21 也是同类病根;**体系要求数据层一致性机检,却在知识层(它最重要的资产)用人工维护的数字**。而且这个坑在它自己的记忆索引上已经真实炸过一次:2026-09-27 瘦身时发现「索引掉行和有意精简长得一模一样」,**42 行掉行中 17 条是有效活条目,5 周无人发现,只有拿旧备份对账才撞见**(memory-index-compression-20260927.md L21)。台账比记忆索引更重要,同样的保险还没上。

### W2. 「精简-膨胀」棘轮:只有长条款的路径,没有减条款的路径

- CLAUDE.md:3,267B(07-14)→ 51,989B(10-07 瘦身)→ **61,533B(今,11 天 +18.4%)**;MEMORY.md:26.0KB(09-27 瘦身)→ 30,585B(今);skill v1.0→v1.1 一个周期 +10 条。
- 结构问题:§5.3「精简保核心」保护的是**被删对象**,**没有任何一条规范规定「谁在什么时候删/并条款」**;错误必进账、条款只加不减、「被违反 2 次的条款」也只是重写不是退役;台账 L1-L49 从未被复审过。
- 判断:这是最可能长期侵蚀效益的因素——**每一条新条款都是永久的每会话税**。

### W3. 单主人依赖:拍板/上报合计 56 处,缺席预案 0 处

- 实测(4 份核心文档):「拍板」**22** 次、「上报」**34** 次、「验收口径」**35** 次。主人是唯一决策队列、唯一 merge 授权方、关键第三方锚点之一。
- `grep 主人不在|休假|主人病了|主人忙|缺席` 在 6 份核心规范 = **0 命中**——没有任何降级模式。
- 流程文档自己承认残余的人依赖:pre-release-quality-flow.md L89 已知弱点表——「差集『不测』的处置是否真的合理,**最终仍靠人判**」。
- 外部对照:单维护者研究(BurnRiSc, arXiv 2609.19422)把「无界需求 + 没有上级帮你分流 + 没人注意到状态下滑」列为烧尽最坏组合——AI 军团恰好放大了"无界需求"("主人愿意等、穷举最大化"),而体系度量了项目的一切,**唯独不度量主人自己的负荷**。"卡住上报、宁可停"的纪律在主人忙/累/病时会把体系变成"全系统等主人"。
- 定性:单人治理天然如此,但**零缺席预案**在长期视角下不可持续(见建议 P4)。

### W4. 「假绿」类失败 12 天复发 3 次:验证器自身没有被兜底,机制也没有生命周期

- L49(10-06 假样本养绿:测试喂了现实中不存在的样本字段)→ L51(10-15 时敏测试:引入当天绿、次日必红)→ L52(10-18 源码形状守卫:pytest 全量未跑,主干 CI 确定性红一天)。三次形态不同、族相同:**"检查全绿 ≠ 真没事"**。
- 更微妙的是 L52 暴露的新问题:**被建来防错的机制(测试守卫)自己变成了新故障源**——没有任何条款规定"一条机检什么时候会过期/误伤/该退役"。L50 同族:审查探针 harness 门控写错,差点真执行生产脚本 2 分 16 秒(唯一副作用=缓存文件被覆盖;事故"由主控巡检兜底 cron 逮到"——兜底有效,但本体是"工具层自证失败")。
- 现状防线(red-first 自检/冻结运行日/边界穷举)全是**纪律条款**、不是机检。预判:该族还会以新形态复发,下一个形态大概率是"机检脚本自身失效/误伤"。

### W5. 共同错误前提下,六道关可全链失守——防护是纪律不是机制

- L44(08-24,has_track 口径 P0):需求记录错 → 挖掘继承 bug → 实施照单执行 → reviewer 在闭环内失守,全链无人对照 UI 文案,「机检全绿卡不归零」。
- 修法是 §23.13 三源核对(UI 文案/产品文档/代码现状)——正确,但仍属"要求人去核对";若三源本身同错(用户口误+文档旧版),体系没有第四道兜底。理论上界:**验收 PASS 的可信度 ≤ 前提的可信度**,而前提检查靠人。
- 同族变体:L42(UI 视觉问题三次声称修好实际零变化,第四次才成功)——"人定的检查标准本身错了,机检照绿"。

### W6. 挂具/模型特定条款占比不低,且没有「退役期」

- **挂具特定**(补偿当前 Claude Code/Agent 平台缺陷):派单三件套 + 巡检 cron(因通知实测 96% 丢,governance 自注"架构限制下最优残余")、worktree 隔离、子 agent 拿不到 TaskStop、后台化残留上报、15 分钟轮询节奏、thinking/effort 档位配置……平台修好通知机制后,这些全部变成纯税。
- **项目特定**(换项目不成立或需改造):交易日/生产时点窗口、R2/CF 部署链、§22 多展示位一致性、ETF/凯利业务条款、双仓开源(数据 CC BY)。
- **永恒方法论**:证据优先、可证伪方案、删除先备份、不静默、独立验证、错误即资产、"两个数据点才立住"。
- **估算比例**(判断,标注为估算):挂具补偿 **~25-35%** / 项目特定 **~15-25%** / 永恒 **~45-55%**。风险不在比例,而在**没有退役机制**——挂具条款写完即永久驻留,"可逆精简"反而变成不敢删的心理锚。
- 点名:REFERENCE 的"通知可靠性三层兜底""15 分钟巡检节奏"等宜标「挂具条款·平台通知修复后复审」;SKILL.md 第 4 条(定期迭代)已留口子,但没有**期限**。

### W7. 蒸馏 skill 只有「意见层」,没有「执行层」——而源系统的精华一半在机检

- 实测:`/tmp/sugas-dev-draft/` 只有 2 个 .md,**零脚本零配置**;而源系统的机检本体 = agent_dispatch_cron_reminder.py(156 行)、main-merge.sh(632 行)、ci_selfcheck.sh(189 行)、deploy.sh(1040 行)等。
- REFERENCE 4.3 把"能机器查的,变成自动闸门"列为铁律级机制——**恰恰这一半没打包**。换项目/换机器,拿到的只有纪律没有闸门,对新项目等于退回"裸人肉执行"。
- 佐证:SKILL.md 用法要求"新会话全文贴"——靠提醒生效,不靠机制生效。这本身不算错,但应诚实标注「本 skill 不含机检脚本,机检请按 REFERENCE 4.3 自行补建」,或直接附 1-2 个最小可运行检查(如台账对账、exit0 检查)。

### W8. 覆盖盲区(四类,有 grep 实证)

- ① **法规/合规/隐私/供应链**:6 份核心规范 `grep 隐私|许可证|供应链|版权|越权|Terms of Service` = **0 命中**;蒸馏版 REFERENCE 只有"凭据不回显/密钥安全"一处安全底线(凭据 2 处、密钥 2 处),隐私/许可/供应链/版权 **全部 0**。对一个采集第三方数据、双仓开源(MIT+CC BY)、持有生产凭据的个人项目,这是最大的未覆盖域。
- ② **探索型/创意型任务无通道**:SKILL.md + REFERENCE 中 `grep 探索|试错|原型|spike` = **0**;核心文档里的"探索/试错"命中也是反义(如 §5.5"防无限探索"、L174"不试错")。体系只有"可证伪承诺/先验证再动手"一路——对生产极好,对 R&D/早期项目/未定型需求太重。
- ③ **对外协作未适配**:仓库对外公开,但规范假设"主人+AI"闭环:无 CONTRIBUTING/行为准则/外部 PR 处理路径/安全报告渠道。
- ④ **AI 成本治理浅**:有省 token 方法(§5.2/§5.5/§5.6),但没有预算/上限/账目——花多少、超没超,无数字可见。

### (附)弱点侧的一个诚实说明

上述 W1/W4/W5 恰恰说明这套体系**允许被批评并记录失败**——归档敢写"机检全绿卡不归零""三次声称修好实际零变化"。这一点比多数工程团队强。批评的价值在于:它的失败模式已经收敛到清晰的几类("不可机检的语义纪律"+"账本自身失检"),是可以被针对性治住的。

## 6. 外部对照(业界同类实践)

### 段落一:与业界在哪里独立收敛、sugas 领先在哪

这套方式与业界前沿多处**独立收敛**,且有三处真领先。
① Anthropic 官方关于 context engineering 的工程文章讲的"上下文会腐烂、独立上下文的子 agent 让同一模型'看到不同东西'、从而机制性缓解自评偏差",与 sugas"执行/审查/测试分上下文 + 独立再推边界清单"同源同向(https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents;https://claude.com/blog/using-claude-code-session-management-and-1m-context)。
② GitHub spec-kit 的"宪法 → spec → plan → tasks → implement + verify"流程,与 sugas 的"需求→方案→实施→(审∥测)→上线→观察"高度同构(https://github.com/github/spec-kit/blob/main/spec-driven.md);SRE 的 blameless postmortem"系统原因而非人责"文化与 sugas 台账同精神(https://learn.microsoft.com/en-us/training/modules/manage-site-reliability/6-blameless-postmortem)。
③ sugas 的**独有增量**:"同一错复发≥2 次 = 强制重写或机检化"的**机制阶梯**(业界 postmortem 普遍有 action item,但自动升级机制少见);"方案=可证伪承诺、证据用例事先写定"(科研预注册思维,个人项目落地极少见);"两个数据点才算立住"的观察锚点。
同时必须标边界:同模型不同上下文的独立审查优于自评、但**仍不等于外部真理**——LLM-as-a-Judge 文献指出自偏好偏差是结构性的,可靠判断靠"度量系统"(顺序打乱/校准集/人类抽检)而非单点评判;L44 全链失守是活例:独立审查防住了"自证",没防住"共同前提错误"。

### 段落二:sugas 落后在哪、谁该借鉴谁

落后处同样明确:
① **无 error budget / 无健康度度量**——"穷举最大化、主人愿意等"等于把主人的耐心当无限预算。单维护者研究(BurnRiSc, arXiv 2609.19422)指出"无界需求 + 无分流机制 + 无人注意到状态下滑"是烧尽最坏组合,sugas 占了前两条;建议借 SRE 的错误预算思路给主人负荷设软上限,借开源治理(Linux Foundation 调查等)的 bus-factor/健康度指标给"一个人"做体检。
② **spec 资产化弱**:spec-kit 每个需求留 spec.md 提交级资产;sugas 三件套随对话生灭,建议方案三件套落档归位。
③ **机检覆盖面窄**:业界(Google SRE/DevOps)把 postmortem action item 当带 owner/期限的受管工作,sugas 台账条目无期限字段(对应 P2);且 sugas 的机检集中在自家脚本层,对"知识层"(台账/记忆索引)反而失检(对应 P1)。
反过来,**开源单人维护者与 AI 辅助开发者应当向 sugas 学**:机制阶梯、观察锚点、删除先备份、"不静默"、四句口诀——这些是它原创度最高、最可借鉴的部分。
