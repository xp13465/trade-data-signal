## 〇、任务一判决:重复消费 = **真**(全链实锤,非推测)

### 1.1 机械根因(为什么必然重复、SEVERE 恒定在 :30)

fetch_news 轮次节律:每小时 :01、:45 各一轮,轮耗时 24-31s(:45 轮 end≈:45:2x)。monitor 15min 一 tick。
窗口「新鲜」判据:`_r2_fresh = (NOW - last_run) < 30min`,**last_run = 日志 mtime 分钟截断**(`schedule_monitor.sh:938-942`)。

于是每个 skip 轮被消费的次数不是 1 次而是 2-3 次:

- tick :00:消费 :45 轮(age≈15min,fresh)→ 计 1
- tick :15:**同一 :45 轮**(age≈29:xx < 30min,仍 fresh)→ 计 2(重复消费第 1 次)
- tick :30:若仍无新轮(:01 轮已消费则看下一轮)—— 对 fetch_news 典型序列为:tick :30 时 age 恰好 29:0x <30 → 计 3 → **SEVERE**
- tick :45:age≈44min >30 → stale 假清零 + 下一 tick 假恢复

即:**13 封 SEVERE 的「第 3 次计数」全部是同一轮的重复消费**。重放成分表 13/13 全部为 `counted=3, distinctRounds=2` —— 消息自称「连续 3 轮」,实际只有 **2 个真实 skip 轮**。
证据样例(10-05 13:30 封):计数来源 = `13:00(消费 12:45 轮) + 13:15(消费 13:01 轮) + 13:30(重复消费 13:01 轮)`。

### 1.2 现有去重机制为何没拦住(代码实读)

- 计数 key `{task}|r2_skip_rounds` 的计数逻辑(L956-966)**根本没有去重** —— 每 tick 只要 fresh+skip 就无条件 `+1`,不比较轮标识;
- 唯一的「防重复」机制 P1-3(L937-955)只处理「滞留值」(last_run 超 30min = 隔日/低频道任务场景),对 fetch_news 这种高频任务恒判 fresh → 完全挡不住「同轮二次消费」(代码注释 L934-936 自己写明「高频任务……连续 N 轮 SEVERE 行为一条不改」,那个「一条不改」正是本 bug 存活的空隙);
- 告警去重 key `{task}|r2_skip_alert`(L971-993)只保证「SEVERE 不重发」,但 :45 的 stale 分支**不 mark seen** → 通用恢复循环 L1685(「active 但本轮未 seen = 已消失」)15 分钟后判「恢复」→ key 复位 recovered → 下一小时 :30 再发。
- **「SEVERE → 15min 假恢复 → 1h 后重发」是结构性循环,锁持续期间每小时 1 封**。

实测:大事件 j45-60(10-04 17:01 → 01:01 锁占用 7h16m,含 j51 被杀轮)产 **6 封**(18:30/19:30/21:30/22:30/23:30/00:30)。

## 二、推荐方案

**主推 ①d(治本,必做)**:它修的是「计数语义 bug 族」—— 重复消费、假清零、假恢复-重报 —— 而不是调阈值绕开它。
效果:4 天 13→5 封,每封对应一个真实多轮事件,消息里的「连续 3 轮」从此是真话;改动最小(单块内,去重键直接用现成的 stats `last_run` 分钟串,不需要新数据源)。
**明确否决 ①a/b/c**(0 封 = 真故障全盲,数据铁证 max 计数=3)。

**可叠加 dial(用户拍板)**:若仍嫌吵,①d 之上二选一:③X=2h(语义升级为「缺口≥2h」,3 封)或 ②B 夜间降级(保昼夜节律,5-6 封)。选 ② 必须带「≥6 轮升级」(数据:正是它把 21:30 大事件补回)。

- **优点**:治本、文件局部、恢复语义不动、老 state 兼容。
- **缺点/代价**:2 轮级事件不再叫(诚实标注);dial 的 X/时段需用户定值。
