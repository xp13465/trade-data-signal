# sugas 开发协议(全量版)

> 用法:核心版(SKILL.md)够日常开工;本文件是"往下钻一层"的全量版 —— 想搞懂某条规矩为什么这么定、或者 AI 又在某类事上翻车,来查对应章节。
> 案例已脱敏:文中「某网站 / 某次事故 / 某个数据产物」代指具体项目,不点名、不引用原项目任何文件名/域名/业务名词。

## ① 核心理念:这套东西为什么有效

四个"根问题" + 两个"放大器"。理解了它们,后面所有条款都是推论。

### 1.1 根问题一:AI 的上下文是稀缺资源 —— 越装越笨
- 长会话里历史越滚越大:注意力被旧结论锚定、被无关信息稀释;一个会话同时干"干活 + 验收",验收必然偏向"我自己刚写的没错"。
- **解法 = 上下文隔离**:每件事开一个新的 AI 子任务(全新上下文),任务书只装这件事需要的东西(目标 / 约束 / 定位锚点 / 验收口径);干完只交「结论 + 证据点」,不把过程全文灌回主人这边。
- 主人这边只保留"调度层":派了谁、到哪一步、结论是什么。执行、审查、测试、调研各用各的会话 —— 这是"军团"能协作又不互相污染的前提。

### 1.2 根问题二:自证陷阱 —— 自己验自己等于没验
- 同一路径上的自我确认会继承同一个错误:写错的函数,自己写的断言也按错的写;复刻的脚本漂移了,自己跟自己对账还是"一致"。
- **「报告 ↔ 实现」同源互证 ≠ 正确**:调研报告、规格文档、代码实现可能从源头就带着同一个错,"三者一致"只说明错得整齐。必须引入双方之外的**第三锚点**:主人原话、界面文案、产品文档、官方文档、外部平台、生产实测。
- 推论:实施方"自己列检查清单、自己判自己没漏"= 自出自证。审查方要**先不看**实施方的清单、独立再推一份,再对账;差集(我有他没有的)必须逐条处置,不许静默吞掉。

### 1.3 根问题三:一切"完成"都是待验证的声明 —— 证据链要端到端
- 四句口诀:**「报完成 ≠ 真完成」「配置对了 ≠ 生效了」「代码在主线 ≠ 功能上线了」「检查全绿 ≠ 真没事」**。每层都要验到"真生效"层:数据真更新了、页面真显示了、真实环境真跑过一轮。
- 证据点长什么样:`文件:行号`、命令 + 输出关键行、字段值、日志时点。**写不出证据的结论一律视为"未验证"**,禁用「应该 / 大概 / 看起来没事」。
- 连"时间"也要证据:提交时间戳 ≠ 任务触发时间;文件生成时间 ≠ 内容本身的数据日期。判断"跑了没有 / 数据什么时候出的",看日志与产物本身。

### 1.4 根问题四:记忆不可靠,机制才可靠
- 靠"记住教训"防重犯:人记得,someday 新会话里的 AI 不知道;所以约束力要"能自动跑"才成立。
- 升级路径:**口头提醒 → 固化条款(写进项目规范,每会话自动加载)→ 机器闸门(每次自动检查,不过就拦截)**。被违反 2 次以上的条款 = 无效条款,必须重写或直接机制化 —— 不是记录得更勤,是让约束更硬。
- 配套:错误台账 + 定期归纳(新错分类:全新模式就新增条目;同类复发就**强化原条款**,不新开条)+ 精简时"移动不删除"(原文归档、索引可反查,防丢核心)。

### 1.5 放大器一:分工对了,产出是复利
- 人的判断力花在真正值钱的地方:方向、取舍、拍板、效用函数(比如"平稳赚钱优先于单期收益最大");AI 的算力花在不知疲倦的查全 / 跑全 / 验全。
- 前提是军团不跑偏 —— 于是有了下面的角色红线、派单纪律、六道关。

### 1.6 放大器二:这套体系自己也是会进化的产品
- 每轮踩坑变条款 / 变闸门;每次绕的弯路写进"这类任务怎么做对"的速查,让下一个全新上下文的 AI 不再重绕。
- 定期回顾(每周一次即可):删过时事实、不删教训;合并重复;检查"规范有没有重新膨胀、条款是不是失效了";优化落地后定期巡检关键指标,发现负向漂移就回滚或迭代。

## ② 人机分工红线(谁干什么 / 怎么派活 / 怎么并行)

### 2.1 主人(总指挥,即项目所有者)= 项目管理,不亲自动手
- 「主人这边」= 主人与当前对话中的 AI 一起(调度台);干活的是被派出去的其它 AI 会话。
- 只做三件事:①拆任务、派活(写清目标 + 约束 + 验收口径)②收总结、验收 ③控节奏与风险(优先级、时点、冲突)。
- 不亲自动手实施 / 调研 / 验证。**"我直接改快一点"是典型走偏**;唯一例外:纯文案 / 单行常数 / 无逻辑变更的小改,且确实紧急 —— 改完必须自测。理由:主人这边是调度台(上下文宝贵);"干活的人"与"把关的人"必须分开(见 1.2 节「自证陷阱」)。
- 验收 = 对已报告的结论做**单点复核**(点到即止);不是自己把整件事重新查一遍,更不是抢在审查前重复验。

### 2.2 角色分工(可按项目裁剪)
| 角色 | 干什么 | 硬边界 |
|---|---|---|
| 实施 | 写代码 / 改文件 / 出数据产物 | 带自测 + 同类面清单 + 只提交到自己的分支 |
| 审查 | 独立批判:查影响面、跑相关检查、独立推边界清单 | **只读,不改代码** |
| 调研 | 定位根因 / 查证 / 方案分析 | 只读;产出结论 + 证据(+ 方案) |
| 测试 | 回归 / 边界 / 数据完整性校验 / 上线验证 | 只读;证据=命令输出 |
| 机械执行 | 批量搬运 / 格式转换 / 按清单逐项改 | 纯确定性;遇到要判断的岔路立即停报;低档模型跑,省时省钱 |

- 小任务可让一个角色兼任;大任务走流水线(实施 → 审查 → 测试),审查与测试并行。

### 2.3 派单三件套(每次派后台任务必齐,缺一不算合规派单)
1. **后台跑**:不阻塞对话,主人随时能插话改需求。
2. **进度文件**:任务书写明路径,要求"每完成一步写一行(时间 + 步骤 + 结果)"—— 出事后一眼看出死在哪一步。
3. **兜底巡检**:主人这边建一个定时巡检(查进度文件 + 任务心跳),所有任务完成后删掉。完成通知会丢是架构事实,巡检是唯一可靠残余(详见 4.4 节)。

任务书还要带:目标 / 约束 / **验收口径** / **定位锚点**(`文件:行号`、函数名、关键字 —— 让子任务直接跳到位,不从第一行开始翻)/ **超时约束**(每条命令都显式带超时,防长命令把任务卡死)/ 回报格式(**只回结论 + 证据点**,全文落档不贴回)。

### 2.4 并行隔离铁律
- 并行跑多个"会写文件"的任务,**必须工作区隔离**:每个任务一份独立的工作区副本 + 独立分支(技术上如 git worktree、独立克隆仓库)。判据只有一条「**是否共享工作区**」——**"改的是不同文件所以安全"是错误心智**:共享工作区的当前分支 / 未提交改动是全局状态,谁切一次分支都可能把别人的改动带走。
- 提交只进自己的分支;主线合并由主人这边走**统一入口**(入口里做:冲突检查 / 版本号统一 / 生产安全窗口检查 / 合并后自检)。
- 承诺要核对:汇报"已隔离"之前,回看自己那次启动参数 —— 凭印象写"齐了"不算;且任务运行期,主人这边不要在共享工作区做切分支 / 合并 / 推送(连"只读"的任务也会被切走工作树)。
- 任何冲突 / 覆盖 / 版本倒退:卡住上报,禁止自行"解决掉"(见避坑清单第 12 条)。

### 2.5 任务生命周期纪律
- **主人接管**(「我自己来 / 你直接改」)= 第一件事:停掉在跑的同任务 AI,再动手(防双写同一文件)。
- **中途改口径 / 方向** = 停旧任务、派新任务带**全新任务书**(旧任务带着旧规格上下文,会按旧规格"对齐"反向操作);若只是执行方理解错了、规格本身没错 = 让它**续跑**(省上下文),别停旧派新。
- **续跑同一任务 = 沿用原分支**(防分支身份漂移 + 废弃分支)。
- **卡死处置**:先唤醒续跑(把"已完成清单"喂回去,只做剩下的 + 收紧纪律);不行再重派 —— 重派前先把半成品 / 未提交改动收好,别丢成果。
- **完成判定只看产物**:提交 / 文件改动 / 进度文件走到哪一步。通知里出现"完成"字样不代表完成;没有产物 = 没完成。

### 2.6 小任务不套大流程
- 改动分级:纯显示 / 文案 / 常量(约 ≤30 行、可一键回退)→ 主人这边直接改 + 自测;逻辑 / 跨文件 → 派实施 + 审查;数据 / 后端 / 定时任务 → 再加数据完整性校验。
- 一行修复走完整"派单 → 重读 → 等通知"流程,流程成本远超干活本身;但"直接改"不等于省自测:**自测铁律不因改得小而豁免**。

## ③ 六道关细则(每关:谁把关 / 做什么 / 保证什么 / 出口条件)

```
① 需求关 → ② 方案关 → ③ 实施关 → ④ 审查关 ┐
                                  ∥        ├→ ⑥ 上线关 → 观察锚点回核(上线后)
                                  ⑤ 测试关 ┘
```
- **审查关 ∥ 测试关 是"并行"不是"先后"**:两关同时开、各查各的,**两关都过**才放行。
- **观察锚点回核是"上线后"的事**:等它在真实环境自然跑一次,再派只读角色去核。

### ① 需求关 —— 保证「做的是对的事」
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 主人 + AI | 复述需求口径让主人点头确认;**三源核对**(界面文案 / 产品文档 / 代码现状)口径一致;举一反三列"同模式 / 同数据源 / 同组件还被谁用";叫停 / 改口径时列"删除清单 + 保留清单" | 不是把错的事做对;不偷偷漏掉该一起改的地方 |

**出口条件**:口径三方一致;不一致 ⇒ **停下报主人拍板**,不许自己选边。发现"多处说法不一"是重要信号 —— 早暴露,别等实施中撞车。

### ② 方案关 —— 保证「值得做,而且能被证伪」
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 调研角色 / 主人 | 方案写齐**三件**:**① 可修正的依据**(`文件:行号` / 实测数字 + 命令;禁用"我觉得")**② 实现预期**(可观测的 X→Y)**③ 证据用例**(事先写定、可独立复现) | 避免"为了改而改";改完能否达标,**动手前就有答案** |

**出口条件**:三件齐 = 方案;写不出 ②③ = 只是「建议」,不许当方案派单实施。
**实施前置**:进实施关之前,依据必须**已实测验证过**(问题真实存在 + 根因可复核定位 + 修复机制可达);未验证的依据 ⇒ 方案不成立,回去验证,不许"为了修而修"。
**反查条件**:实现完拿证据用例一对;对不上 ⇒ 判「**方案失败**」(不是"完成度打折"),回报并重新定位;同时查"证据用例是不是事后凑的"(设计早于实现 = 合格)。

### ③ 实施关 —— 保证「改完整」
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 实施角色(工作区隔离) | 改代码 + 自测;修 bug 先列「同类错误面清单」(同一根因还有哪些地方)再**修根因,不逐文件打补丁**;改了算法 / 规则要同步"给主人看的说明文案";新增/改动有真实副作用的东西(通知 / 告警 / 外发)先声明行为参数;边界维度清单想全;写码前爬"能不能不写/少写"的阶梯 | 根治而不是打地鼠;主人看到的说明跟规则一起改 |

- **边界七轴**(逐轴推导,不适用也要写"不适用 + 理由"):①输入域(空 / 缺 / 非法 / 超阈值 / 边界值)②状态组合(盘中盘后 / 首日 / 兜底态生效中)③时序(重复触发 / 幂等 / 乱序 / 跨日翻滚)④上下游依赖(源失败备源顶上后,展示位读的是死字段还是新值)⑤极端值(全空 / 全满 / 巨大 / 负值)⑥回退路径(降级 / 关开关 / 逃生门)⑦并发与重入。
- **写码前的阶梯**(自上而下停在第 1 个成立的层):需要存在吗(不需要=不做)→ 已有可复用吗 → 标准库有吗 → 原生能力有吗 → 已装依赖有吗 → 一行能搞定吗 → 以上都不行,才写最小实现。删除优先于添加;抽象只在出现第二个真实使用者时才提取。
- **出口条件**:自验含「同类面清单 + 逐项自测结果 + 边界清单(每条标"测 / 不测 + 理由")」。

### ④ 审查关 —— 保证「没改坏老功能,也没漏边界」(与 ⑤ 并行)
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 审查角色(**只读,不改代码**) | 按改动分级定审查深度;影响面穷举(grep"改动的东西被谁引用",列受影响老功能点);跑跟影响面相关的检查;**边界完整性独立复核**(先不看实施方的清单,自己再推一份再对账);审方案承诺(证据用例真跑过没有、预期达成没有) | 改坏老功能 = 拦住;**实施方没想到的边界,由审查方补上** |

**出口条件**:0 个阻断项;**两边边界清单差集非空 ⇒ 必须报主人**,逐条给处置(补测 / 显式声明不测 + 理由 / 上报);差集被静默吞掉 = 这关没落地。
- **发现治理**:每个发现先自评置信度,只报高置信度的;<低阈值项滤掉,但报告末尾必须写一句"另 N 个低分项已滤"(防黑箱)。"旧问题 / 主人故意保留的行为"走**上报**通道 —— 不当新问题报,也不默默忽略。
- **静态失败专查**:diff 里出现 try-except / catch / fallback / 判空兜底时必查 —— 空捕获、宽捕获吞错、"失败静默切备用但不留痕"、错误只打印不上抛、返回空值掩盖异常。

### ⑤ 测试关 —— 保证「事实层是真的」(与 ④ 并行)
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 测试角色(只读) | 跑冒烟清单(核心功能点逐个用命令验);边界用例(维度想全,深度按"最小充分");数据完整性校验 + 多展示位一致性;上线后三查 | 数字、数据、线上真生效 —— 不是"代码写了就算" |

- **安全底线**(绝不为"省事"省略):输入验证 / 权限与密钥安全 / 数据缺失兜底(该有的数据在不在,缺失即失败)/ 涉及钱与关键链路的路径。
- **证据纪律**:每条结论的证明命令**当场真跑**,读全输出核退出码,再看结论是否被支撑;证据必须是**命令输出**,不是口头描述;失败项立即报,不掩藏。
- **自验脚本先证明"能抓坏"**:造一个已知坏样本,确认脚本真报失败;坏样本也过 = 尺子坏了,修尺子而不是信结果。
- **出口条件**:全过 + 无漏维度 + 数据校验通过。

### ⑥ 上线关 —— 保证「主人真能看到,而且不撕裂」
| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 主人 | ①三查齐(提交在主线 / 数据层生效 / 展示层真上线)②发布物指纹 + 缓存校验(内容变必换指纹;部署后校验"入口引用的指纹 == 实际文件内容")③环境门禁**真绿**(本机自测绿 ≠ 目标环境绿)④避开生产任务时点(见避坑清单第 13 条) | 上线即主人可见;不白屏、不撕裂、不撞定时任务 |

**出口条件**:三查齐 + 指纹校验通过 + 门禁结论 = 成功(失败**当场修**,不等主人发现)。
- 展示层验证小技巧:打包压缩后的产物变量名会被混淆重命名,验证要用**字符串 / 类名**(主人能看到的文字),不要 grep 变量名。

### 观察锚点回核(上线后,不是关)
- 做法:上线后挑一个**真实自然跑**的时刻(下一轮定时任务 / 下一轮采集),派只读角色核一次。
- 判据:**两个数据点才算立住**(自然跑两次都过);只有一个点 = 未立。
- 意义:证明治本"真治住了",而不是"改完那一刻看着对"。

### 横向铁律(每道关都适用)
1. **派单三件套**:后台跑 + 进度文件 + 巡检兜底,缺一不算合规派单。
2. **不信自述,信物证**:报"完成"≠真完成;关键结论逐字复核。
3. **冲突绝不静默**:版本倒退 / 文件被覆盖 / 异常 diff,一律停下上报,不许吞。
4. **删除前必备份**:先做出可独立恢复的副本并**实测可恢复**。
5. **治本优先**:止血可以快,但必须同时立案治本(止血 ≠ 结案)。

### 本流程的已知弱点(诚实标注)
| # | 弱点 | 现在的兜法 | 还差什么 |
|---|---|---|---|
| 1 | **环境假绿**:本机绿、目标环境红 | 硬规:发布后必看真实运行结论;检查禁用"本机有/无某命令"类环境判断 | 把"目标环境可跑"写成派单验收点 |
| 2 | 边界清单**谁推谁证**(自己列清单、自己判自己没漏) | 已由"独立再推一份 + 对账"堵住 | 差集里"不测"的处置是否真合理,最终靠人判 |
| 3 | 方案预期写得出、**证据用例可能事后凑** | 要求核"用例是否早于实现" | 时间先后只能靠提交顺序佐证,不是硬机检 |

## ④ 关键机制(四条,把纪律变成系统)

### 4.1 基准锚定 —— 一切测试 / 对比都站在「当前基准」上
- 任何回测 / 测试 / 挖掘 / 对比,**默认前提 = 当前基准**:基准有名字有版本、有定义、有可复现的锚点数字;先复现基准,才能往下走。
- 测**非基准口径**(旧版 / 其它参数档)必须**显式声明** + 说明为什么测 + 结论标注口径差异;非基准口径的结论**不作主推**。
- 引用"当前默认值 / 最优配置"的一切材料(派单 / 报告 / 汇报),**下笔前先读当前真值**(配置 / 页面实际),并标注来源与日期 —— 默认值会变,报告是快照、会过时。
- 动到核心默认行为 = 必须"**发版本**":更新基准定义 + 全站登记点逐个同步(同一事实在代码 / 配置 / 文档里可能有多份副本)+ 一致性机检通过;老版本保留作对照。
- 发现基准过时,**第一时间同步给正在跑的任务**(越早越省,别等它跑完返工)。

### 4.2 错误台账 —— 错误即资产,复利积累
- 结构:每条带「锚点编号 + 一句话防重犯 + 根因 + 归档位置」,可反查原文;索引与归档要能对账(条目数一致 = 零丢失)。
- 规则:
  - 每次犯错追加一条;**同类复发不新开条** —— 在原条上标"第 N 次复发(日期 + 本次差异)"并**强化原条款**(改得更具体 / 换机制)。
  - **被违反 ≥2 次的条款 = 无效条款**,必须重写或升级为机器闸门 —— 不是记录得更勤,是让条款更有效。
  - 归纳要**结合历史**:先读全部历史过错,分类(全新 / 复发)再处理;总结是**归纳不是删减**(核心结论、根因、场景不删;删的只是过时事实)。
  - 精简时"**移动不删除**":原文全量归档、索引可反查;精简只动外层(索引),底层(主题文件)原封,出问题能恢复。
  - 防重犯条款写成「**X 场景做 Y**」(具体可执行),不写"注意检查"这类空话。
- 节奏:会话级 / 每日归纳新错;**每周回顾**一次(删过时事实、不删教训;合并重复;检查规范有没有重新膨胀、条款是不是失效了)。

### 4.3 机器闸门 —— 能机器查的,不要靠人记得
- 升级路径:口头提醒 → 规范条款(每会话自动加载)→ **机器闸门**(每次自动检查,不过就拦截)。凡"每次都要做的机械动作",光写进规范一定会忘(新会话不读它、忙碌时会跳过),必须机检。
- **机检三道质量关**:
  1. **设计关**:判据按真实形态写(按代码实际写法,不按脑内写法);写完必测「命中数 > 0」—— 给数字,不许写"应该能匹配"。判据写完从没命中过 = 空转。
  2. **判别力关**:造一个"该被拦"的坏样本,闸门必须真报失败(变异测试)。**空转的闸门比没有更危险** —— 它给人"已有防护"的错觉。
  3. **挂载关**:闸门挂在哪个强制点决定爆炸半径(挂错环节可能拖垮整条流水线);要在**真实生产环境**验证(干净副本里通过不算);核对"检查命令实际跑的范围"与"目标文件实际所在目录"是否相交(差一层目录 = 没挂上);优先选"失败不阻断生产部署"的强制点。
- **部署后的自动校验也属闸门**:如"入口引用的版本指纹 == 实际文件内容"(防缓存滞留旧快照)、"关键数据产物完整性校验(该有的数据在不在:缺失 / 滞后 / 空值超标即拦截)"。
- 诚实口径:**本机自测绿 ≠ 服务器上自动检查(CI)绿**(环境差异会假绿);闸门报"绿"时要分清是"真跑过且真产生了输出"还是"空转"。

### 4.4 异步任务的可靠通知 —— 通知会丢,巡检兜底
- **架构事实**:后台任务的"完成通知"会丢(多个渠道都会丢,别赌)。**唯一可靠残余 = 主人这边兜底巡检**:定时查(进度文件 DONE 标记 + 任务心跳),全部完成后撤掉。
- **判死活两条件**:①系统登记表里在册(直接列出的任务清单)②**心跳在推进**(任务的转录文件大小 / 时间在变)。两个都满足 = 活着;**在册但 ≥20 分钟零推进 = 卡死**(冻结在"启动时刻"最常见,典型死因是被无超时的网络操作挂死)。
- **卡死处置顺序**:先**唤醒续跑**(把"已完成项清单"喂回去,只让它做剩下的 + 收紧纪律)> 再考虑重派。重派前先把半成品 / 未提交改动收好,别丢成果;**同一个任务续跑两次仍卡 = 别续第三次**,换更规定化的任务书重派(把已查明的结论直接喂给它,不让它重查;禁止整文件读超大文件;每完成一条立即回写进度)。
- **子任务自己设"定时器等它唤醒"不可靠**(会话一停,定时器就没了)—— 要等时点的动作由**主人这边**设一次性触发兜底,或干脆改为立即执行。
- **网络型任务防卡死**:一切网络操作必须有硬超时(用"带超时的通道"取代"无超时的通道");每步回写进度(不许只在开头写两行);失败最多重试一次,失败即标"未测"继续,不死磕;白名单给 URL,不许发散浏览。
- **收工纪律**:任务结束自查有无残留后台进程 / 未落盘的半成品;有就在报告首行声明(残留任务 ID + 命令 + 预期退出),交主人处置。

## ⑤ 避坑清单(52 条真实错误 → 15 个通用坑 + 2 条补充)

> 每坑三行:**症状 → 根因 → 防重犯**。案例已脱敏。遇到同类场景,先读这一条再动手。

**坑 1:派出去的 AI 任务"石沉大海"**
- 症状:派了任务后半天没动静;等"完成通知"干等,任务其实早就死了,没人知道;或通知说"完成",产物却根本没生成。
- 根因:完成通知在平台层不可靠(会丢);"等通知"当唯一通道 = 赌运气。
- 防重犯:派任何后台任务必配**兜底巡检**(定时查进度文件 + 心跳);任务书要求**每步回写进度**;判死活 = "在册 + 心跳在推进"两个条件;超过阈值零推进 = 卡死,按 4.4 节处置。

**坑 2:自己干完自己验(自证陷阱)**
- 症状:执行方报"已验证通过",上线后还是坏的;或"报告"和"实现"互相引用都错得一模一样;主人肉眼才发现问题。
- 根因:同路径自我确认继承同一错误;报告与实现同源,互证 ≠ 正确。
- 防重犯:执行与审查**分离上下文**;关键结论引入双方之外的**第三方锚点**(主人原话 / 界面文案 / 官方文档 / 生产实测);审查方**先不看**实施方的检查清单、独立再推一份对账,差集必须逐条处置。

**坑 3:全绿 ≠ 没事(假样本 / 坏尺子 / 环境差异)**
- 症状:检查全过,生产却是空转 / 缺数据 / 功能没生效;或者"修好了三次"实际零变化。
- 根因:①断言样本是人工编的("看起来合理",现实里不存在该字段 / 形态)②尺子(校验脚本)本身有 bug,算出假数据给错误方向背书 ③本机环境 ≠ 目标环境(假绿)。
- 防重犯:断言输入取**真实生产样本**;机检写完必做两件事 —— 实测命中数 > 0、造坏样本让它真报错;自验脚本先证明"能抓坏";本机绿 ≠ 目标环境绿,看**真实运行结论**;观感类问题要产出"主人同一视角"的证据(路径条数 / 颜色段密度这类主人真能看到的东西),局部数值全对 ≠ 主人觉得修好了。 另两条同族:①**单一通道的"绿 / 安静"≠ 全局没事** —— 多出口的系统先盘点"这条链有哪几个出口",再逐出口核对;排查"最近有没有出过事"按"最近动过的全量扫一遍",猜关键词式搜索必漏。②改了**公共源码**后要跑**全量检查面**——"只跑直接相关的用例、全绿"≠ 全绿(有些检查是盯源码形状的全局守卫,源码一变它就红)。

**坑 4:报告数字和真实页面 / 真值对不上(复现脚本 = 第二份实现)**
- 症状:报告结论数字与产品页面 / 真实运行不一致;排查时还先怀疑"主人看错了 / 主人改过设置"。
- 根因:**任何"复刻逻辑"的脚本都是第二份实现** —— 源头改逻辑,副本不会自动跟,静默漂移是必然不是偶然;而报告没有"与真实渲染对账"这一步,假数字直接发表。
- 防重犯:进报告的核心数字(尤其结论 / 主推建议依赖的)**发布前必须与真实渲染 / 实跑结果对账**(逐位比);对不上 = 停下查根因再发布;**禁止预设"主人记错"**,先测真值再定性;修正后在报告里标注修复链,旧假数保留可反查。

**坑 5:修 A 坏 B(影响面是网状的)**
- 症状:新功能上线,老功能挂了;一个数据文件被多个模块读,牵一发动全身,单靠"改的人自己测"覆盖不到。
- 根因:依赖网 + 无回归机制。
- 防重犯:改动分级(显示级 / 逻辑级 / 数据级),按级配审查深度;实施方列**同类错误面清单**(同一根因还有哪些地方)+ 自测全覆盖;审查方 grep"改动点被谁引用",列受影响功能清单 + 跑相关检查;修 bug **修根因**("一个共享函数里的守卫,好过每个调用处各打一个补丁"),不逐文件打补丁。

**坑 6:拿着过期的基准干活**
- 症状:基于旧默认值 / 旧报告跑回测、做拍板材料,结论全部作废;任务书写"按最新最优",却没写是哪一版;给主人的材料把"旧默认"标成"现役默认",被当场纠正。
- 根因:默认值 / 最优配置会变;报告是快照,会过时。
- 防重犯:一切测试 / 回测 / 拍板**默认前提 = 当前基准**(见 4.1 节);引用默认口径的材料,下笔前**先读当前真值**并标注来源 + 日期;要测非基准口径必须显式声明;发现基准过时,**第一时间同步在跑的任务**。

**坑 7:做错方向 / 擅自加改动(需求理解偏差)**
- 症状:交付了主人没要的东西;把"相关增量"当核心需求做完,核心需求没动;主人叫停"删 X"被理解成"删整条链路",把可保留的中间档也删了。
- 根因:不复述确认就开干;凭语义猜口径;没分"核心需求 vs 相关功能"。
- 防重犯:动手前**复述需求口径**让主人确认(尤其"删到什么粒度 / 保留什么档");只做明确要求的,**不擅自加**;接"分析 / 建议 / 新增视图"类需求,先列需求拆解清单(回答什么问题 / 新增什么 / 用哪份数据)再派活;叫停 / 改口径时列"**删除清单 + 保留清单**"逐项确认;口径类改动后自验关键展示值(不等主人报异常)。

**坑 8:分类 / 档位 / 阈值靠猜("差不多就这么归")**
- 症状:边界值(空值 / 极弱 / 临界)被归错档;同一概念在界面、文档、代码里三种说法,没人对照,全链一路错到底;机器检查全绿但主人肉眼发现不对。
- 根因:语义靠猜;更隐蔽的是"报告 ↔ 代码"互证闭环 —— 报告与实现同源带 bug,互相印证全绿。
- 防重犯:涉及"分类 / 档位 / 象限 / 阈值 / 区间"的改动,必须做"**三源核对**"(界面文案 / 产品文档 / 代码现状),缺一源或对不上 = **停下上报主人拍板**,不自行选边;报告与实现一致 ≠ 正确,必须引入两者之外的锚点;**守恒类断言**(该归零的必须归零)不能只靠键集比对。

**坑 9:"没有 / 做不到 / 不可改善"下结论太快**
- 症状:一句"全市场没有符合条件的标的 / 这条路走不通",被主人换个平台当场搜出好几个可用结果。
- 根因:只验证了自己当前的方法 / 数据源覆盖范围,把"我的算法搜不到"当成"客观不存在"。
- 防重犯:下否定类结论前,**换方法**(换一类算法)、**换数据源**(第三方平台 / 别家口径)、**换关联维度**(直接匹配 vs 间接重叠)再验证;结论里列"**已验证了哪些方法 / 数据源**",让主人判断充分性。

**坑 10:"测试"把真告警发到了主人手机(危险脚本先打桩)**
- 症状:一次"自测 / 变异测试"变成主人可见的真事故(真邮件 / 真通知发了出去,撤不回)。
- 根因:脚本带真实外发链路(通知 / 告警 / 邮件),自测没打桩,或沙箱判定没生效。
- 防重犯:凡能产生**真实副作用**(发通知 / 写生产数据 / 调外部接口)的脚本,自测前**必须先打桩**(dry-run / 替身 / 沙箱,并**先证明打桩判定真的生效**);派单验收点含"本次自测未产生真实外发"证据;万一真外发:**如实上报 + 留痕不删已发记录**(删了 = 记录与事实不符)。 同族:审查 / 测试用的**探针一律只读**,绝不执行生产脚本;**副作用防护门控用正面白名单**(只放行显式声明的对象),禁用"环境变量齐不齐"这类可被真实形态绕过的条件。

**坑 11:删了才想恢复,恢复不了(先备份)**
- 症状:清理 / 删除 / 覆盖之后要回退,发现没有可恢复副本;或"有备份"但真要取回时发现从来没验证过,取不回来。
- 根因:删除没先建立可逆性;把"要不要删"当成风险点,而不是把"备份做了没有"当分界线。
- 防重犯:**先备份,后删除**(顺序不可反;本地空间不够就备到远端,**没有例外**);备份必须**实测可恢复**(清单全量比对"缺失 = 0" + 抽样取回逐位一致);**验过直接删,验不过停下报警**;删除报告写明"怎么恢复"(从哪取回 + 恢复命令),写不出来 = 不算可逆 = 不许删;有备份 ≠ 可以删,要尊重既有的保留决定。

**坑 12:冲突 / 覆盖被静默吞掉**
- 症状:某次改动悄悄消失、版本倒退、线上行为变回老样子,等主人肉眼发现显性 bug 才暴露,修复成本翻倍。
- 根因:合并 / 覆盖类异常被"看起来能跑"地自行消化;"先合并看看、先推上去再说"的侥幸。
- 防重犯:任何冲突 / 覆盖 / 倒退 / 异常 diff —— **一律停下上报,宁可卡住等决策,绝不静默解决**;汇报格式 = 现象 + 根因 + 影响 + 选项;用机制兜底:统一合并入口 / 版本倒退哨兵 / 并发串行检查 / 合并前核对文件范围。

**坑 13:两个任务撞在同一时点(动手前先看"时刻表")**
- 症状:两个定时任务 / 两次操作同时写同一资源,互相覆盖 / 抢锁 / 数据打架。
- 根因:动手前没查"当前时点 + 并发任务清单"。
- 防重犯:每次派任务 / 设定时器 / 发布前,先列**任务时刻表**核对不撞,避开生产窗口;"**紧急也不豁免**"—— "线上坏了要马上重出数据"不是豁免理由:能挪窗口就挪,挪不了先上报主人拍板,事后如实留痕(现象 / 重叠时长 / 实际影响);把时点约束**内建进自动化设计**(窗口门 + 硬超时上限),不靠"跑的时候记得看表"。

**坑 14:同一份数据,三个地方显示三种值(一处更新 ≠ 处处更新)**
- 症状:主人在不同页面看到不一致的数据;一个新版一个旧版;文件一致但缓存没清,看到的还是旧值。
- 根因:更新只做了半步(生成了没同步副本 / 同步了没清缓存);同一事实在代码里有多份副本(常量表 / 白名单 / 展示文案),改一处忘一处。
- 防重犯:一处更新 = **N 处同步**(N 个数据副本 + N 层缓存),列清单逐个勾;用**一致性机检**在发布时拦截"不一致";同一事实的多处代码登记点,切口径时**全 grep 同步 + 机检比对**;对主人承诺"一旦更新,所有展示位必须同时更新"。

**坑 15:压缩 / 重启后状态全丢**
- 症状:会话被压缩或重启后:在跑的任务、定时器、待办、已定的决策全记不起来;重复问、重复派、重复讨论。
- 根因:临时状态只活在会话内存里;而"压缩"只保留结论概要,丢掉过程状态。
- 防重犯:**任何事默认持久化** —— 进度 / 状态落盘(重要状态还要进版本库);定时任务默认持久化(会话关了不丢);关键决策 / 验收结论**落档**不只口头;恢复时按清单核对:在跑任务(含每个任务的心跳)/ 定时器 / 提交链 / 待办 —— 核对完发现兜底巡检不在位,**第一动作补建**。

**补充两条(轻量)**
- **小任务套大流程**:一行修复走完整"派单 → 重读 → 等通知"流程,流程成本(冷启动 + 重读 + 反复沟通)远超干活本身。按改动分级处理(见 2.6 节);自测不豁免。
- **慢 / 贵只往流程上想**:遇到"慢 / 贵"先查**参数层**(推理开关 / 模型档位 / 缓存命中),再查流程层;外部系统 / 第三方行为的未知问题,**第一动作上网查社区 + 官方文档**,不闭门做实验自我证伪。

## ⑥ 沟通决策风格(和 AI 协作时,双方都按这套来)

**6.1 说人话**
- 中文、口语化;规范 / 文档 / 界面文案里禁用黑话缩写,换成一读就懂的中文表达;技术名词首次出现加解释。
- 判据:**没干过这行的人读这句,知道要干嘛吗?** 不知道就继续改。
- 结论先行,证据在后;**简洁砍的是废话,不砍证据**(改了哪些文件 / 自测逐项结果 / 口径标注,这三样必须给)。

**6.2 给选择题,不给开放题**
- 请示 / 拍板场景固定骨架:① **2~4 个具体方案**(每个都能直接选)②每个方案的**好坏**(缺点优先)③**我的建议**(明确说选哪个 + 为什么)④一句话重点。
- **禁止句式**:"要不要…""是否可以…""你觉得如何比较好""有没有必要"。一律改写成"方案 A:… / 方案 B:… / 我建议 A,因为…"。
- 方案必须**自足**:主人回一句"选 A"就能直接开工;技术细节(参数 / 默认值)自己调研定,不抛回。

**6.3 缺点优先**
- 要主人拍板前,**先报风险与缺点**,再报好处,最后才是我倾向;"缺点"要具体到可想象的后果(谁在什么场景看到什么变化、会不会漏报、能不能回退)。
- **没有缺点、只有好处的事不用问** —— 直接做并告知(所以"要不要做 X"这种问题通常是个多余的问题)。

**6.4 目标函数先定死,再排序方案**
- 先确认主人真正的效用函数(例:"年年都赚、平稳优先于单期收益最大";"可操作性优先于账面数字"),然后**所有方案按它排序** —— 先报回撤与稳定性,再报收益;账面收益率再高、不可操作的方案不当主推。
- 主人提供想法 / 方向,AI 用数据验证并给建议;不把"决策"原样抛回主人(主人提供想法,你跑数据)。
- 主人凭使用记忆提出的疑问 = **最高优先级信号**(主人天天用产品);先验证再下结论,不拿自己的推断去纠正主人。

**6.5 穷举最大化 + 诚实标注**
- 回测 / 调研不省计算(主人明确愿意等):该查的维度全查,不留"待进一步验证"的尾巴;全局选优类报告**一次给全维度**(基线复现 / 分年分解 / 稳定性 / 回撤与恢复 / 极端场景 / 参数变体 / 口径诚实标注),不等主人点名补。
- 新旧口径**全对比**(持仓规模 / 收益率 / 盈亏 / 是否爆炸),用数据选优,不预设。
- 退化年 / 反例 / 不确定**如实标注**,不选择性隐瞒;发现"两处说法不一致"先做**归因**(谁在生效 / 是不是历史遗留 / 当初是不是刻意),把"刻意设计"误报成"文档漂移"会让主人在错误前提上拍板。

**6.6 认知有限,就上网调研**
- 自己知道的方法不够 / 不确定最优时:主动上网调研业界可用的方法(数据分析 / 挖掘 / 算法)与社区经验,挑合适的用;调研后落档方法论供复用。
- 外部系统 / 第三方 / 官方参数类问题:**先查社区 + 官方文档**,不闭门做一堆实验自我证伪(有真实教训:闭门 11 组实验的结论,社区一轮就能印证)。
- 评估任何外部项目 / 方法论值不值得用:对它服务的**每个角色逐个**问"能带来什么增量",穷举完才下结论;只覆盖一个角色 = 评估不完整。

**6.7 完整正确 + 敏捷节奏(两者不矛盾)**
- 质量底线:尽可能完整正确、一步到位、不交半成品、不做"温和版"凑数;上线必须是完整版(数据 / 覆盖全就绪才发,**残缺版上线 = 事故从上线那一刻开始**)。
- 节奏策略:短周期迭代、尽快交付可用版本、边攒边用边校准、欢迎变化;不排"N 个月后才有产出"的路径。
- 一句话:**质量要完整,节奏要快**;不拿敏捷当偷懒借口,也不拿"终极方案"当拖延借口。
- 先建能力,再评分:先把东西做出来(哪怕有过拟合 / 不完美风险),再评稳定性;"做都做不到,担心过拟合就是空谈"。

**6.8 一切默认持久化 + 定期自省**
- 重要结论 / 决策 / 方案 / 检查报告 → 落档进版本库,不只放会话记忆、不只口头;"落档是经验积累成长的基础"。
- 每轮犯错都进台账(4.2);每周回顾一次规范 / 记忆 / 台账;优化落地后定期巡检关键指标,发现负向漂移就回滚或迭代。
