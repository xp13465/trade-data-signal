### 23.5 新产物当场落档·塞入即归类(2026-08-14 用户定,通用归档铁律,核心资产保护)
**核心**:论证报告+回测数据+运行脚本是项目最有价值的资产,必须落档。**所有新增(文档/脚本/数据/代码/目录)从创建起就放在最合适的位置与归类,一次到位,塞入即归类,不能依赖定期整理兜底**。
- **适用范围**:任何新增文件/文档/脚本/数据产物/功能代码/目录,创建时先想"该放哪":①有现成主题目录(如 `docs/kelly/<主题>/`)→ 直接放对应目录 ②无合适目录 → 先想清楚归类再建,命名与既有一致(如 kelly-xxx 前缀)③研究产物三层落档:报告(结论 md)→ 主题目录;脚本 → 同目录 `scripts/`;数据 → 结果 json/csv 同目录(注明生成命令/日期)
- **索引必建**:落档时同步更新对应目录 `README.md` 或索引(列文档+脚本+数据);索引建好后,**新产物入场即更新索引**,不攒
- **报告可复现闭环(2026-08-15 用户定)**:报告要经得起"质疑→反查→复现",必须靠脚本咬合。四件套缺一不可:①报告本体(结论+数据+诚实标注)②生成脚本 ③复现段(报告内强制)④配套 commit。缺脚本=报告无法复现=泛泛之谈。
- **③复现段(报告内强制)**:每份回测/调研/论证报告 md 末尾必含「## 复现」节,写清:脚本路径+输入依赖(哪些 DB/JSON)+重跑命令(一行可跑)+数据截止日期/数据版本+关键口径一句话(如"买C1=RSI上穿30,卖D1=20日高回落5%")。
- **②生成脚本两态**:活脚本(被生产/定时任务引用)→ 报告只写指向,不复制(防双份维护分叉);死脚本(一次性回测)→ 副本放报告同目录 scripts/ 跟报告咬合。
- **脚本头部注释规范**:脚本头部 docstring 必含 目的/方法口径/输入依赖(DB路径)/输出(REPORT路径)/关键参数种子/复现命令。脚本=规则的唯一事实源。
- **验收口径**:grep 报告「## 复现」段有脚本路径+命令+依赖;脚本文件存在且 git ls-files 已 tracked;脚本头部含目的/依赖/口径;新脚本与报告同 commit。研究/回测/新增功能任务验收须含「落档位置确认+索引更新确认+git 已跟踪确认」,缺落档=验收不过;新目录若为临时摆放需当场说明并定迁移计划。
- **触发词**:任何研究/回测/论证/数据挖掘任务收尾 + 任何新增文件/目录落位时,主控核对「产物已放最合适位置+索引已更新」;派单 prompt 含落档要求,agent 收尾自验落档完整性

### 23.7 版本功能冻结契约(2026-08-15 用户定,生产环境稳定性第一要素)
**用户原话**:「补一条默认规范。既然做了版本号。正常情况 不混序破坏最近版本的所有功能 只能新增。若需要调整历史功能。一定是我确认过的」「线上稳定版本默认契约是不能动。但是如果在做性能或测试时发现有bug或历史遗留需要提醒我 给出完整的证明链路。问我确认要不要修」
**触发词**:任何改动触及已上线/已发布的功能行为/布局/口径/数字/交互;想"顺手优化"老功能;做性能/测试时发现 bug 或历史遗留。
**核心一句话:已发布功能 = 冻结资产,默认只能新增、不能改旧;动历史功能必须用户确认过才动手;发现 bug/历史遗留必须上报完整证明链路问确认,不默认修也不默认忽略。**
- **① 默认只增不改**:版本号机制下,最近版本已上线的所有功能(行为/布局/口径/数字/交互)在正常情况下**不得破坏/调整**,需求只能以"新增"方式叠加。新增必须默认不改变既有功能默认行为(如新 toggle 默认关、新档位不覆盖默认值)。
- **② 改历史功能必先确认**:需调整/修改已发布功能,必须先向用户说明"要动哪个、改成什么样、影响什么",**用户确认后才实施**;未经确认不得自行调整(哪怕觉得"更合理"或"顺手")。
- **③ 与 §5.4/§15 关系**:§5.4 是回测/测试必须落在当前测试基准,本条是更上位的功能冻结契约(已发布的展示/交互/布局同样冻结);§15 回归防改坏老功能,本条从源头拦"不该动老功能"。
- **④ 例外**:纯 bug 修复(功能坏了而非优化)不受限,但修复仍走 §23.2 + 修复自验同类;用户主动要求改(如 #88 用户点名改对比表布局)视为已确认。
- **⑤ bug/历史遗留发现必须上报问确认**:线上稳定版本默认不能动。但**在做性能/测试时发现 bug 或历史遗留**,不得默认修、也不得默认忽略——必须**提醒用户 + 给出完整的证明链路(现象/根因/影响/证据/修复方案)**,**问用户确认要不要修**。不点头就落档为「已知问题待用户决定」。
- **验收口径**:派单/实施涉及"改既有功能"时,任务描述须含「用户已确认此项改动」或「纯新增」;reviewer 查改动是否夹带未确认的历史功能调整,夹带=验收不过;agent 在做性能/测试时发现 bug/历史遗留,回报必须含「完整证明链路 + 是否已问用户确认」,缺=验收不过。

### 23.9 复杂数值表三档互证教学法:白话+场景+1:1直白举例(2026-08-17 用户定)
**触发词**:给用户写难懂/绕的数值表或复杂指标的说明文案(AI监控卡统计口径/过拟合风险分/回测表/信号口径/任何"绕"的展示)。
**核心一句话:复杂难懂的数值表/指标说明,用「三档互证」教学法教会用户怎么看——白话解释(是什么)+ 场景模拟(什么时候用)+ 最直白 1:1 举例(拿真实日期/数字落到具体数据)三者互相印证。1:1 直白举例可能最冗长,但最清晰易懂,反而对难懂绕的数值表是最好的学习说明方法(用户原话)。全站适用。**
- **① 三档各自定位**:白话=一句说清是什么(如"统计口径15日≈最近3周信号的命中率");场景=说清什么时候用(如"昨天新开降亏过滤想验证好不好用→选15日");1:1=拿真实数据举例(如"8/14 看到过拟合 = 拿 8/13 往前 15 个有信号交易日(约 2026-07-24~08-13)内 181 个买入信号:实盘 40.9% vs 回测 58.7%,差 17.9pp → 风险分 82 红")
- **② 1:1 数字必须核实**:1:1 举例的数字(日期/n/命中率/风险分)必须从源码+数据文件核实(派 researcher 查机制再写),不臆造;复杂指标若用户可能混淆(如"曲线点风险分"vs"左上综合风险分"是两个指标),必须在例子中明确区分
- **③ 全站适用**:AI 监控卡使用指南、回测表、信号口径、任何"绕"的数值表都可套用此教学法
- **④ 与 §6 口语化关系**:§6 是回复口语化,本条是"给数值表写说明文案"的方法论,适用所有展示文案(前端 tooltip/使用指南/README/报告)
- **⑤ 1:1 举例 = 强制自查手段(2026-08-17 用户心得,核心升级)**:用户亲历「一开始觉得实盘40.9 vs 回测58.7 差17.9pp 正常,看 1:1 举例才发现数据/算法不对,而且正是写举例时自查揪出」——1:1 举例不只教用户,更是**逼自己逐位核实数据来源与算法口径的检查点**。为了给出真实日期+真实数字的举例,必须核对到逐位一致;**凑不上/对不齐 = 大概率数据或实现有误,停下查根因**(联动 §5.1 数据说话/§23.2 修bug三铁律),不"差不多就行"。**平台所有复杂说明/数值表文案都适合配 1:1 直白举例——既是用户最好懂的说明,也是你自己的自查手段**(用户原话:"也算是一种你自查的手段")
- **验收口径**:涉及数值表/复杂指标说明文案任务,自验含「三档互证齐不齐(白话+场景+1:1)+ 1:1 数字是否从数据核实」;写任何数值说明前**先自查能不能写出 1:1 举例(真实日期+真实数字)**——写不出来=对数据/算法理解不到位,先派 researcher 核实再写,不直接落文案。缺=验收不过

**触发词**:任何动 task/todolist/待办/归档/会话收尾落档;看到 TASKS.md 堆历史/打勾/远期/长期无人关注项;派治理/瘦身/归档任务。

**核心一句话:任务分 4 态 ↔ 4 文件流转;处理时机=会话收尾落档时;task 只放当下活跃排队任务。**
- **① 活跃(当下排队)→ task(TASKS.md)**:真正在干的活;长期没人关注→主动提醒移入 todolist,不默默留。
- **② 待办/远期 → todolist(docs/pending-features-index.md)**:远期/搁置/用户明说的;要远期时用户明说再去 todolist 捞回 task,不说明就留 todolist。
- **③ 完成 → 完成文件**(独立完成清单,如 docs/tasks-done-list.md):task 任务完成→移入完成文件,标注完成态+commit/链接。
- **④ 归档 → docs/archive/**:**完成文件呆满 7 天→自动归档**(可反查,§23.5)。
- **处理时机=会话收尾落档时**(每次会话收尾顺手治理 4 态流转,不积累不专门找时间)。
- **状态日志保留上限(独立规矩,2026-08-28 补,与 4 态流转①②③④并行)**:**TASKS.md 顶部「📍 当前会话状态/前次更新」交接日志只保留最新一坨**(最后更新+今日队列+待办指针);更老轮次在会话收尾落档时折叠/归档(指向 docs/tasks-done-list.md 或 docs/archive/,可比照 ④),**不 append 无限累积**(根因:TASKS.md 越堆越大不是 4 态流转问题,而是跨会话交接日志无清理规范,现堆 5 大轮)。§23.12 只管「任务清单」怎么流转,本条补「状态日志」怎么清,两套并行各自独立。
- 勾选 `[x]` ≠ 归档:完成项进完成文件/归档,不长期占 task;`[x]` 与正文状态必须一致(防"正文待做/勾已打"矛盾,如 L60 教训)。
- **禁一刀切按块类型**(memory [[archive-dispatch-by-block-type]],L53 误删 28 活待办已回滚):按块类型/逐条核;活待办数前后核清;核心不丢(§5.3)。
- 关联:docs/main-governance §18.2 索引维护、memory tasks-md-only-active、pending-features-index 每日 23:47 cron 自动重建。
- **验收口径**:涉及 task/todolist/归档任务,agent 自验含「4 态流转对照(活跃留 task/远期移 todolist/完成进完成文件/归档可反查)+ **状态日志只留最新一坨(老轮次已折叠/归档)**+ 活待办数前后不变 + 会话收尾已落档」,漏=验收不过。

### 23.12-1 任务状态单一事实源 + 机检兜底(2026-09-06 用户拍板根治,任务状态一致性 P0)
**触发词**:任何"登记任务状态/改 pending-index 状态列/写 TASKS 交接日志 #N 指针/设巡检 cron/记拍板结果/归档任务"动作;看到同一任务状态在多处各写各的;发现状态两处不一致。
**背景(2026-09-06 三事故复盘)**:①#36 北交所宽度宇宙拍板结果没落档 + 僵尸巡检 cron(e5c24403)挂着,造成"待拍板"误判——拍板已定但没写回索引,巡检 cron 没随任务结束删掉;②#81 已关闭但 TASKS L49/L116 曾残留远期指针——关闭项还在 TASKS 待办/远期块被当可捞回项列着;③FAPI 评估 09-04 产出 09-06 才 commit——产出与落档脱节。根因=同一任务事实 6 处各写各的(TASKS 交接日志/pending-index/TaskList/cron/git commit/memory),靠主控人肉同步必漂移;数据一致性有 check_data_integrity 挂 deploy 机检,任务状态零机检。
**核心一句话:任务状态唯一权威 = docs/pending-features-index.md(编号+状态列);其余各处置写指针不写状态断言;机检 check_task_state.py 兜底,FAIL 阻断上线;拍板必三连。**
- **① 单一事实源**:任务状态(编号/待办/进行中/已拍板/已完成/已关闭)唯一权威 = `docs/pending-features-index.md` 表格行的编号+状态列。TASKS.md 交接日志 / cron prompt / memory **一律只写指针**(如「#102 已拍板A,见 pending-index」),**不写状态断言**(不写"#36 待拍板"这类会漂移的断言语);发现同一任务状态两处不一致 = §23.11 绝不静默同精神,上报主控/用户拍板,不自行选边。
- **② 机检兜底**:`scripts/check_task_state.py`(只读,对账 A pending-index 编号完整性 / B TASKS 幽灵编号+残留关闭指针 / C 僵尸巡检 cron)挂 **每日 cron + deploy 前 check(与 check_data_integrity 同链)**,FAIL 阻断上线;漂移项自带定位行号/编号/建议动作。
- **③ 拍板联动三连**:任何"用户拍板/任务关闭/任务完成"动作固定三连:①更新 pending-index 对应编号状态列(或移入 done-list/archive)②删/改对应 cron(巡检类任务完成即 CronDelete,防僵尸)③清 TASKS.md/memory 残留指针(已关闭项不得再作远期/待办指针列着)。
- **关联规范源**:本条 = §23.12(4 态流转)的状态一致性补强 + §23.5(落档) + §22(一致性)在任务域落地;对应脚本 `scripts/check_task_state.py`;2026-09-06 用户拍板根治,三事故复盘见 docs/tasks-done-list.md 或本会话交接日志。
