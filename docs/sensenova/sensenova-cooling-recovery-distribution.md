# sensenova-rotate-proxy 冷却恢复耗时分布与定档报告

日期:2026-09-01(周一)
状态:已按数据定档,落代码(COOL_L0_SEC=180s 起步,档位 180/360/720/1440/2880,封顶 48min;高峰 9-14 冷却×2 + 退避加长)

## 一、背景与目标

商汤 token.sensenova.cn 的 deepseek-v4-flash 按账户限流:5 把 key = 5 个独立账户,每账户独立 1500 次/5h 配额 + 各自 TPM/RPM。429 分两类:
- **短时限流**(inference tpm / rpm exhausted)→ 换 key 即解,不冷却;
- **账户额度型**(token plan entitlement / Allocated quota)→ 单 key 冷却。

旧冷却逻辑(2026-09-01 上午)为 `COOL_L0_SEC=60s` 起步、每级 ×2 封顶 32min,是拍脑袋定档。本次按用户拍板「数据驱动 + 高峰应对 + 保守容量退避」,用 555 次 quota 型 429 的真实日志解析恢复耗时分布,重定档。

- 日志:`/Users/linhuichen/code/trade-data/data/logs/sensenova-rotate-req.log`(仓外,2026-09-01 02:10 ~ 2026-09-02 15:45,73k 行,COOL 标记 426 次 / SKIP COOLED 8970 次 / 429 响应 9554 次)
- 日志时间 = 本机本地时间(CST+0800,北京时间)

### 口径说明(诚实标注)
日志 RESP 行**不带 key 标识**,无法精确关联「某 key 冷却后哪次响应成功」。因此用每把 key 的冷却状态机重建(COOL 标记 + SKIP COOLED 事件),按日志时间线重放,统计:
- 指标A COOL → 冷却期内最后一次被 SKIP = 代理侧冷却占用时长观测值;
- 指标B 冷却解除(末次 SKIP)→ 下一次 COOL = 解除后到再撞 quota 的真实可用时长(定档核心);
- 指标C 相邻两次 COOL 间隔 = 冷却周期复发节奏;
- 指标D 全局 429 响应间隔(不限 key)= 整体撞车频率。

## 四、关键结论(数据说话)

1. **空转实锤**:当前 60s 冷却起步下,冷却解除后 **p50 仅 48s 就再撞 quota 429**,36% 场景解除后不到 30s 就撞——即「冷却 1min 解除 → ~1min 又撞」的空转模式占三分之一以上。60s 起步明显偏短。
2. **恢复节奏**:quota 429 是滚动恢复型(非 5h 全量冻结),解除后有一个几十秒~几分钟的可用窗口,然后再次耗尽。冷却时长越长,解除时点配额恢复越充分,单次可用期越长,空转越少。
3. **冷却不损失配额**:quota 429 撞车 = 账户配额已耗尽,此刻发请求必 429(浪费);冷却期间不发请求,配额按时间自然恢复。因此冷却偏长只损失实时性、不损失配额,宁等勿空转。

## 五、定档方案(基于以上数据)

### 5.1 冷却起步与档位(对应代码 COOL_L0_SEC / COOL_MAX_LEVEL / _cool_duration_sec)
- **`COOL_L0_SEC = 180`(60s → 180s,3min 起步)**:
  - 依据:60s 冷却解除后 p50 48s 又撞(36% <30s)= 空转;180s 起步让解除时点越过「假恢复快速又撞」区(p50=48s),解除后配额恢复更充分,单次可用期拉长,冷却循环频率从每 ~2min 降到每 ~5min。
- **档位公式:180 / 360 / 720 / 1440 / 2880(×2),封顶 48min**:
  - 依据:指标A p90=3.5min(90% 场景 3.5min 冷却足够)、p99=39.9min(极端恢复场景需 ~40min)→ 封顶 48min 覆盖 99% 恢复场景;真死 key 靠递增自然隔离,不狂试。

### 5.2 高峰主动限频(北京时间 9:00-14:00,写死窗口)
- 高峰检测到 quota 型 429 时:**该 key 冷却时长 ×2(180→360s 起步等档位翻倍)** + **ROTATE_BACKOFF 0.3s → 1.5s**。
- 理由:高峰全体账户都在烧配额,撞车后恢复更慢;翻倍冷却减少高峰空转;换 key 退避加长降低高峰换 key 重试的请求率(short 类 429 换 key 即解,1.5s 单次重试影响可接受)。
- **诚实标注**:日志实测北京时间 9:00-16:00 均为 quota 429 高峰(10:00 1554 / 13:00 1797 峰值 / 15:00 1569 / 16:00 1632 次 429),比用户拍板窗口 9-14 延伸至 16:00。代码默认窗口按用户拍板写死 9-14,窗口做成 env 可配(`TTP_PEAK_HOURS`,默认 "9-14"),如实际部署想扩至 16:00 改 env 即可,不改默认。
- 节假日可能误判是已知边界(写死北京时间,不判交易日)。

### 5.3 全 key 冷却时保守整体退避(替代直接返回 429)
- 当前:全 key 冷却 → 直接返回 429 给客户端。
- 保守版:全 key 冷却时进入整体退避等待(30s 起步 ×2,单次退避 30/60/120/240/480s),退避期间不发请求(不把 key 打进长冷却),到点重新探测是否有 key 恢复;累计等待超 480s(8min)仍全冷却 → 返回 429(如实告知)。实现上等待前 cap 掉剩余累计额度,保证累计等待严格 ≤480s(自测校正:序列 30/60/120/240/30,累计恰 480,不会因单次 480s 把累计顶破)。
- **明确**:这是保守等待重试版,不做「容量超载」判定(响应特征分不清容量 vs 配额,避免误判),注释里已声明。
