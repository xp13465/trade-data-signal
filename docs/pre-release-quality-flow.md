# 上线前质量流程规范(2026-10-14 定稿)

> 目的:一句话说清「一个版本从需求到上线,中间过几道关、谁把关、每一关**保证什么**」。
> 权威来源:根 `CLAUDE.md` §5.7(方案=可证伪的承诺)/ §6(说人话)/ §0.2(派单三件套)/ §8(三查)/ §14(时点)/ §23.2-23.13(各条铁律) + `docs/main-governance.md` §15(改动分级 A/B/C 与回归三层) + 各角色 `.claude/skills/role-*/SKILL.md`。本文件是**路线图**,不重复各条的全文;冲突时以 CLAUDE.md 为准。

## 0. 总览:6 道关 + 1 个观察锚点

```
① 需求关 → ② 方案关 → ③ 实施关 → ④ 审查关 ┐
                                  ∥        ├→ ⑥ 上线关 → 观测锚点回核
                                  ⑤ 测试关 ┘
```
- **审查关 ∥ 测试关 是「并行」不是「先后」**:两关同时开、各查各的,**两关都过**才放行上线。
- **观察锚点回核是「上线后」的事,不是上线前的关**:等它在真实环境自然跑一次,再派人去核。

---

## ① 需求关 —— 保证「做的是对的事」

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 主控 | 复述需求口径让用户确认;**三源核对**(界面文案 / 产品文档 / 代码现状)口径一致(§23.13);**举一反三**列同模式/同数据源/同组件还有谁在用(§23.3) | 不是把错的事做对;不偷偷漏掉该一起改的地方 |

**出口条件**:口径三方一致;不一致 ⇒ **停下报用户拍板**,不许自己选边。

## ② 方案关 —— 保证「值得做,而且能被证伪」(§5.7,2026-10-14 新立)

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| researcher / 主控 | 方案必须写齐**三件**:<br>① **可修正的依据**(`文件:行号` / 实测数字+命令,禁用"我觉得")<br>② **实现预期**(可观测的 X→Y:哪个字段/数字/行为,从什么变成什么)<br>③ **证据用例**(事先写定、能独立复现的用例/命令/断言) | 避免"为了改而改";改完能不能达标,**动手前就有答案** |

**出口条件**:**三件齐 = 方案;写不出 ②③ = 只是「建议」,不许当方案派单实施**。
**反查条件**:实现完拿证据用例一对,**达不到预期 ⇒ 判「方案失败」**(不是"完成度打折"),按 §23.7 / §23.11 回报并重新定位。

## ③ 实施关 —— 保证「改完整」

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| implementer(worktree 隔离) | 改代码 + **同类错误面清单**(§23.2 修 bug 三铁律)+ 算法改动同步**公示文案**(§21)+ **边界维度清单想全**(tester skill §5.3.1 七条轴)+ 自测 | 根治而不是逐文件打补丁;用户界面上的说明跟算法一起改 |

**出口条件**:自验含「同类面清单 + 逐项自测结果 + 边界维度清单(每条标测/不测+理由)」。

## ④ 审查关 —— 保证「没改坏老功能,也没漏边界」

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| reviewer(**只读,不改代码**) | ① 按 §15 改动分级(A/B/C)决定审查深度<br>② **影响面穷举**:grep 改动文件被谁引用,列出受影响的老功能点<br>③ 跑**跟影响面相关**的那部分冒烟测试 + 数据校验<br>④ **边界完整性独立复核**(2026-10-14 新立,skill §10.8):**自己再推一份**"这次改动可能踩到的边界"清单,和实施方那份**对账**<br>⑤ 审方案的可证伪性(§10.7):证据用例真跑过没有、预期达成没有 | 改坏老功能 = 拦住;**实施方没想到的边界,由审查方补上** |

**出口条件**:0 个阻断项(或有阻断项 ⇒ 打回);**两边边界清单的差集非空 ⇒ 必须报主控**,逐条给处置(补测 / 显式声明不测 + 理由)。差集 silently 吞掉 = 本节未落地。

## ⑤ 测试关 —— 保证「事实层是真的」(与审查关并行)

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| tester(只读,不改代码) | ① 跑**冒烟测试清单**(主功能点 curl 数据层 + 关键交互)<br>② **边界用例**:维度要想全(§5.3.1 七轴),深度按「最小充分」(§5.4)<br>③ 数据完整性校验 + 多展示位一致性(§22)<br>④ 上线curl三查(§8):main 链含 commit / 数据层生效 / 前端展示层真上线 | 数字、数据、线上真生效 —— 不是"代码写了就算" |

**出口条件**:冒烟全过 + 边界清单无漏维度 + 数据校验通过;**验收证据必须是命令输出,不是口头描述**。

## ⑥ 上线关 —— 保证「用户真能看到,而且不撕裂」

| 谁 | 做什么 | 保证什么 |
|---|---|---|
| 主控 | ① §0 三查齐(见 ⑤④)<br>② 版本串 + 缓存哈希校验(§24:部署后"内容哈希 == index 引用版本串")<br>③ **CI 必须真绿** —— 本机自测绿 ≠ CI 绿(CI 环境差异会假绿)<br>④ §14 时点:盘中不跑全量导出+部署;盘后禁区 15:35/16:00/17:50/20:35/22:00 不推 main;安全窗口 23:00 后 | 上线即用户可见;不白屏、不撕裂、不撞定时任务 |

**出口条件**:三查齐 + 哈希校验 PASS + **CI 结论 = success**(FAIL ⇒ 当场修,不等用户发现)。

## 观察锚点回核(上线后,不是关)

- **做法**:上线后挑一个**真实自然跑**的时刻(次日定时任务 / 下一轮采集),再派 tester 或 reviewer **只读**核一次。
- **保证**:治本**真的治住了**,而不是"改完那一刻看着对"。
- **判据**:**两个数据点才算立住**(如伪跳空 10-13 + 10-14 两次自然跑均 PASS)。只有一个数据点 = 未立。

## 横向铁律(每道关都适用)

1. **派单三件套**(§0.2):后台跑 + 进度文件 + 巡检兜底,缺一不算合规派单。
2. **不信自述,信物证**:agent 报"完成"≠真完成(验收铁律);关键结论主控逐字复核 / grep。
3. **冲突绝不静默**(§23.11):版本倒退 / 文件被覆盖 / diff 异常,一律停下上报,不许吞。
4. **删除前必备份**(§25):任何删除类动作,先做出可独立恢复的副本并**实测可恢复**。
5. **治本优先**:止血可以快,但必须同时立案治本(止血 ≠ 结案)。

## 本流程的已知弱点(诚实标注)

| # | 弱点 | 现在的兜法 | 还差什么 |
|---|---|---|---|
| 1 | **CI 假绿**:本地绿、CI 红(CI 只装 pytest/pyyaml/numpy/pandas/pyarrow,环境不同) | §8 硬规:push main 后必自查 CI 结论 + 测试禁写死"本机有/无某命令" | 派单时把「CI 环境可跑」写成验收点(已入 tester skill 验收口径) |
| 2 | 边界清单**谁推谁证**(自己列清单、自己判自己没漏) | 已由审查关 ④ **独立再推一份 + 对账**堵住 | 差集"不测"的处置是否真的合理,最终仍靠人判 |
| 3 | 方案预期写得出、**证据用例可能事后凑** | §10.7 要求核"用例是否早于实现" | 时间先后靠 commit 顺序佐证,不是硬机检 |
