# Token 缓存命中率统计:2026-08-15 优化落档前后对比

## 结论(一句话)

**命中率由优化前 0.8908 提升到优化后 0.9776,改善 +8.68 个百分点,已远超健康标准 0.7。** 8 天窗口内前后各 13428 / 4555 条 usage 记录,样本充足,结论可靠。

## 背景

2026-08-15 落档了一批 token 优化规范:
- `cache-hit-rate-optimization` memory(同主题 SendMessage 续跑、派单给差异信息、一批独立任务并行启动)
- §5.5 token 优化 6 条 0 成本行为层(输出简洁/命令静默/派单只回结论/@文件直引/小任务不spawn/失败方向用rewind)
- §5.2 模型参数层(thinking 开关等)

本统计量化这些优化落地后,Claude Code 调 API 的 token 缓存命中率改善。

## 统计口径

- **数据源**:`~/.claude/projects/-Users-linhuichen-code-trade/*.jsonl`(本项目全部会话记录,共 85 个文件)
- **命中率公式**:`cache_read / (cache_read + input)`(cache_read 为缓存命中读、input 为冷启动重读,两者之和=请求总输入,命中率=命中占比)
- **提取字段**:每条 assistant 消息 `message.usage` 的 `cache_read_input_tokens / cache_creation_input_tokens / input_tokens` + `timestamp`(ISO 格式)
- **聚合方式**:按天求和后算当天命中率(非逐条命中率平均),窗口整体则是窗口内求和再算(避免天数不等偏差)
- **窗口**:前=08-10~08-14,后=08-15~08-16
- **异常行过滤**:`cr=cc=inp=0` 空 usage 行跳过(全史 420 条,占比 0.6%,不影响统计)

## 诚实标注

- `cache_creation_input_tokens` 全史(72333 条 usage)均为 0,nonzero=0。本环境(火山方舟/deepseek 经代理)在此字段不计量缓存创建,因此命中率只用 `cache_read+input` 口径(任务给定),不受影响。若用"含 cache_creation 命中"的更严格口径,本数据无法区分——故不做 cache_creation 维度的结论。
- 命中率改善**相关性 ≠ 因果性**:08-15 同时落档了 3 类优化(cache 续跑/§5.5 行为层/§5.2 thinking 开关),无法拆出各自单独贡献;且 08-15 当天 `input`(冷读)骤降从 ~1100 万降到 ~900 万,主因是「派单只回结论/@文件直引减少重扫大文件」+「同主题续跑同 session」直接压低了冷读量。
- 08-16 只有半天数据,「后」窗口结论主要靠 08-15 单一全天 + 08-16 半天佐证,样本量仍充足(4555 条)。
