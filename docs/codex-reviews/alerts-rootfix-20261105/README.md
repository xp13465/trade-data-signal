## 真实问题与证据

### 1. QVIX 主备源口径混写，历史输入反复切换

这不是仅调告警阈值能解决的问题。代码中备用 RV 在缺少 `just_date` 时会返回整段历史，随后与主源历史混批，以一个来源标签写入；主源整体失败时的整段 RV 也可覆盖已有主源。SQLite 冲突更新没有来源优先级保护。

生产只读快照比较：2026-11-03 07:03 到 21:00，QVIX300 的 1650 个已有日期、QVIX1000 的 2838 个已有日期数值变成 RV；后续分别有 1649、2837 个日期精确返回先前值。剩下的 20261102 是主源合法更正，不能整体回滚旧库。来源标签本身不足以证明数值来源，结论同时使用数值比较与独立 RV 计算。

11/03、11/04 的四批审计变化中，真实两条直接 `g.*` 信号的 **433 个变化键**，由原信号算法离线重放逐键完全重现；将输入截断到 20261030 仍一致。1001 个历史变化键涉及六族，但其余四个下游族的 568 个真实键未完整复算，不能把 433 外推成 1001 全部修复证明。11/04 21:00:01 快照早于当晚采集，不拿它冒充采集后快照。

实现：

- 主源历史与备用补日独立批次、独立来源；三个真实采集/回填入口一并迁移。
- 有 `just_date` 时备用源严格限定目标日；目标日不存在就报告缺日，不退回整段。
- 单条/批量写入均在 SQLite `ON CONFLICT ... DO UPDATE WHERE` 内原子限定：仅两个 QVIX 指标的 `rv_local`/`sse` 来数只插缺日，不覆盖任何已有来源（包括 manual、unknown、NULL、旧备用源）。主源保留原有人工保护及合法修订语义。
- SSE/RV 异常不丢弃已取得的主源数据；备用非有限值/None 拒绝并保留诊断；RV=0 合法，有限负值的既有边界不扩大。
- 不改 a_qvix_1000 的既有代理映射、信号阈值、标准化窗口、冻结及回测规则。

此策略有意保守：已有备用值不会被后续备用值改写，只有主源可以升级/更正它。未知历史来源不做批量猜测修复。

详见 [QVIX 实施说明](../../ops/alerts-rootfix-qvix-20261105.md)。

### 2. 基金净值自愈后重抽样，不能证明原失败对象已修复

原检查抽到不一致对象，后续自愈/复验又随机抽样，可能刚好绕开第一次失败者。网络超时可能触发初始落后，但告警反复与“修后 PASS”证据不可靠是检查契约的问题。

实现：首次失败对象（bucket/code/direction）传给自愈与修后验证；清单绑定规范化数据目录和数据库身份，拒绝跨目录/串库；真实方向由 DB 与导出内容重算，清单不能授权修改。逆向、未知或损坏输入继续阻断，不因定点路径降级为 PASS。原无清单的随机检查兼容保留。

独立复核使用实际 exporter 口径和两个只读生产 payload 共 2574 行；不是只验证自造 JSON。范围仍是既有“最新三点”比较，不能声称全历史净值质量已验证。临时摘要随现有日志归档并清理，不另加 timer；必须保留原退出码与首轮/最终两份摘要。

详见 [净值自愈实施说明](../../ops/alerts-rootfix-selfheal-20261105.md)。

### 3. verify-r2 写保护与通知状态处理存在缺口

`verify-r2` 名称像对账，但内部会自动 PUT 补传；把它列入只读白名单会绕过本地公共桶写保护。另有三处调用不看 `notify.send` 结果便占用 24h 去重窗，所有通道失败时也可能压掉下次通知。

实现：移出只读白名单；三处通知只有完整布尔渠道结果中至少一个渠道明确成功，或明确成功持久入摘要，才占窗。入摘要只是已接收，不等于飞书送达。`ALERT_DIGEST_DISABLE=1`/预算禁用时，复用现有可用性函数，自动预算、域抑制、恢复轨迹入口不再继续吸入自动摘要；显式入队 writer 和 flush 的存储契约不变。

现有可用性函数只检查环境开关，不能检测 cron 是否实际挂载/健康。没有证明历史每条未送达告警都由这一机制造成，也没有把三类修复包装成所有告警已经消失。

详见 [R2 与通知实施说明](../../ops/alerts-rootfix-r2-20261105.md)。
