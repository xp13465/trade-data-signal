## 已核实的问题与实现边界

### R2 共享文件反复依赖对账补传

`cmd_upload_intraday` 将上传覆盖 key 写入独立链台账；`cmd_upload_all_data` 随后将所有活跃台账 key 都排除。`boot` 与 HK 范围文件又会被普通 exporter 重生成，形成“曾被独立链上传”被误当“永久独占责任”的错误。

04:25 告警包含 `data/boot.json`、`data/hk-1y.json`、`data/hk-3m.json`、`data/hk-6m.json`，当时 1907810 字节、累计第 16 轮。07:52/07:53 的只读 HEAD/GET 显示四对象与本地 exact bytes 相同，总计 1907811 字节；不能把这两个时点混成同一版本。07:18 状态的累计值为 18，不能说这 18 轮全发生于本次部署后。当前对象相同证明补传已补平，不能证明主上传已修复。

实现复用既有生成范围，仅以本轮成功写出的 UTF-8 bytes、独立运行 ID 和规范目录放行共享产物。静态 membership、文件 mtime 或表 MAX(date) 单独不能证明本次真生成。不设置四文件例外、不删台账、不放宽告警，也不引入远端 CAS 或版本收据。

已复现的共享发布锁旁路改为同 key 互斥：锁内读取实际 payload、核 proof、PUT/HEAD 并确认该 bytes；raw 保留原 global 豁免，small 保留原轻量外锁，不把小通道塞进整批 data 队列。已有通道指纹为 A、其它合法上传变 B、下一次真正生成 A 的场景，也会在 key 锁内核对远端，避免只看旧指纹漏传。

并发 pending 现在按请求携带不可变 proof 副本、ID/hash 和规范目录，精确消费，不以全局 latest 覆盖上下文。不再出现旧 worker 用 A proof 补跑、删掉 B 待办并返回成功但 B 未上传的已复现路径。每轮仍为初次加至多一次 catch-up，snapshot 每次最多 32 条；最后 snapshot 后到达者保留凭据和 pending，并明确记录 remaining，由下一正常 worker 接手，不冒充本轮完成。

独立复验覆盖实际完整 exporter/main、shell 外锁/timeout/skip 接力、uploader CLI、同 key 交错与旧指纹盲点；网络、verify 修复和通知为隔离桩，没有真实 R2 PUT。详见 [共享产物与接力实现说明](../../ops/r2-shared-export-handoff-20261106.md)。原型失败及迭代报告保留，不沿用旧候选 PASS。
