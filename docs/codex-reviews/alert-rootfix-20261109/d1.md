这次消除的是**既有五个稳定索引每轮被删除重建**的开销，不是删除索引换成本。零业务变化仍写同步元数据，真实变化仍维护主键和二级索引，缺索引时仍付一次补建成本。

首次 `row_hash` 列及 score 的 `score_date` 列迁移仍按既有逻辑执行。历史数据缺哈希时，每个业务行仍需初始化/更新；包含日期列的哈希也可能让评分日更新触发大量 changed。因此首次迁移不可按稳定期“零变化”估算。上轮 **142280 是五个索引条目的模型数量，不是本次或上轮实测计费 rows_written**。

## 补充：日/周变化范围及 UPSERT 的剩余写入成本

此项只作边界分析，不扩大本次补丁。结论是：**消除五个索引的无条件重建可以独立验收；总配额告警仍不能关闭。**

### daily 不等于两表都只变 2000 行

- `scripts/pf_score_daily.sh:45` 调 `compute_all_scores(top_n=2000, resume=True)`；`app/collector/public_fund.py:3813` 按规模排序 LIMIT 选取基金。`_compute_fund_score` 返回的 `score_date`（3745 行）和 `update_date`（3770 行）都是当天。若跨日新评分成功落库，即使数值相同，成功重算的那部分基金也会改变哈希。`latest_by_key` 不会把其余基金的旧评分日自动改成当天；所以**仅此评分链不会自动让全部 score 行每天都变**。同日 resume 还会跳过已完成基金，实际成功数也可能少于 2000。
- score 同步还 JOIN 基础扩展字段；规模、类型、费率等实际变更也会扩大变化集合，2000 不是所有来源变更的硬上限。
- screener 是 `fund_basic` 全集的平表。`scripts/update_all.sh:291` 调 `stage0-daily`，`app/collector/public_fund.py:5748–5751` 更新收益、评级、申赎、经理四个汇总来源。收益采集（2013–2050 行）和申赎采集（2103–2137 行）均按返回的全市场基金写当天 `update_date`；screener 把它们作为 `perf_date`、`purchase_date` 纳入全列哈希。**只要这些广覆盖采集成功，下一次同步就可能有大批非头部基金 changed，即便收益/申赎值本身没变。** 实际覆盖数、成功时点及同步间隔本轮未读生产数据，不能声称每天恰好全表变化。
- screener 的 `setup_years` 还是按运行日重新算、保留两位小数（同步脚本 `years_from_ymd` / `RUN_DATE`），跨日即使源库未更新，也可能有一部分行因年数舍入跨档而改变哈希；`built_at` 在 meta 内，只产生元数据写入，不进入业务哈希。
- weekly 调 `compute_all_scores(top_n=None)`（`scripts/pf_score_weekly.sh:41`），新日期成功重算的全部基金都会变化，不能按日常头部 2000 预算。注意 weekly 脚本本身只同步 score；随后下一次 screener 同步才消费这些全量新评分，并非 weekly 直接调用两表。
- 首次历史哈希为空时，diff 会将其归入 new；已有主键仍由 UPSERT 冲突分支初始化。新库才走真正 INSERT。两者都不能按稳定期 unchanged 估算。

本轮另用真脚本 DRY_RUN 做了日期单变量重放：score 两只基金只改 S1 的评分日期、数值不变，日志 `total=2 changed=1 new=0 unchanged=1`；screener 三只基金只改申赎源 `update_date`、评分和申赎状态不变，日志 `total=3 changed=3 new=0 unchanged=0`。证据为同目录 `d1-date-boundary.json`。这是可达路径小样，不把三只样本外推成生产当日变化数。

### 离线 Miniflare 小样：全列 UPSERT 确实会维护未变索引

复用本机已有 `miniflare 5.20261104.0-beta`，未安装依赖、未调用 wrangler。使用包内 `convertV4MiniflareOptions` 适配本机版本接口。输入是这次真脚本 DRY_RUN 实际生成的 **45 列 score / 81 列 screener** 表结构、原五个二级索引及一条合成基金行；两表均有 `fund_code TEXT PRIMARY KEY`。在系统沙箱中仅开放本机回环、禁止外网与仓库写入；使用纯本地临时数据库，结束调用 `dispose()`。

| 单行操作 | score 本地 meta.rows_written | screener 本地 meta.rows_written |
| --- | ---: | ---: |
| 新主键 INSERT，全列 | 4 | 5 |
| 全列 UPSERT，所有值均相同 | 3 | 4 |
| 全列 UPSERT，仅 row_hash 值变化 | 3 | 4 |
| 直接 UPDATE 仅 row_hash 列 | 1 | 1 |
| 直接 UPDATE 仅 composite_score 索引列 | 2 | 2 |
| 全列 UPSERT，composite_score 值变化 | 3 | 4 |

生成器的 SET 列表包含全部非主键列：score 脚本 `set_cols`，screener 脚本 `set_cols`，以及 `scripts/lib/d1_incremental_sync.py:build_conflict_clause`。因此在本地实现里，即使只因日期或哈希变化入选，现有 UPSERT 仍维护全部二级索引，不能把 1 个 changed 业务行算成 1 行写入。哈希完全一致的行确实被 diff 跳过，不会发这条 UPSERT。本次不引入按列差异 UPDATE，不改变日期和哈希语义。

本地原始证据均在 `/tmp/codex-reports/alert-rootfix-20261109/`：`d1-local-budget.cjs`、`d1-local-budget-input.json`、`d1-local-budget.json`、`d1-local-budget.log`。可用 `node d1-local-budget.cjs` 复现，脚本引用本机缓存包及输入绝对路径；正式复现应继续包在本次离线沙箱内。**表中数字是本机模拟器返回值，不是生产 D1 计费测量，也不是套餐余额。**

### 首轮/周全量预算风险的条件估算

仅为说明量级，代入上轮元数据的每表 **28456 行历史样本**，把上述本地每行成本线性外推：

- 两表历史行初始化哈希且主键都已存在：`3×28456 + 4×28456 = 199192`；两张空表首次 INSERT：`4×28456 + 5×28456 = 256104`。
- weekly 仅 score 全量成功更新的模型为 `3×28456 = 85368`；之后 screener 全量更新的模型为 `4×28456 = 113824`。是否落同一个 UTC 配额日取决于实际执行时点；本轮没有验证。
- 若 daily 的 score 变 2000 行、同时 screener 广覆盖数据使全量变化，模型为 `3×2000 + 4×28456 = 119824`。这是假设场景，不是对当前每日 changed 数量的实测声明。

以上均未加列迁移/DDL、缺索引补建、元数据、removed 清理、其它同步和 OPS 等同账号写入；不能作为实际收费数字。它们已经足够说明：**即便稳定索引不再重建，首次迁移、周全量以及 screener 广覆盖日更仍有超过免费 100000 行/UTC 日参考门槛的风险；没有预算安全保证。** 实际 plan/余额未知，是否适用免费门槛也未知；必须留待生产自然同步的真实用量及完整 UTC 周期验收。本任务只记“索引重复重建根因修复”一项。
