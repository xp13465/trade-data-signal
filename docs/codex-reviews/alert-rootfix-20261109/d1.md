## 补充：日/周变化范围及 UPSERT 的剩余写入成本

以下为 Phase1 时的边界分析与旧写法成本证据；用户随后授权 Phase2 根治其中的 UPSERT 放大器，最终行为见后文。结论仍是：**两个已证实的放大器可以独立验收；总配额告警不能关闭。**

### daily 不等于两表都只变 2000 行

- `scripts/pf_score_daily.sh:45` 调 `compute_all_scores(top_n=2000, resume=True)`；`app/collector/public_fund.py:3813` 按规模排序 LIMIT 选取基金。`_compute_fund_score` 返回的 `score_date`（3745 行）和 `update_date`（3770 行）都是当天。若跨日新评分成功落库，即使数值相同，成功重算的那部分基金也会改变哈希。`latest_by_key` 不会把其余基金的旧评分日自动改成当天；所以**仅此评分链不会自动让全部 score 行每天都变**。同日 resume 还会跳过已完成基金，实际成功数也可能少于 2000。
- score 同步还 JOIN 基础扩展字段；规模、类型、费率等实际变更也会扩大变化集合，2000 不是所有来源变更的硬上限。
- screener 是 `fund_basic` 全集的平表。`scripts/update_all.sh:291` 调 `stage0-daily`，`app/collector/public_fund.py:5748–5751` 更新收益、评级、申赎、经理四个汇总来源。收益采集（2013–2050 行）和申赎采集（2103–2137 行）均按返回的全市场基金写当天 `update_date`；screener 把它们作为 `perf_date`、`purchase_date` 纳入全列哈希。**只要这些广覆盖采集成功，下一次同步就可能有大批非头部基金 changed，即便收益/申赎值本身没变。** 实际覆盖数、成功时点及同步间隔本轮未读生产数据，不能声称每天恰好全表变化。
- screener 的 `setup_years` 还是按运行日重新算、保留两位小数（同步脚本 `years_from_ymd` / `RUN_DATE`），跨日即使源库未更新，也可能有一部分行因年数舍入跨档而改变哈希；`built_at` 在 meta 内，只产生元数据写入，不进入业务哈希。
- weekly 调 `compute_all_scores(top_n=None)`（`scripts/pf_score_weekly.sh:41`），新日期成功重算的全部基金都会变化，不能按日常头部 2000 预算。注意 weekly 脚本本身只同步 score；随后下一次 screener 同步才消费这些全量新评分，并非 weekly 直接调用两表。
- 首次历史哈希为空时，diff 会将其归入 new；已有主键仍由 UPSERT 冲突分支初始化。新库才走真正 INSERT。两者都不能按稳定期 unchanged 估算。

本轮另用真脚本 DRY_RUN 做了日期单变量重放：score 两只基金只改 S1 的评分日期、数值不变，日志 `total=2 changed=1 new=0 unchanged=1`；screener 三只基金只改申赎源 `update_date`、评分和申赎状态不变，日志 `total=3 changed=3 new=0 unchanged=0`。证据为同目录 `d1-date-boundary.json`。这是可达路径小样，不把三只样本外推成生产当日变化数。

### 实施前三验及最小机制

- 问题真实：新增 `test_d1_selective_upsert_20261109.py` 在 Phase1 代码上运行，原始末行 **`8 failed, 4 passed in 3.88s`**。六例通过真正执行生成包、用 SQLite `AFTER UPDATE OF 索引列` 触发器证明：日期、setup/年数、首次 NULL 哈希仍触发索引列更新；不是仅检查字符串。
- 根因：两脚本 `set_cols → conflict_clause → bundle.add_inserts` 无条件把所有非主键列放进 SET；广覆盖日期变化进入 changed 后，即使二级索引键相同也维护它们。Phase1 Miniflare 的 3/4 写数及真实日期单变量重放是独立依据。
- 机制可达：实施前离线 Miniflare 用实际 45/81 列 schema 验证候选分写，日期及首次哈希更新 3/4→1/1，重复包 0/0，索引键从/到 NULL 均结果正确。先原子落盘 `d1-phase2-root-cause.json` 再修改业务脚本。

每批仍使用原生完整 `INSERT ... VALUES ... ON CONFLICT(fund_code)`，顺序放入同一导入包两遍，条件在数据库当前行上判断：

1. **完整分支**：SET 全部非主键列，仅在 `composite_score IS NOT excluded.composite_score OR fund_type IS NOT excluded.fund_type` 时更新；screener 再包含 `scale IS NOT excluded.scale`。
2. **非索引分支**：SET 全部非索引、非主键列，**包含所有日期、setup_years 和 row_hash**；仅在上述索引键逐个 `IS excluded` 且 `row_hash IS NOT excluded.row_hash` 时更新。

`IS` / `IS NOT` 是 NULL 安全的相等/不同判断。不能合并成多个相同 conflict target 的 ON CONFLICT 尾缀：SQLite 每行只执行首个匹配子句，其 WHERE 为假也不会尝试后续子句。两条语句复用已有 `Bundle.add_inserts` 与字节封顶机制，仅两个脚本各增加约十行生成逻辑，无新抽象、缓存分类或依赖。

新主键在第一遍完整插入，第二遍看到相同 hash 会跳过；第一遍中断后若第二遍独立遇到缺失主键，也仍是完整 INSERT。已有行索引键变化由第一遍一次写全，第二遍跳过；仅非索引字段变化由第二遍一次写全，第一遍跳过。首次空哈希/新增 score_date 若索引键没变，走非索引分支。`INCREMENTAL=0` 与 legacy 原全表替换语义保持。

### 不匹配数据不会获得新哈希

安全性不依赖“整包一定是单事务”的假设：

- 每条真正更新的语句都把使整行对应目标 hash 的必要字段**和 hash 一次写入**；没有单独“先推进 hash”的语句。
- 完整分支要么完整成功，要么同一语句回滚；非索引分支更新前再核对数据库当前索引键，因此中间另一个完整状态改变了索引键时，不会套用与这些键不相符的 hash。
- 第一遍成功、第二遍未运行时：新行及索引变化行已经全列正确；仅非索引变化行仍是旧字段与旧 hash。原包重放会补完后者，已匹配行不再 UPDATE。
- 不新增分布式并发锁；不同快照交错时仍可能由较后写入的完整状态覆盖较新快照，这是原导入链的并发/新鲜度边界。保证的是每次本方案写入后的字段/hash 对应关系，不承诺外部任意写库后仍保持哈希正确。
