## 可复核依据与根因边界

- 诊断 `models-diagnosis.json` 的 `overfit_public_delivery`：云 Nov9 21:40 为
  74/red，公开主/ext 仍 Nov6 70/red。90/20/90/100 加权74符合既有三源口径。
- 本轮只读 SSH 再核原日志：Nov9 `R2_UPLOAD_TIMEOUT 960s`，随后
  `overfit_monitor.sh ... 退出码=0`。`.env` 只读取白名单字段，实值
  `R2_UPLOAD_HTTP_TIMEOUT=600`；两把原锁的元信息可读，但元信息不证明当晚谁持锁。
- 旧 `build_output` 调整个 `upload-data-large`，范围包含无关大文件。
  `_acquire_r2_upload_lock` 的 skip 路径最多等默认60秒，240秒排队上限不是此路径实际等待。
  锁后未传已有 `R2_UPLOAD_WORK_TIMEOUT`，S3 单请求最多五次尝试，600秒超时与
  1+2+4+8秒退避可构成3015秒路径，超过960秒父墙；这也不是整个HTTP链的绝对最坏上限。
  上传还有线程池收尾、PUT/HEAD及缓存清理（缓存清理另有三次请求重试）。
- 旧 `subprocess.run(capture_output=True)` 通过 communicate 排空管道，**未证实管道死锁**。
  真正已证实的是整轮预算缺席/范围扩大、超时只杀直接子进程以及失败被吞后报成功。
  历史超时分支没保留 `TimeoutExpired` 中的子进程输出；当晚究竟卡在哪个网络请求，
  无法倒推。没有将网络底层未知写成已解决。
- 用固定基线 AST 隔离重放原上传分支，注入超时后仍到达 return out；新 CLI 则
  将发布失败返回给 shell。原 `build_output` 的计算结果字典返回值保留，上传归 CLI 调度。
  一跳 caller 搜索仅发现定时包装层，没有其它 Python 调用方；上游
  `OVERFIT_SKIP_R2=1` 继续表示计算完成、交付由上游负责，不伪称已验公开发布。

## 修复机制与验收预期

1. 通过现有 `upload-data-files` 仅传两份当前 canonical 产物，不用旧快照补传。
   复用原生产写入守卫、原 data 域锁+全局共享屏障、HTTP重试、独立产物登记及缓存清理。
   overfit 前缀仍由原路由归全局路径，再取 data 域；没有改成独立小锁。
   其它 data-large 写者仍受相同互斥约束，等待后读取当前文件，防旧快照排队后覆盖新代。
2. 发布子进程单请求30秒、锁后已有工作预算780秒、默认整链墙960秒；不抬总预算。
   等锁重试窗口限制0–60秒，仍保留让路；锁忙以75表达发布未完成。
   现有S3预算不覆盖的purge/公开读取也在父进程整链墙内。
3. 子进程输出接临时文件，避免孙进程持管道拖住回收；超时TERM后最多等1秒，再KILL
   自己的独立进程组，回收直接子进程最多2秒。其它任务的进程和锁不动。
4. 取锁后检查主/ext时间和原有结构/compact校验；上传后四次GET核主/ext在
   `ss.fx8.store`、`ssd.fx8.store` 均与上传前本地字节哈希一致，并再查本地没有被替换。
   任何半成功、旧缓存、缺文件、不同代、上传非零或超时均明确非零。
   `stage=upload`/`R2_UPLOAD_INCOMPLETE` 与原上传器错误输出表示上传阶段未完成；
   上传命令返回后 `R2_PUBLIC_UNCONFIRMED`/rc76 表示公开副本未对齐或验证网络失败，
   不把短时旧缓存说成PUT失败。公开验证每请求30秒且整链受960秒墙约束；
   明确重试publish-only会重传两件并清理缓存，不触发计算。
   这不是远端双对象事务；失败期间仍可能短暂半套，不能宣称原子远端发布。
5. 计算文件和预警发送结果保留。CLI非零经原shell结束行、systemd与schedule统计消费，
   不再把计算成功写成完整交付成功。`delivery_evidence` 当前无overfit策略登记，且是可关闭的
   best-effort元数据，未造无人消费的回执、队列或定时器。
